# F1.2 — Pure load/save graph ops

- **Status:** planned
- **Milestone:** M1 · **Level:** L1
- **Depends on:** F1.1 (UiGraph JSON schema)

## 1. Purpose (abstract)

Give `@ui-graph/core` the two pure I/O ops that turn a `UiGraph` between its
in-memory form and its on-disk JSON form. `load` reads a serialized graph and
validates it against the F1.1 JSON schema before handing back a typed `UiGraph`,
so malformed files are rejected at the boundary instead of corrupting downstream
ops. `save` writes the graph back in a single **canonical** form, making the file
a stable, content-addressable artifact: extracting, loading, and re-saving the
same graph always yields the same bytes, which is what lets the rest of the
system (overlay `base` hash, caching, diff) trust the document.

## 2. Contract & boundary

**Lives in `@ui-graph/core`** — framework-agnostic, no React/Angular, no network,
no filesystem assumptions baked into the ops themselves (callers pass strings).

Exposes (operating on the shared IR from `30-ir-spec-v0.md`):

```ts
function load(json: string): UiGraph;          // parse + schema-validate, or throw
function save(graph: UiGraph): string;          // canonical JSON serialization
function canonicalize(graph: UiGraph): UiGraph; // stable ordering, no I/O
```

`load` throws a schema validation error (field-level, from F1.1's validator) on
any non-conforming input. `save` is total: any in-memory `UiGraph` serializes.

**Depends on:** F1.1 JSON schema + its validator, and the IR types from F0.4.
**Does not** depend on `validate()` invariants (F1.3) — schema conformance is the
only gate here; structural/golden invariants are a separate, later op.

## 3. Abstract design

`load`: parse JSON → validate against the F1.1 schema → return the typed object.
Parse failure and schema failure both surface as thrown errors carrying the
offending field path; `load` never returns a partial or coerced graph.

`save`: run `canonicalize`, then serialize deterministically (stable key order,
fixed indentation, trailing-newline policy fixed once). Canonical ordering is
defined by stable `id`: `nodes` sorted by `id`, `edges` sorted by `id`, and
object keys emitted in a fixed order. Ordering is by `id` (never structural
position) to match merge/diff identity (`30-ir-spec-v0.md` §5).

Key decision: canonicalization is a pure transform separate from serialization,
so other ops can compare graphs canonically without going through strings.
Trade-off accepted: round-trip is byte-equivalent **modulo canonical ordering**,
not byte-identical to arbitrary hand-formatted input — re-saving normalizes
formatting and ordering, which is exactly the property content-addressing needs.

## 4. Data shapes

This feature owns **no new IR types**. It consumes `UiGraph` (and its
`GraphNode` / `GraphEdge` / `meta`) exactly as defined in `30-ir-spec-v0.md`. The
only feature-local concept is the *canonical form* — a normalization (sorted by
`id`, fixed key order) of an existing `UiGraph`, not a new type.

## 5. Test strategy (write these first)

1. **Round-trip identity:** `save(load(doc))` of a representative graph equals a
   re-`save` of the same graph — byte-equivalent under canonical ordering.
2. **Idempotent canonicalization:** `save(load(save(load(doc))))` is a fixed
   point (second round-trip changes nothing).
3. **Ordering normalization:** a graph whose `nodes`/`edges` are shuffled and
   whose object keys are reordered saves to the *same* canonical bytes as the
   sorted original.
4. **Schema rejection — missing required field:** `load` of a doc missing e.g.
   `version` or an edge `modality` throws a schema validation error.
5. **Schema rejection — bad enum:** `load` of a doc with an invalid `modality`
   or `source` value throws with the offending field surfaced.
6. **Parse rejection:** `load` of non-JSON / truncated input throws (not returns).
7. **Valid load:** the `30-ir-spec-v0.md` §3 example graph loads to a typed
   `UiGraph` with all nodes/edges/witnesses intact.

## 6. Self-check / acceptance criteria

- A graph loaded and saved produces an **equivalent canonical document**
  (round-trip is byte-equivalent modulo canonical ordering; second round-trip is
  a fixed point).
- Loading a **malformed file** (missing required field, bad `modality`/`source`
  enum, or non-JSON) **throws a schema validation error** with a field-level
  message.
- `@ui-graph/core` still has zero React/Angular/network/filesystem deps in these
  ops, and the F0.3 self-check (typecheck + lint + test) is green.

## 7. Soundiness / open questions

- **Numeric `confidence` formatting:** canonical serialization must fix a stable
  representation (e.g. `1.0` vs `1`) so round-trips are byte-stable; decide once.
- **Schema vs. invariants split:** `load` validates *schema* only; it deliberately
  does not enforce dangling-ref / witness / `must`-provenance invariants — those
  belong to F1.3 `validate()`. A schema-valid but invariant-violating file loads
  successfully here by design.
