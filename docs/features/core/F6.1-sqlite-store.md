# F6.1 — SQLite workspace store

- **Status:** done
- **Milestone:** M6 (persistence) · **Level:** L1
- **Depends on:** F1.2 (load/save ops), F1.4 (overlay), F5.x (proposals), Tier-3 (observations)

## 1. Purpose (abstract)

Persistence had grown into a scatter of JSON sidecars per workspace —
`ui-graph.json`, `ui-graph.soundiness.json`, `ui-graph.overlay.json`,
`observations.log.jsonl`, `proposals.json`. Each tool re-read and rewrote whole
files, `get_proposals` filtered a 1500-element array in memory, and the canonical
state was spread across five files. This feature makes a single per-workspace
**SQLite database (`uigraph.db`) the canonical store**, replacing the sidecars.
JSON becomes an import/export interchange format, not the live store.

## 2. What goes where (document vs. relational)

The split follows the data's nature, not dogma:

- **Documents** (JSON in a `docs` table, keyed `graph` / `overlay` / `soundiness`).
  The base graph and overlay must round-trip **byte-faithfully** — content
  hashing (`hashValue`) and `validateGraph`/`validateMerged` depend on exact
  structure and order. Storing them relationally and reconstructing would risk the
  hash; storing the JSON verbatim cannot.
- **Relational rows** — `proposals` and `observations`. These are
  high-cardinality, queryable, and append-y. `get_proposals` filters map straight
  to SQL (`WHERE screen=? AND evidenced=1 AND confidence>=?`) instead of scanning
  an array; observations are ordered rows.

## 3. Boundary & soundness

- **Driver:** Node's built-in `node:sqlite` (`DatabaseSync`) — no native
  dependency, no build step (Node 22+). Lives in `@uigraph/core` (`store.ts`),
  exported only through the node-only `@uigraph/core/node` subpath, so the
  browser-safe core stays pure and the dashboard never imports it.
- **Validation preserved:** `setBaseGraph` runs `validateGraph` and `setProposals`
  runs `validateProposals` before writing — an invalid graph/sidecar can never be
  persisted, exactly as the old `saveGraph`/`saveProposals` guaranteed.
- **Golden invariant intact:** the merge/fold pipeline is unchanged. `loadMergedGraph`
  still does base → `mergeOverlay` → `applyObservations` → `validateMerged`; only the
  source moved from files to the store. Tier-3 observations still enter via
  `appendObservation`, so "the observation, not the guess, enters the graph" holds.

## 4. Surface

- `Store` / `openStore(dbPath)` (core/node): `setBaseGraph`/`getBaseGraph`,
  `getSoundiness`, `getOverlay`/`setOverlay`, `appendObservation`/`getObservations`,
  `setProposals`/`getProposals`/`queryProposals(filter)`, `close()`.
- `importJsonWorkspace(dir, store)` (core/node): one-shot JSON→db migration.
- CLI: `uigraph map` writes `<dir>/uigraph.db`; `uigraph migrate <dir>` imports
  legacy sidecars; `uigraph serve` and the MCP tools read/write the db; `uigraph
  diff` accepts `.db` or `.json` sources.
- MCP: every tool (`get_graph`, `get_proposals`, `get_grounding`, `plan_path`,
  `update_graph`, `report_observation`) is backed by the store via a `withStore`
  open/close helper; `dbPath(ctx)` = `<dir>/uigraph.db`.

## 5. Tests / acceptance

- `store.test.ts` (7): document round-trip, invalid-graph rejection, overlay
  round-trip, observation order + optional fields, proposal reconstruct (null
  optionals dropped), SQL filters, replace-not-accumulate.
- `mcp` (14) and `cli` (12) suites re-pointed to seed the store; all green.
- Migrated the live demo (`/tmp/demo`: 761 proposals, 14 observations) and the production-app
  (1548 proposals, 11 soundiness) workspaces; the dashboard serves
  identically from `uigraph.db`. Full `scripts/check.mjs` green.

## 6. Open questions

- Base graph stored as a JSON document, not normalized node/edge tables; graph
  queries (recursive-CTE reachability, edge-by-modality) would want denormalized
  tables, but dual storage risks drift and the hash depends on the document. A
  read-only derived view could be added later without changing the source of truth.
- No migrations/versioning of the db schema yet (single version). `CREATE TABLE IF
  NOT EXISTS` is forward-only; a schema-version row + migrations is future work.
