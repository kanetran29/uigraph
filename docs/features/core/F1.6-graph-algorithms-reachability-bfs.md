# F1.6 — Graph algorithms: reachability and plan_path BFS

- **Status:** planned
- **Milestone:** M1 · **Level:** L1
- **Depends on:** F1.5 (`diff(a, b)` over two graphs)

## 1. Purpose (abstract)

This feature adds the small graph-algorithms layer to `@uigraph/core`: `reachability`, which reports the set of nodes reachable from a start node, and `plan_path`, a breadth-first search that returns a shortest sequence of edges from a source node to a target node. These are the navigation primitives the MCP `plan_path` tool and the dashboard steps view consume so neither has to re-derive routes over the IR. They operate purely on IR nodes and edges and treat `may`/`unknown` edges as traversable, so a guarded-but-possible transition is never silently dropped from a plan.

## 2. Contract & boundary

Lives entirely in **`@uigraph/core`** — framework-agnostic, no React/Angular imports, no I/O. It consumes only the shared IR (`UiGraph`, `GraphNode`, `GraphEdge`) defined in `30-ir-spec-v0.md`.

Public surface:

```ts
export function reachability(graph: UiGraph, startId: string): Set<string>;
export function planPath(graph: UiGraph, fromId: string, toId: string): PathResult;
```

- **Depends on:** the IR types only. It does not depend on `load`/`save`, `validate`, `merge`, or `diff`; callers pass an already-loaded (and typically already-merged) `UiGraph`.
- **Consumed by (downstream):** `@uigraph/mcp` `plan_path` (F5.3), the local API server (F4.4), and the dashboard steps view (F6.5).

Edge direction is honored (`from → to`); the graph is treated as directed. Modality and source are read-through, never filtered — all declared edges are traversable.

## 3. Abstract design

**Inputs → outputs.** Both functions take a `UiGraph` and node id(s). `reachability` returns the set of node ids transitively reachable following directed edges, **including** `startId` itself. `planPath` returns either a found path (the ordered list of edges traversed, plus the node sequence) or an explicit no-path result.

**Approach.** A single BFS over an adjacency index built from `graph.edges` keyed by `from`. BFS guarantees the returned edge sequence is shortest in **hop count** (number of edges) — the relevant cost here, since edges are unweighted. `reachability` is the BFS visited-set; `planPath` is the same BFS with parent-pointer backtracking from `toId`.

**Key decisions / trade-offs.**

- **`may`/`unknown` are traversable.** Plans over-approximate: a conditional transition is included because the agent reads guards for itself (legibility over decidability, dossier §4.4). We do not prune by guard.
- **Shortest = fewest edges**, not lowest-confidence-weighted; `confidence` is ignored for v1. Among equal-length paths the first found by deterministic edge order wins; iteration order over `graph.edges` makes results stable for golden tests.
- **Explicit no-path result**, not an exception or empty array, so callers (MCP, dashboard) can render a clear "unreachable" state distinct from a zero-length self-path.
- **`from === to`** yields a valid zero-edge path (already at target).
- Unknown/missing `fromId` or `toId` (not a node in the graph) yields no-path.

## 4. Data shapes

This feature owns one result type; everything else is shared IR (do not redefine — see `30-ir-spec-v0.md`).

```ts
export interface PathResult {
  found: boolean;
  nodes: string[]; // node ids in visitation order, fromId..toId; [] when not found
  edges: string[]; // GraphEdge.id sequence, length nodes.length - 1; [] when not found
}
```

`reachability` returns a plain `Set<string>` of node ids and owns no new type.

## 5. Test strategy (write these first)

Use a small hand-built fixture `UiGraph` with a known shape (e.g. a chain plus a branch, one disconnected node, and at least one `may` and one `unknown` edge).

1. **reachability — basic set:** from a chosen start, `reachability` returns exactly the known reachable node ids, and includes the start node itself.
2. **reachability — traverses may/unknown:** a node reachable only via a `may` or `unknown` edge is present in the result.
3. **reachability — respects direction:** a node reachable only by going against an edge's direction is **absent**.
4. **reachability — disconnected:** a node in no path from start is absent from the set.
5. **planPath — shortest path exists:** for a reachable target, `found` is true and `edges` is the known shortest edge-id sequence; assert it is shortest (no shorter sequence exists) and valid (consecutive edges chain `from→to`).
6. **planPath — picks fewest hops over a longer alternative:** when two routes exist, the returned path has the minimal edge count.
7. **planPath — same node:** `planPath(g, x, x)` returns `found: true`, `nodes: [x]`, `edges: []`.
8. **planPath — no path (disconnected target):** for an unreachable target, `found: false`, empty `nodes`/`edges`.
9. **planPath — unknown node id:** a `fromId`/`toId` not present in the graph yields the no-path result, not a throw.
10. **purity:** neither function mutates the input `graph`, its `nodes`, or `edges` (deep-equal before/after).

## 6. Self-check / acceptance criteria

- [ ] On the fixture graph, `reachability` returns the known-correct reachable set (including start, traversing `may`/`unknown`, honoring direction).
- [ ] `plan_path` returns a shortest **valid** edge sequence when a path exists (minimal hop count, edges chain correctly).
- [ ] Unreachable targets yield an explicit no-path result (`found: false`), distinct from a zero-edge same-node path.
- [ ] Functions are pure: input graph is provably unchanged after each call.
- [ ] `@uigraph/core` still has zero React/Angular dependencies; this layer imports only IR types.
- [ ] `node scripts/check.mjs` prints `CHECK GREEN` (typecheck + tests + lint).

## 7. Soundiness / open questions

- **Over-approximation is intentional.** Plans may include guarded (`may`) or undetermined (`unknown`) transitions that are infeasible at runtime; uigraph never evaluates guards, so a returned path is "structurally possible," not "guaranteed walkable." This is a declared limitation, consistent with the legibility-over-decidability principle, not a bug.
- **No weighting in v1.** `confidence` does not influence path choice; shortest is purely fewest edges. Confidence-aware or guard-aware ranking is out of scope.
- **Single shortest path only.** `plan_path` returns one path, not all shortest paths or k-best alternatives. Out of scope for v1.
