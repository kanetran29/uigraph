# F1.1 — UiGraph JSON schema
- **Status:** planned
- **Milestone:** M1 · **Level:** L0
- **Depends on:** F0.4

## 1. Purpose (abstract)
The on-disk `ui-graph.json` is the wire format every other part of uigraph reads and writes — load/save, the MCP server, and the dashboard. This feature publishes a single formal JSON schema that *is* the contract for that file, so all consumers agree on field names, types, and required fields, and a malformed graph is rejected at the boundary with a clear, field-level error instead of failing deep inside an op. It is the machine-checkable mirror of the IR spec (`30-ir-spec-v0.md`), turning prose invariants about shape into an automated gate.

## 2. Contract & boundary
**Lives in `@ui-graph/core`** — framework-agnostic, with zero React/Angular knowledge. It describes the same IR a React graph and an Angular graph both serialize to.

**Exposes:**
- A JSON Schema (Draft 2020-12) document describing a serialized `UiGraph` (and the sidecar `Overlay`), shipped as a static asset in core.
- A compiled validator surface: `validateUiGraphDocument(data) → { valid: boolean; errors: SchemaError[] }`, where `SchemaError` carries a JSON-pointer path and message.

**Depends on:** F0.4 (the IR TypeScript types — `UiGraph`, `GraphNode`, `GraphEdge`, `Witness`, `Overlay`, and the `Modality`/`Source`/`NodeKind` enums). The schema mirrors those types; F0.4 is the source of truth for the shapes and is not redefined here.

## 3. Abstract design
**Input → output:** an arbitrary parsed JSON value in → a boolean valid/invalid plus a list of field-level errors out. The schema encodes structural shape only; it does not encode the *semantic* invariants (dangling refs, witness-presence, must-provenance) — those belong to F1.3 `validate()`. Keeping the split clean means the schema answers "is this the right shape of document?" and `validate()` answers "is this a sound graph?".

Key decisions:
- **JSON Schema as the canonical artifact**, compiled with a standard validator (Ajv) so errors are field-level and the schema is reusable by any consumer (MCP, dashboard) without importing TS.
- **Enums pinned** for `modality`, `source`, and `kind` so an invalid value is rejected by enum, not by free string.
- `required` lists and `additionalProperties: false` on each object so a missing field or an unexpected key surfaces a precise pointer.
- `version` fixed to the constant `0`; `confidence` constrained to `0 ≤ x ≤ 1`.

Trade-off: cross-field/referential rules (e.g. `edge.from` resolves to a node) are deliberately *out of scope* for the schema and deferred to F1.3, avoiding brittle, hard-to-express JSON-Schema conditionals.

## 4. Data shapes
This feature owns no new IR types; it owns the **schema document** and a small validator-result shape:

```ts
interface SchemaError { path: string; message: string; } // path is a JSON pointer
interface SchemaResult { valid: boolean; errors: SchemaError[]; }
```

All graph/overlay shapes (`UiGraph`, `GraphNode`, `GraphEdge`, `Witness`, `Overlay`) and the `Modality`/`Source`/`NodeKind` enums are defined in `30-ir-spec-v0.md` / F0.4 and only *referenced* by the schema.

## 5. Test strategy (write these first)
1. The §3 concrete example from the IR spec (`Home → Login` must-edge, `Login → Dashboard` may-edge) validates as a complete, representative `ui-graph.json`.
2. A graph missing a required field (e.g. an edge without `modality`, or a node without `id`) is rejected, with the error path pointing at the offending field.
3. An edge with an invalid `modality` enum value (e.g. `"maybe"`) is rejected.
4. An edge or witness with an invalid `source` enum value (e.g. `"guessed"`) is rejected.
5. An edge with `confidence` out of range (e.g. `1.5` or `-0.1`) is rejected.
6. A document with `version` ≠ `0`, or with an unexpected extra property, is rejected.
7. A valid `Overlay` sidecar document validates against the overlay schema; a non-`manual` source inside it is *not* caught here (shape-valid) — documenting the schema/validate boundary.

## 6. Self-check / acceptance criteria
- A representative `ui-graph.json` (the IR spec §3 example) validates clean against the schema.
- Each known-bad document (missing required field, bad `modality`, bad `source`, out-of-range `confidence`, wrong `version`, extra key) fails validation and returns a field-level error with a usable path.
- `node scripts/check.mjs` is green: `tsc --noEmit`, `vitest run`, and `eslint .` all pass with these tests committed.

## 7. Soundiness / open questions
- None for v1 shape validation. Referential and golden invariants (dangling refs, witness presence, must-provenance, overlay purity) are intentionally deferred to F1.3 `validate()`, not this schema.
- Open: whether to generate the JSON Schema from the F0.4 TS types or hand-author and drift-test it against them. v1 hand-authors the schema and relies on the IR-spec example tests to catch drift.
