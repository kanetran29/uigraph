# F1.3 — Invariant validation (golden witness invariant)

- **Status:** planned
- **Milestone:** M1 · **Level:** L1
- **Depends on:** F1.2 (Pure load/save graph ops)

## 1. Purpose (abstract)

`validate` is the deterministic guard that enforces the **golden invariant**:
*no edge enters the base graph without a deterministic witness* (a static proof
or a runtime observation). It checks a `UiGraph`'s structural and provenance
invariants — referential integrity, unique ids, witnessed `static`/`runtime`
edges, consistent modality/source, and overlay purity — and returns a list of
actionable errors. This is what makes a uigraph "verified" rather than merely
"a map": every other op (`merge`, `diff`, MCP, dashboard) can trust a graph that
has passed `validate`.

## 2. Contract & boundary

Lives in **`@ui-graph/core`** — pure, framework-agnostic, no React/Angular, no IO
(callers handle reading files via F1.2 `load`). It is the canonical
implementation of the invariants enumerated in `docs/30-ir-spec-v0.md §4`.

Exposes:

```ts
export interface ValidationError {
  code: ValidationCode;   // e.g. 'DANGLING_REF', 'MISSING_WITNESS'
  message: string;        // actionable, names the offending id/field
  ref?: string;           // offending node/edge id, when applicable
}

// validate the base graph alone, or a base + overlay pair (merge view).
export function validate(graph: UiGraph, overlay?: Overlay): ValidationError[];
```

Depends on: the shared IR types (`UiGraph`, `GraphEdge`, `GraphNode`, `Overlay`,
`Source`, `Modality`, `Witness`) from `@ui-graph/core` (F0.4 / §2 of the IR spec).
JSON-schema shape conformance is F1.1's job and runs at `load` time; `validate`
checks the **semantic** invariants the schema cannot express. Returning an empty
array means the graph is clean; `validate` never throws on a malformed-but-typed
graph — it reports.

## 3. Abstract design

Input: a typed `UiGraph` (optionally with an `Overlay`). Output: a flat
`ValidationError[]`, **exhaustive** — every violation is reported, not just the
first, so a fixer sees the whole picture in one pass. Deterministic: same input
→ same ordered error list.

Checks (one error code per invariant, per IR spec §4):

1. `DANGLING_REF` — every `edge.from`/`edge.to` resolves to a node id present in
   the graph (or added by the overlay, when an overlay is supplied).
2. `DUPLICATE_ID` — node ids and edge ids are each globally unique.
3. `MISSING_WITNESS` — every edge with `source` `static` or `runtime` carries a
   `witness` whose `source` matches the edge's. **The golden invariant.**
4. `OVERLAY_IMPURITY` — every overlay element has `source: 'manual'`; the base
   graph contains no `source: 'manual'` element.
5. `MUST_PROVENANCE` — a `must`-edge originates only from `static` or `runtime`
   provenance (never `manual`); `manual` edges are `may`/`unknown`.
6. `CONFIDENCE_RANGE` — `0 ≤ confidence ≤ 1`.

Key decision: `validate` treats `guard`/`effect` text as **opaque** (legibility
principle, §6) — it never parses guard strings. Trade-off: the check stays cheap
and total, at the cost of catching no semantic guard errors (by design — not its
job).

## 4. Data shapes

This feature **owns** only `ValidationError` and the `ValidationCode` union
(`'DANGLING_REF' | 'DUPLICATE_ID' | 'MISSING_WITNESS' | 'OVERLAY_IMPURITY' |
'MUST_PROVENANCE' | 'CONFIDENCE_RANGE'`). All graph/overlay types are the shared
IR — see `docs/30-ir-spec-v0.md §1–2`; do not redefine them here.

## 5. Test strategy (write these first)

1. A fully-witnessed, well-formed graph → `validate` returns `[]`.
2. Edge whose `to` (and a second case, `from`) names no node → one
   `DANGLING_REF` per dangling endpoint, naming the edge id.
3. Two nodes (and separately two edges) sharing an id → `DUPLICATE_ID`.
4. `static` edge with no `witness`, and a `runtime` edge with no `witness` →
   `MISSING_WITNESS` each; a `manual` overlay edge with no witness is **not**
   flagged.
5. Edge whose `witness.source` disagrees with `edge.source` → `MISSING_WITNESS`.
6. Overlay element with `source: 'static'`, and a base edge with
   `source: 'manual'` → `OVERLAY_IMPURITY` each.
7. `must`-edge with `source: 'manual'` → `MUST_PROVENANCE`.
8. `confidence` of `-0.1` and of `1.5` → `CONFIDENCE_RANGE` each; `0` and `1`
   pass.
9. A graph seeded with several distinct violations → all are reported in one
   call (exhaustiveness), each with the correct `code` and `ref`.
10. `validate(base, overlay)` where the overlay adds the node an edge points to →
    no `DANGLING_REF` (overlay nodes satisfy referential integrity in merge view).

## 6. Self-check / acceptance criteria

- [ ] `validate` returns `[]` on a well-formed, fully-witnessed graph.
- [ ] Each seeded violation (dangling endpoint, duplicate id, missing/mismatched
      witness on a `static`/`runtime` edge, overlay impurity, `must` from
      `manual`, out-of-range confidence) yields a specific error with the
      correct `code` and offending `ref`.
- [ ] All violations in a multi-fault graph are reported in a single call.
- [ ] Every new function/type has a leading doc-comment; no inline comments.
- [ ] `node scripts/check.mjs` prints `CHECK GREEN` (typecheck + tests + lint).

## 7. Soundiness / open questions

None for v1. `validate` is total and deterministic over the typed IR. It does
**not** interpret guard text, verify that a witness's `file`/`loc` actually
points at real source, or check that a `runtime` `observationId` exists in the
log — those are out of scope (legibility over decidability; witness-content
verification belongs to the runtime/replay tier, not this op).
