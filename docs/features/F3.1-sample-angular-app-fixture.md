# F3.1 — Scaffold sample-angular-app golden fixture

- **Status:** planned
- **Milestone:** M3 · **Level:** L0
- **Depends on:** F0.5

## 1. Purpose (abstract)

The Angular adapter (F3.2–F3.5) needs a controlled target whose correct output is
known *before* the extractor exists. This feature hand-authors that target: a
small Angular app with a deliberately chosen, fully enumerated `RouterModule` /
`Routes` configuration — including nested `children` and `canActivate` guards —
plus `Router.navigate` / `navigateByUrl` and `routerLink` navigations. Because
the app is small and authored on purpose, its expected transition graph is known
by construction; it is the golden ground truth every later Angular adapter
feature is scored against, not a real codebase we hope to handle.

## 2. Contract & boundary

This feature is **not core and not an adapter** — it is a *fixture*, an input the
adapter reads. It lives under `examples/sample-angular-app/` as a buildable
Angular app plus a sibling human-authored manifest. It imports neither
`@uigraph/core` nor any `@uigraph/adapter-*`; it is plain Angular + `@angular/router`
source.

**Exposes** (consumed by F3.2–F3.5):
- A compiling/building Angular app exercising the Angular router constructs
  catalogued in `40-adapter-contract.md §4` (the Angular row).
- A `MANIFEST.md` (and a machine-checkable list) enumerating the known routes,
  children, guards, and navigation call sites — the documented "known set".

**Depends on:** F0.5 (adapter contract) only to know *which* constructs the
adapter promises to handle, so the fixture covers exactly that surface. The
golden `UiGraph` JSON encoding of this manifest is produced later (F3.5); here we
own only the app and the prose/known-set manifest.

## 3. Abstract design

Input: nothing (hand-authored). Output: a buildable app + a manifest of its known
set.

Key decisions:
- **One module, nested routes.** Author a single `Routes` array with at least one
  parent route carrying `children`, so the fixture exercises the parent/child
  nesting F3.2 must resolve — flat-only routes would not test it.
- **Every adapter rule gets a witness in source.** Cover each row of the Angular
  table in `40-adapter-contract.md §4`: a literal `routerLink` and a literal
  `Router.navigate` / `navigateByUrl` (→ expected `must`), a `canActivate`-guarded
  route (→ expected `may` with the guard class name as symbolic text, F3.4), and
  at least one non-literal/computed navigate target (→ expected over-approximated
  `may` over the route set, F3.3). Including the hard cases on purpose is what
  makes the fixture able to *fail* a naive adapter.
- **Small and total.** Keep the route set tiny so the manifest can enumerate the
  full expected node/edge set exhaustively, by hand, without ambiguity.
- **Manifest is the spec, not a dump.** The manifest is authored from intent
  (what we *put* in the app), then the app is written to match it — so it is an
  independent oracle, not a transcript of the code.

Trade-off: the fixture is intentionally not representative of a real app's size,
and uses a single eager-loaded module (no lazy `loadChildren`) to keep the known
set total; real-world coverage is not M3's job.

## 4. Data shapes

This feature defines **no IR types** — shared types live in `30-ir-spec-v0.md`
and are not redefined or imported here. It owns one local artifact: the manifest
schema for the known set, expressed as plain documented rows, e.g.

- **route**: `{ path, component, parentPath: string | null, canActivate?: string,
  expectedNodeLabel }`
- **navigation**: `{ fromRoute, idiom: 'routerLink' | 'navigate' | 'navigateByUrl',
  targetExpr, literal: boolean, expectedModality: 'must' | 'may', guard?: string }`
- **guard**: `{ className, symbolicText, guardsRoute }`

These describe expectations in plain terms (which become `GraphNode` /
`GraphEdge` fields in the F3.5 golden), so the manifest is readable without the
IR.

## 5. Test strategy (write these first)

1. **Build test.** `pnpm --filter sample-angular-app build` (and `tsc --noEmit`)
   exits zero — the fixture is a real, compiling Angular app.
2. **Manifest exists and parses.** The known-set manifest file is present and its
   enumerated rows parse into the route/guard/navigation lists.
3. **Routes present, with nesting.** Each route declared in the manifest is found
   in the `Routes` config (matching `path` / `component`), every manifested
   `children` relationship is present as a nested route, and there is no manifest
   route missing from source and no extra unlisted route in source.
4. **Navigation call sites present.** Each manifest navigation idiom
   (`routerLink`, `Router.navigate`, `navigateByUrl`) has a corresponding call
   site in source.
5. **Idiom coverage.** Assert the fixture contains at least one of each: a literal
   `must` navigation, a `canActivate`-guarded `may` route, and a non-literal
   computed-target navigation — so F3.3/F3.4 each have a case.
6. **Guards present.** Each manifest guard maps to a `canActivate` entry in the
   route config referencing the recorded guard class name.

## 6. Self-check / acceptance criteria

- `examples/sample-angular-app` **builds** (and typechecks) green via the
  workspace scripts; the self-healing gate (`scripts/check.mjs`) passes with the
  fixture in the tree.
- A **written manifest enumerates** the app's known routes, children, guards, and
  navigations, and tests 2–6 above confirm every manifest entry is actually
  present in source (and vice versa) — establishing it as usable golden ground
  truth for F3.2–F3.5.
- The fixture imports no `@uigraph/*` package.

## 7. Soundiness / open questions

- The **golden `UiGraph` JSON** (the committed expected graph) is intentionally
  *out of scope here* — it is authored in F3.5 once the IR encoding and node/edge
  ids are settled; F3.1 ships only the app and the prose/known-set manifest.
- The included **non-literal/computed navigation** is the deliberate
  over-approximation case; F3.1 only guarantees the call site exists, not how the
  adapter fans it out (that is F3.3).
- **Lazy `loadChildren` routes are excluded** in v1 to keep the known set total;
  the fixture covers eager nested `children` only. Lazy-boundary resolution is a
  declared soundiness gap, not a fixture obligation.
- Guard / node `id` and `event` string conventions are not fixed by this feature;
  the manifest records *labels, guard class names, and intent*, leaving id
  assignment to the adapter so the fixture does not prematurely lock the IR
  encoding.
