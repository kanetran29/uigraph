# F0.5 — Adapter contract interface (extract/register/stamp)

- **Status:** planned
- **Milestone:** M0 · **Level:** L0
- **Depends on:** F0.4 (Framework-agnostic IR types)

## 1. Purpose (abstract)

This feature declares the single seam that keeps `@ui-graph/core` framework-agnostic: the `Adapter` interface every framework plugin implements. The whole architecture rests on one rule — *adding a framework means implementing this interface, never editing the core* — and that rule only holds if the contract is a real, compiled type the core owns. v1 makes `extract(projectDir)` the one required capability (source → shared `UiGraph`) and declares `register` and `stamp` as part of the interface but as future stubs, so the DOM-anchor and testid surfaces have a documented home without being built yet.

## 2. Contract & boundary

**Lives in:** `@ui-graph/core` (framework-agnostic). This is a type-and-prose contract, not an implementation. Concrete adapters (`@ui-graph/adapter-react`, `@ui-graph/adapter-angular`) implement it in later milestones.

**Exposes:** the `Adapter` interface and its supporting types (`AdapterContext`, `ExtractOptions`), exported from the core entry point. Minimal surface:

- `name: string` — stable adapter id (`'react' | 'angular'`).
- `detect(projectDir: string): boolean` — cheap framework heuristic.
- `extract(projectDir, opts, ctx): Promise<UiGraph>` — the only v1-required capability.
- `register?(...)` / `stamp?(...)` — declared, optional, **future-stub** signatures (return `never`).

**Depends on:** the IR types from F0.4 (`UiGraph` is `extract`'s return type). **No framework imports** — no `react`, `@angular/*`, or ts-morph types may appear in this contract; that knowledge belongs to adapter packages downstream.

This contract is authored to match the existing reference in `docs/40-adapter-contract.md` §1; this doc is the feature-level spec for landing it.

## 3. Abstract design

An adapter is a plain object the core can hold and call without knowing its framework. The core hands it an `AdapterContext` (cached file reads, a shared TS project, a logger) so adapters never open files or boot a compiler themselves, and `ExtractOptions` (commit hash, ruleset version) so results stay content-addressable.

**Input → output:** `extract` takes a project directory plus context and returns a `UiGraph` (the IR from F0.4). Everything an adapter produces flows through this one return value; the core never branches on framework after it.

**Key decision — declare-but-stub.** `register` (DOM anchor) and `stamp` (testid) are named in the interface now, as optional members typed so any call is a compile-time dead end (`(...args: unknown[]) => never`), and documented as v1 future stubs. This reserves the seam and makes the L0→runtime/testid roadmap legible without committing implementation. **Trade-off:** the alternative — adding these methods only when needed — risks a later breaking change to every adapter; declaring them now costs two stub signatures and zero runtime code.

## 4. Data shapes

This feature **owns** the contract types; it does **not** define IR types (see `docs/30-ir-spec-v0.md`, F0.4 — `UiGraph`, `GraphNode`, `GraphEdge`).

```ts
interface Adapter {
  name: string;
  detect(projectDir: string): boolean;
  extract(projectDir: string, opts: ExtractOptions, ctx: AdapterContext): Promise<UiGraph>;
  /** FUTURE STUB (v1): bind a node to a live DOM anchor. */
  register?(...args: unknown[]): never;
  /** FUTURE STUB (v1): emit a stable testid for a node/edge. */
  stamp?(...args: unknown[]): never;
}

interface ExtractOptions { commit?: string; rulesetVersion: string; }
interface AdapterContext { readFile(path: string): string; log: Logger; }
```

## 5. Test strategy (write these first)

1. **Minimal stub satisfies the contract.** Declare an in-test adapter implementing only `name`, `detect`, and `extract` (returning an empty `UiGraph` — `version: 0`, empty `nodes`/`edges`, valid `meta`) typed as `Adapter`; assert it type-checks and `extract` resolves to a `UiGraph`.
2. **`extract` is the v1-required member.** Assert that omitting `extract` from an `Adapter` is a type error (compile-fail fixture / `@ts-expect-error`), while omitting `register`/`stamp` is allowed.
3. **`register`/`stamp` are present and distinguishable from `extract`.** Assert both are declared optional stub signatures returning `never`, distinct from `extract`'s `Promise<UiGraph>` — so the stub seam is detectably different from the live capability.
4. **No framework leakage.** Assert the contract module imports nothing from `react`, `@angular/*`, or ts-morph (static import-check over the core source).

## 6. Self-check / acceptance criteria

- `node scripts/check.mjs` is green (typecheck + lint + test) for `@ui-graph/core`.
- The `Adapter` interface compiles under strict TS and exports cleanly from `@ui-graph/core`.
- A stub adapter returning an empty `UiGraph` from `extract` satisfies the `Adapter` type.
- `register` and `stamp` exist as documented future-stub signatures, distinguishable from `extract`.
- Zero React/Angular/ts-morph imports in the contract module.

## 7. Soundiness / open questions

- `register`/`stamp` argument and return shapes are intentionally unspecified in v1 (typed `(...args: unknown[]) => never`); their real signatures are deferred until the runtime/testid features exist and must not break existing adapters when filled in.
- Dynamic-target and data-dependent-guard handling is an `extract`-implementation concern (per-adapter, M2/M3), not part of this contract; the contract only fixes the return type as `UiGraph`.
