# F0.3 — Self-healing check gate (scripts/check.mjs)

- **Status:** planned
- **Milestone:** M0 · **Level:** infra
- **Depends on:** F0.2

## 1. Purpose (abstract)

Provide the single deterministic completion gate that every feature must pass before it can be claimed done. It runs the workspace typecheck, tests, and lint and collapses their results into one unambiguous green/red signal with the failing stage named. This is the harness the development cycle (step 5, SELF-HEAL) and every later acceptance check reference, so a feature is never "done" on a red or short-circuited gate.

## 2. Contract & boundary

**Exposes:** an executable Node script at `scripts/check.mjs`, run as `node scripts/check.mjs`. No importable API — its surface is its exit code and stdout. Exit `0` only when all stages pass; non-zero when any fail. It prints exactly one summary line: `CHECK GREEN` or `CHECK RED: <comma-separated failed stages>`.

**Depends on:** the F0.2 toolchain root scripts — `pnpm -r --if-present run typecheck` (tsc `--noEmit`), `pnpm -r --if-present run test` (vitest run), and root `eslint .`. It shells out to these; it owns no compiler, runner, or linter logic of its own.

**Boundary:** repo-root infrastructure, not a workspace package. It is framework-agnostic and has no relationship to `@uigraph/core` or any adapter; it knows nothing of the IR.

## 3. Abstract design

**Input:** the current workspace state on disk. **Output:** an exit code plus a summary line.

The script defines an ordered list of three stages — `typecheck`, `test`, `lint` — each a shell command. Key decision: it **always runs all three** regardless of earlier failures, so one run surfaces the full picture rather than stopping at the first red. Each stage's child-process exit code is captured; a stage is failed iff its command exits non-zero. After all stages run, the script joins the failed stage names into the summary and exits `1` if the failed set is non-empty, else `0`.

Trade-off: running all stages costs more time than fail-fast, but the design prioritizes a complete diagnostic in a single pass over the heal loop — the gate is run repeatedly while healing, and seeing every broken stage at once shortens that loop.

## 4. Data shapes

Owns one internal shape only (no exported types, no IR):

```ts
type Stage = { name: 'typecheck' | 'test' | 'lint'; cmd: string };
```

The run result is just the list of stage names whose command exited non-zero. No shared IR types are involved; this feature predates and is independent of `30-ir-spec-v0.md`.

## 5. Test strategy (write these first)

1. On the clean baseline workspace, the gate exits `0` and prints `CHECK GREEN`.
2. With a deliberate type error introduced, the gate exits non-zero and the summary names `typecheck`.
3. With a deliberately failing vitest test, the gate exits non-zero and the summary names `test`.
4. With a deliberate eslint violation, the gate exits non-zero and the summary names `lint`.
5. With errors in two stages at once, the gate runs all stages and the summary names both failing stages (proving no fail-fast short-circuit).
6. The summary line and exit code agree: `CHECK GREEN` ⇒ exit `0`; any `CHECK RED` ⇒ non-zero.

## 6. Self-check / acceptance criteria

- `node scripts/check.mjs` exits `0` and prints `CHECK GREEN` on the clean baseline.
- Introducing a deliberate error makes it exit non-zero with an **identifiable failing stage** named in `CHECK RED: …`.
- Each of the three stages (`typecheck`, `test`, `lint`) is independently shown to fail the gate when its own input is broken.
- All stages run on every invocation; multiple simultaneous failures are all reported.

## 7. Soundiness / open questions

None. This is deterministic infrastructure with no dynamic-target or guard-evaluation concerns; the gate reports stage exit codes verbatim and makes no inferences.
