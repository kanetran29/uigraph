# F4.4 — Local API server feeding the dashboard

- **Status:** planned
- **Milestone:** M4 · **Level:** L1
- **Depends on:** F4.2 (CLI `map --adapter` command)

## 1. Purpose (abstract)

The dashboard needs to view and edit the graph without bundling any extraction or framework logic into the browser. This feature provides a **small local HTTP API** that serves the displayed graph `merge(base, overlay)`, accepts overlay edits, and answers `plan_path` queries — all over core IR only. It is the framework-agnostic backend that keeps the UI a thin client: the API owns file I/O and core ops, the dashboard owns rendering. Adapter (React/Angular) knowledge never reaches this layer.

## 2. Contract & boundary

Lives in **`@uigraph/cli`** (started by `uigraph dash` in F4.5), depending only on **`@uigraph/core`** — framework-agnostic, no React/Angular imports, no LLM calls. It is a localhost-only server (loopback bind) over the three data files in a project dir.

Exposes a factory plus an HTTP surface:

```ts
export function createApiServer(opts: { projectDir: string }): { listen(port: number): Promise<{ port: number; close(): Promise<void> }> };
```

HTTP routes (JSON):
- `GET /api/graph` → `merge(load(base), load(overlay))` as a `UiGraph`.
- `POST /api/overlay` → apply one overlay edit (added/edited/removed ref), `save` to the sidecar, return the new merged graph.
- `POST /api/plan-path` `{ from, to }` → the core `plan_path` BFS result (edge sequence or no-path).

**Depends on:** `load`/`save` (F1.2), `merge` (F1.4), `validate(graph, overlay)` (F1.3), `plan_path` (F1.6), and the IR/`Overlay` shapes from `docs/30-ir-spec-v0.md`. It reads/writes `ui-graph.json` and `ui-graph.overlay.json` (architecture §6).

## 3. Abstract design

**Inputs:** HTTP requests against a `projectDir`. **Outputs:** core IR JSON responses.

Read path: `GET /api/graph` loads the base and overlay from disk, returns `merge(base, overlay)`. The base file on disk is never mutated.

Write path: `POST /api/overlay` loads the current overlay, applies the supplied edit (stamped `source: 'manual'` per the IR purity invariant), runs `validate(base, overlay)`, and `save`s **only** the sidecar. The base file is left byte-unchanged — this is the load-bearing guarantee. Invalid edits are rejected with a field-level error and no write occurs.

Plan path: `POST /api/plan-path` runs the core BFS over the merged graph and returns the edge sequence, or an explicit no-path result.

**Key decisions:**
- **Stateless over files.** Each request loads from disk rather than caching, so the API and CLI commands never disagree about on-disk truth — simplest correct model for a single local user (KISS).
- **Core does the work.** The server is glue: validation, merge, and BFS all come from `@uigraph/core`; the API adds only transport and file routing. No graph logic is reimplemented here.
- **Localhost only.** Loopback bind, no auth (single-user dev tool); CORS allows the local dashboard origin.

Out of scope: websockets/live reload, multi-client concurrency control, remote/auth deployment, serving the dashboard static assets (that wiring is F4.5).

## 4. Data shapes

This feature **owns no new IR types**. It consumes `UiGraph`, `GraphEdge`, `GraphNode`, and `Overlay` exactly as defined in `docs/30-ir-spec-v0.md` §2, and the `merge`/`plan_path` semantics from §5 and F1.6.

The only feature-local shapes are the HTTP request/response envelopes (e.g. the `plan-path` request `{ from: string; to: string }` and a `{ found: boolean; edges: GraphEdge[] }` result). These are transport DTOs, not IR, and stay confined to the CLI package.

## 5. Test strategy (write these first)

1. **Serves the merged graph.** `GET /api/graph` against a fixture project (base + a one-`manual`-edge overlay) returns a body equal to `merge(base, overlay)` and validates against the JSON schema.
2. **Overlay edit persists to the sidecar.** `POST /api/overlay` with a new edge writes it to `ui-graph.overlay.json` with `source: 'manual'`; re-reading the sidecar shows the edge.
3. **Base is untouched by an edit.** After the `POST /api/overlay` in test 2, `ui-graph.json` is byte-identical to its pre-call snapshot.
4. **Edit shows up in the merged view.** A subsequent `GET /api/graph` includes the just-added `manual` edge as part of the merge.
5. **Invalid overlay edit is rejected.** Posting an edit that fails `validate` (e.g. dangling ref, or `source` not `manual`) returns an error and leaves both files unchanged (no partial write).
6. **`plan_path` for a reachable target.** `POST /api/plan-path` with a known `from`/`to` returns the expected shortest edge sequence.
7. **`plan_path` no-path.** A disconnected target returns an explicit no-path result, not an error.
8. **Localhost bind.** The server binds loopback and `close()` releases the port.

## 6. Self-check / acceptance criteria

- [ ] `GET /api/graph` serves `merge(base, overlay)` (tests 1, 4 green).
- [ ] `POST /api/overlay` writes the edit to the sidecar as `source: 'manual'` and leaves the base file byte-unchanged (tests 2, 3, 5).
- [ ] `POST /api/plan-path` answers reachable and unreachable queries correctly (tests 6, 7).
- [ ] The server lives in `@uigraph/cli`, depends only on `@uigraph/core`, and has zero framework/LLM imports.
- [ ] `node scripts/check.mjs` prints `CHECK GREEN` (typecheck + tests + lint, whole workspace); no sibling regression.

## 7. Soundiness / open questions

None for v1. The API is a thin transport over already-resolved IR and core ops; it has no adapter, dynamic-target, or data-dependent-guard exposure (those live in the adapters, upstream of any graph this server reads). Concurrency is single-user by assumption — no last-writer-wins policy is specified because the only writers are this dashboard and the CLI, used one at a time. Live-reload/websocket push is deliberately deferred; the dashboard refetches.
