# F4.1 — uigraph CLI scaffold and command dispatch

- **Status:** planned
- **Milestone:** M4 · **Level:** L1
- **Depends on:** F1.6 (graph algorithms: reachability + plan_path), F2.7 (React adapter golden-validated), F3.5 (Angular adapter golden-validated)

## 1. Purpose (abstract)

This feature creates `@uigraph/cli` with the `uigraph` bin: the single user-facing entry point that ties the framework-agnostic core and the framework-specific adapters together. It owns only the *dispatch layer* — parsing `argv`, routing to the `map`, `diff`, `dash`, and `mcp` subcommands, validating each one's arguments, and printing help. It exists so a person has one command to reach every uigraph capability, while framework knowledge stays confined to which adapter `map` selects by name.

## 2. Contract & boundary

`@uigraph/cli` is the **only workspace package that may depend on both the core and the adapter packages** (per the package map in `10-architecture.md` §5). It is not framework-agnostic by itself, but its framework coupling is confined to one place: a `--adapter <name>` → adapter lookup. The dispatcher and all other subcommands touch core IR only.

Public surface (the bin and its dispatcher; subcommand *bodies* land in F4.2–F4.5):

```ts
// bin: uigraph
export function run(argv: string[]): Promise<number>; // resolves to the process exit code

interface Subcommand {
  name: string;                       // 'map' | 'diff' | 'dash' | 'mcp'
  summary: string;                    // one line, shown in top-level --help
  parse(args: string[]): ParsedArgs;  // validate flags/positionals; throw UsageError on bad input
  run(args: ParsedArgs): Promise<number>;
}
```

- **Depends on:** `@uigraph/core` (IR types, ops), `@uigraph/adapter-react`, `@uigraph/adapter-angular` (selected by `map`), and an argument-parsing primitive. F4.1 wires the table; the four handlers are stubbed here and filled by F4.2 (`map`), F4.3 (`diff`), F4.5 (`dash`, `mcp`).
- **Consumed by:** the end user via the `uigraph` bin.

## 3. Abstract design

**Inputs → outputs.** Input is `process.argv`; output is a process exit code plus text on stdout (results, help) / stderr (errors). The dispatcher reads the first token, looks it up in a static subcommand registry, and delegates parsing and execution to the matched `Subcommand`.

**Approach.** A small registry maps each name to its `Subcommand`. `run` resolves `--help`/`-h` and the no-arg case to the top-level help listing every subcommand; resolves a known name to its handler; and treats an unknown name as a usage error. Each subcommand validates its own flags and positionals before doing any work, so argument errors are caught at the dispatch boundary, never mid-extraction.

**Key decisions / trade-offs.**

- **Adapter selection is the *only* framework-aware point.** `map --adapter react|angular` resolves a name to an adapter via a name→adapter table; every other path is core-IR only. This honors the one-place-for-framework-knowledge rule.
- **Errors are exit codes, not thrown stacks.** Unknown command, unknown flag, or a missing required argument print a clear one-line message plus the relevant usage to stderr and exit non-zero. Success exits zero.
- **Help is generated from the registry**, not hand-maintained, so adding a subcommand cannot leave `--help` stale.
- **Dispatch is thin (KISS/YAGNI):** no plugin auto-discovery, no config files, no shell completion in v1 — a fixed four-entry registry.

This feature owns only dispatch-layer types; all graph data is shared IR (do not redefine — see `30-ir-spec-v0.md`).

## 5. Test strategy (write these first)

1. **top-level help:** `uigraph --help` (and bare `uigraph`) prints a help text listing all four subcommands — `map`, `diff`, `dash`, `mcp` — and exits zero.
2. **subcommand routing:** each known subcommand token dispatches to *its* handler (assert via a spy/stub handler), not another.
3. **per-subcommand flag parse:** `map --adapter react <dir>` parses the adapter flag and positional dir; `diff <a> <b>` parses two positionals; `dash`/`mcp` parse with no required args.
4. **unknown command:** `uigraph bogus` prints a clear "unknown command" message to stderr and exits non-zero.
5. **missing required argument:** `map` without `--adapter`, or `diff` with fewer than two positionals, prints a specific missing-argument message and exits non-zero.
6. **unknown adapter name:** `map --adapter vue <dir>` errors clearly (no adapter registered) and exits non-zero — without crashing.
7. **subcommand help:** `uigraph map --help` prints that subcommand's usage and exits zero.
8. **exit-code contract:** valid parse → 0; any usage error → non-zero, asserted on the returned code from `run`.

## 6. Self-check / acceptance criteria

- [ ] `uigraph --help` lists all subcommands (`map`, `diff`, `dash`, `mcp`).
- [ ] Each subcommand validates its arguments and dispatches to the correct handler.
- [ ] Unknown commands and missing required arguments exit non-zero with a clear, specific message on stderr.
- [ ] An unknown `--adapter` name errors cleanly rather than crashing.
- [ ] Framework imports appear only at the `map` adapter-selection point; the dispatcher and other subcommands import core IR only.
- [ ] `node scripts/check.mjs` prints `CHECK GREEN` (typecheck + tests + lint).

## 7. Soundiness / open questions

- **Handler bodies are out of scope here.** F4.1 proves dispatch, help, and argument validation; the actual extraction (`map`, F4.2), diffing (`diff`, F4.3), and server launches (`dash`/`mcp`, F4.5) are tested in their own features. Tests here stub the handlers.
- **Adapter registry is static in v1.** Only `react` and `angular` are registered; no dynamic/third-party adapter discovery (deferred per the adapter-contract §6 "adding a third adapter" path).
