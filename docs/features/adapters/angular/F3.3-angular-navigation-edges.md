# F3.3 — Angular navigate/navigateByUrl/routerLink edges

- **Status:** planned
- **Milestone:** M3 · **Level:** L1
- **Depends on:** F3.2

## 1. Purpose (abstract)

F3.2 gives the Angular adapter its node inventory — the declared route set that
bounds where any navigation can land. This feature adds the edges: it reads the
three Angular navigation idioms (`Router.navigate`, `navigateByUrl`, and
`routerLink`) and turns each call site into an IR edge to the route it targets.
A literal, resolvable target becomes a witnessed edge to the matching route node;
a non-literal target (variable, computed string, dynamic dispatch) is
over-approximated into `may`-edges across the declared route set, so a navigation
is never silently dropped and never invented beyond the known routes.

## 2. Contract & boundary

Lives in **`@ui-graph/adapter-angular`** (an adapter, not core). It imports
`@ui-graph/core` only for the IR types and the `Adapter` contract; all Angular
knowledge stays here per `40-adapter-contract.md §7`.

**Exposes** (internal to the adapter, consumed by F3.4 then the F3.5 pipeline) a
pure edge-extraction step over the route inventory from F3.2:

```ts
// nodes: the declared route nodes from F3.2 (bounds the codomain)
extractNavigationEdges(project: TsProject, nodes: GraphNode[]): GraphEdge[]
```

**Depends on:** F3.2 (route nodes + their path→node-id resolution, used to match a
literal target to its node and to enumerate the codomain for over-approximation)
and the IR types in `30-ir-spec-v0.md` (`GraphEdge`, `Witness`, `Modality`,
`Source`). It targets the **Angular** rows of `40-adapter-contract.md §4`.

## 3. Abstract design

**Input:** the TS project (TS source + component template strings) plus the F3.2
route nodes. **Output:** a list of `source: 'static'` `GraphEdge`s.

Per call site:
- **Literal target** (`navigate(['/users', ...])` / `navigateByUrl('/login')` /
  `routerLink="/login"` / `[routerLink]="['/users']"`): resolve the URL against
  the declared route set. On a match, emit a **`must`-edge** to that node with a
  static `Witness` (file + loc + `ruleId`), `confidence ≈ 1.0`. The `from` node is
  the route owning the component where the call site lives.
- **Non-literal target** (variable, template literal with interpolation, function
  result): **over-approximate** — emit one **`may`-edge** per declared route node,
  each flagged over-approximated (lower `confidence`), witnessed at the call site.
  Never a `must`, never a guessed string, never an interprocedural points-to chase
  beyond the literal (`§2`/IR invariant 5).

**Key decisions / trade-offs.** `routerLink` is parsed from component template
strings (string `routerLink="…"` vs bound `[routerLink]="…"`); a bound non-literal
follows the over-approximation path. A literal that matches **no** declared route
yields no edge but is recorded for the F2.6-style soundiness report (F3.5), not
fabricated. `event`/`effect` are set per idiom (e.g. `event: "navigate"` /
`"click:routerLink"`). Guard/`canActivate` attachment is **out of scope here** —
that is F3.4; this feature emits unguarded edges only.

## 4. Data shapes

This feature defines **no new IR types** — it populates the shared `GraphEdge` and
`Witness` from `30-ir-spec-v0.md`. It only fixes adapter-local conventions:

- **`ruleId`** per idiom, e.g. `ng.router-navigate`, `ng.navigate-by-url`,
  `ng.router-link`.
- An over-approximation marker on fanned-out edges (e.g. `effect:
  "over-approx:<idiom>"` plus reduced `confidence`) so F3.5's soundiness report can
  enumerate them. Modality/source/witness all reuse the IR exactly.

## 5. Test strategy (write these first)

1. **Literal `routerLink` → witnessed `must`-edge.** A `routerLink="/x"` in a
   template yields one `must`-edge to node `/x` with a static witness (file+loc)
   and `confidence ≈ 1.0`.
2. **Literal `Router.navigate([...])` → witnessed `must`-edge** to the matching
   route node, with the correct `from` (the component's owning route).
3. **Literal `navigateByUrl('/y')` → witnessed `must`-edge** to node `/y`.
4. **Non-literal `navigate(target)` → over-approximated `may`-edges** spanning the
   declared route set, each flagged over-approximated, **none promoted to `must`**.
5. **Non-literal `[routerLink]="expr"` / `navigateByUrl(expr)`** also
   over-approximate the same way (bound template + computed string).
6. **Bounded codomain.** Over-approximated edges target only F3.2's declared route
   nodes — no edge to a non-existent node.
7. **Witness presence.** Every emitted edge carries a `static` witness (IR
   invariant 3); no guard is attached (that is F3.4).
8. **Sample-app golden slice.** On `examples/sample-angular-app`, the extracted
   navigation edges match the known navigation set from the F3.1 manifest.

## 6. Self-check / acceptance criteria

- On `examples/sample-angular-app`, every **literal** `navigate` / `navigateByUrl`
  / `routerLink` yields a correct edge to the matching route node, `must` modality,
  `source: 'static'`, and a static witness.
- Every **non-literal** target yields **over-approximated `may`-edges over the
  known route set**, none promoted to `must`, none targeting an undeclared node.
- All emitted edges pass `validate()` (witnessed base edges, `must`-provenance,
  confidence range).
- The self-healing gate (`scripts/check.mjs`) is green with these tests added.

## 7. Soundiness / open questions

- **Over-approximation is intended imprecision:** a non-literal target fans to the
  whole route set rather than a guessed value. F3.5's soundiness report lists every
  such case; this feature only guarantees the fan-out exists and is bounded.
- **Literal-but-no-match** targets (typos, runtime-only paths) produce no edge and
  are deferred to the F3.5 soundiness report rather than fabricated.
- **Template parsing scope:** only `routerLink` in component template strings is
  read; cross-file/HTML-file template extraction depth is a fixture-driven detail
  settled with F3.1, not a new abstraction here.
- **Guards / `canActivate`** are explicitly F3.4; edges here are unguarded.
