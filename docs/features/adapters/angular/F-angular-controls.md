# Angular control + selector extraction (parity with React)

- **Slug:** F-angular-controls
- **Status:** designed

## Purpose

Bring the Angular adapter (packages/adapter-angular/src/extract.ts) to control-level parity with React. Today it emits only screen nodes + routerLink/Router.navigate edges and ignores opts.controls entirely (the param is destructured but never read — see extractGraph signature line 253, which never branches on opts.controls, unlike React's `if (opts.controls)` block at extract.ts:946). After this feature, with opts.controls set, the Angular adapter parses each route component's inline @Component template HTML and emits control nodes (kind:'control', parent set to the screen) carrying ControlMeta { element, controlType, selector, input?, name?, events?, effects? }, mints their ids via a shared controlNodeId with per-screen nth disambiguation, and wires control->nav edges when a control's (click)/(submit) handler calls a class method that does router.navigate / navigateByUrl. The existing route/edge golden (extract.test.ts, 8 nodes / 11 edges / 6 must / 5 may) must stay byte-for-byte green because controls are gated behind opts.controls (default false) exactly as in React.

## Contract & boundary

Public API unchanged: extractGraph(project: Project, projectDir: string, opts: ExtractOptions = {}): ExtractResult, and the Adapter object's extract(projectDir, opts, ctx). Behavior delta is purely additive and gated on opts.controls (default false). When opts.controls is true: append GraphNodes of kind 'control' (with parent = owning screen node id, componentPath set, control: ControlMeta) and GraphEdges from those control ids to route nodes for wired navigations. When false: output is byte-identical to today. ids.ts gains exported `controlNodeId(screen, sel)`; index.ts re-exports it.

## Data shapes

No new IR types. Reuse core ControlSelector { strategy: 'testid'|'role-name'|'label'|'structural'|'text'; value: string; nth?: number }, ControlInput { type?; required?; pattern? }, ControlMeta { element; controlType; name?; events?; effects?; selector?; input? }, GraphNode { id; route; componentPath; label; kind:'control'; parent; control }. New internal (non-exported) shapes in extract.ts: TagToken { tag:string; attrs:Map<string,string>; kind:'open'|'selfclose'|'close'; offset:number; text?:string } and ControlInfo { element; controlType; name?; selector:ControlSelector; input?; events:string[] } (mirrors React's ControlInfo at extract.ts:366). controlNodeId(screen:string, sel:ControlSelector):string added to ids.ts. New ruleIds (strings, no type): 'ng.control.navigate', 'ng.control.navigate-by-url'.

## Soundness

Golden invariant (no proven edge without a deterministic static witness) is preserved: every control->nav edge is witnessed by the exact (event) binding attr offset (loc via sf.getLineAndColumnAtPos(tpl.start + tokenOffset)) and a ruleId (ng.control.navigate / ng.control.navigate-by-url), and is emitted ONLY after resolving the binding's method name to a real class method whose body contains a real router.navigate/navigateByUrl call. No must-edge is emitted for a conditional/loop/early-returned/iterated navigation (ported getGuard + extraConditionGuard demotion from React extract.ts:96/126) — closing the phantom-must gap, matching React's red-team tests. canActivate-guarded targets stay may, consistent with the route-level code (guardsByNodeId). Targets that don't resolve to a declared route are recorded as soundiness ('unresolved-target') and dropped, never invented — same as the existing route path. The control gate (opts.controls) defaults false, so the route golden is provably unaffected (controls block is additive and skipped). One honest over-approximation: the regex/stack tokenizer does not model Angular structural directives (*ngIf/*ngFor) or template control-flow (@if/@for) — a control inside *ngFor is still emitted as a single static control (its repetition is runtime), which is the correct conservative may-style behavior and should be noted as a soundiness 'over-approximation' note rather than silently expanded.

## Dependencies

- No new runtime/dev dependencies — uses existing ts-morph (already a dep of adapter-angular) for class/method/decorator access, and a hand-rolled regex/tokenizer for the inline template HTML (KISS: no parse5, no @angular/compiler, no jsdom).
- Reuses @uigraph/core exports already present: fnv1a (index.ts:32), and types ControlSelector/ControlInput/ControlMeta/SelectorStrategy/GraphNode (ir.ts).
- Reuses existing in-adapter helpers in extract.ts: inlineTemplate (line 173), classifyTarget (158), routerCallTargets logic (231) to be generalized, matchLiteral/matchPrefix (matcher.ts), pushEdge + guardsByNodeId machinery (extractGraph), and routeToNodeId/edgeId (ids.ts).
- controlNodeId must be ADDED to adapter-angular/src/ids.ts (only React's ids.ts has it today) and exported from adapter-angular/src/index.ts alongside the existing routeToNodeId/edgeId exports.

## Risks

1) HTML-in-string parsing fragility: a hand-rolled tokenizer can mis-handle exotic markup (comments, CDATA, attribute values containing '>' inside quotes, self-closing void elements written as <input>). Mitigation: the attribute regex already tolerates quoted '>'; void elements (input) are handled as self-contained controls regardless of close tag; keep scope to the control tags + event-binding elements the spec lists. 2) Angular two-way/banana-in-box [(ngModel)] and bracket bindings [disabled] must not be misread as event bindings — only /^\(.+\)$/ keys count as events; verify in a unit. 3) Method resolution only covers methods on the SAME component class (no inherited/base-class or injected-service indirection) — acceptable v1 scope (React's interprocedural depth is broader, but YAGNI here); cross-method calls within the class could be added later. 4) The minimal sample-app edit MUST avoid touching routes/routerLinks or the 8/11/6/5 route golden breaks — guard by re-running the no-opts test block immediately after editing login.component.ts. 5) MODALS: React also emits modal nodes + open:modal edges (extract.ts:957-964,1016-1020); Angular has no modal convention in the sample and the spec does not ask for it — explicitly OUT OF SCOPE to keep KISS/YAGNI; note it as a future parity gap rather than inventing an Angular modal heuristic. 6) Effects parity (api:/state:) is also broader in React; the spec asks for control+selector+events+input+nav wiring, so non-nav effects beyond what naturally falls out are out of scope for this feature.
