# F3.4 — Angular canActivate guard capture to may-edges

- **Status:** planned
- **Milestone:** M3 · **Level:** L2
- **Depends on:** F3.3

## 1. Purpose (abstract)

Angular routes can be gated by `canActivate` guards declared in the route config,
so a transition into a guarded route is conditional, not certain. This feature
records the guard class name(s) as symbolic guard text on the affected route
transitions and downgrades those transitions from `must` to `may`, so the graph
honestly reflects that entry is gated. Guards are captured for *legibility* — an
agent reads which guard fences a route — not evaluated, so the extractor never
decides the guard's outcome.

## 2. Contract & boundary

**Lives in the adapter:** `@ui-graph/adapter-angular`, alongside the route
(F3.2) and navigation (F3.3) extraction. `@ui-graph/core` stays framework-agnostic
and gains nothing here — the `guard`/`modality` fields it already owns are simply
populated with Angular knowledge.

**Exposes** (internal to the adapter pipeline, surfaced via `extract`):
- A guard-capture pass that reads each route node's `canActivate` array from the
  `Routes` config and, for every navigation edge whose `to` is that route,
  sets `edge.guard` to the guard class name(s) (symbolic text) and `edge.modality`
  to `'may'`, lowering `confidence` and stamping a `ruleId: "ng.can-activate"`
  witness.

**Depends on:** F3.3 (navigation edges + the route-node inventory it consumes),
and transitively F3.2 routes and the F0.4 IR `GraphEdge` shape.

## 3. Abstract design

Input: the extracted route nodes (each knowing its `canActivate` class
references) plus the navigation edges from F3.3. Output: the same edge set with
guarded edges rewritten to `may` carrying guard text.

Key decisions:
- **Guard is a property of the target route, applied to incoming edges.** A
  `canActivate` guards a *route*; every edge whose `to` is that route is the
  guarded transition, so the pass keys on `edge.to` rather than re-walking
  navigation call sites.
- **Symbolic class name, not evaluation.** Copy the guard's class identifier(s)
  (e.g. `AuthGuard`, or `"AuthGuard, RoleGuard"` for multiple) verbatim per the
  legibility principle (IR spec §6). No resolution of the guard's logic.
- **Only downgrade what is guarded.** Edges into unguarded routes keep their
  F3.3 modality (a literal `must` stays `must`). The pass never promotes; an
  already-`may` over-approximated edge stays `may` and just gains guard text.
- **Cheap-availability scope.** Capture the guard *class names* present in the
  config array; resolving guard logic, factory/`functional` guard bodies, or
  `inject()`-based deps is out of scope (legibility, not decidability).

Trade-off: keying on `edge.to` means a guard text is attached to *all* inbound
edges of a guarded route, which is correct (any entry is gated) and avoids
re-parsing navigations.

## 4. Data shapes

This feature defines **no new IR types**. It populates fields the `GraphEdge`
already owns (`30-ir-spec-v0.md §2`): `guard` (symbolic class name string),
`modality: 'may'`, lowered `confidence`, and a `witness` with
`ruleId: "ng.can-activate"`. The IR spec §3 already shows the target shape:
`"guard": "AuthGuard"`. The only adapter-internal datum is the per-route list of
captured `canActivate` class names, threaded from F3.2's route nodes.

## 5. Test strategy (write these first)

1. **Guarded route yields a may-edge.** A navigation into a `canActivate`-guarded
   route in the sample app produces an edge with `modality: 'may'`.
2. **Guard text carries the class name.** That edge's `guard` field contains the
   guard class name (e.g. `AuthGuard`) as symbolic text — verbatim, not evaluated.
3. **Unguarded routes are not downgraded.** A literal navigation into an
   *unguarded* route keeps its F3.3 `must` modality and `guard: null`.
4. **Multiple guards.** A route with more than one `canActivate` entry records all
   class names in the guard text (deterministic ordering/joining).
5. **All inbound edges gated.** Every edge whose `to` is a guarded route carries
   the guard text, not just one.
6. **Witness/ruleId.** Guarded edges carry a static witness with
   `ruleId: "ng.can-activate"` and lowered `confidence` (< 1.0).

## 6. Self-check / acceptance criteria

- Each `canActivate`-guarded route in `examples/sample-angular-app` yields at
  least one inbound **may-edge whose `guard` field contains the guard class name**.
- Unguarded routes' edges remain `must`/their F3.3 modality with `guard: null` —
  no spurious downgrade.
- Output still passes core `validate()` (no `must` edge claims a guard; guarded
  edges are `may`/`unknown`, satisfying invariant §4.5) and the self-healing gate
  (`scripts/check.mjs`) is green.

## 7. Soundiness / open questions

- **Functional/factory guards.** `CanActivateFn` and inline functional guards may
  have no clean class name; v1 captures whatever identifier is cheaply available
  and otherwise flags the route as guarded-but-unnamed (a soundiness-report entry,
  finalized in F3.5).
- **canActivateChild / canMatch / canDeactivate.** Out of scope for v1; only
  `canActivate` is captured. Other guard kinds are a declared gap.
- **Guard data-dependence.** The guard's runtime decision is never modeled — the
  may-edge says "gated", not "feasible"; deciding outcomes is explicitly not the
  extractor's job.
