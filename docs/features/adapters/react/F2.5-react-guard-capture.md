# F2.5 — React guard capture as symbolic guard text

- **Status:** planned
- **Milestone:** M2 · **Level:** L2
- **Depends on:** F2.4

## 1. Purpose (abstract)

When a navigation is conditional, the React adapter already downgrades it to a
`may`-edge (F2.3 literal-in-conditional, F2.4 over-approximated) — but the edge
says nothing about *why* it is conditional. This feature captures the surrounding
condition (an enclosing `if`/`else`, a `?:` ternary, a `&&` short-circuit, or a
guard-component condition) as **symbolic guard text** and stamps it onto that
`may`-edge's `guard` field. The text is recorded for legibility, never evaluated:
an agent reads the gate (`"isAuthenticated"`, `"user.role === 'admin'"`) without
the extractor having to decide whether the branch is feasible (dossier §4.4,
legibility over decidability).

## 2. Contract & boundary

This lives in **`@uigraph/adapter-react`**, not the core — it is React/AST-specific
knowledge. The core only owns the opaque `guard: string | null` field
(`30-ir-spec-v0.md §6`); it never parses guard text.

**Exposes** (internal to the adapter pipeline, consumed by F2.6/F2.7):
- A guard-resolution step over the edges F2.3/F2.4 produce: given a navigation
  call site's AST node, walk its enclosing conditional context and return readable
  source text, e.g. `resolveGuard(callSiteNode): string | null`.
- The rule that attaches that text to the corresponding `may`-edge's `guard`,
  leaving unconditional `must`-edges with `guard: null`.

**Depends on:** F2.4 (and transitively F2.3) for the `may`-edges to annotate and
their static witnesses/AST anchors; the shared TS project via `AdapterContext`
(`40-adapter-contract.md §1`). It adds no new edges and changes no modality —
it only fills `guard`.

## 3. Abstract design

Input: the `may`-edges from F2.3/F2.4, each anchored to a navigation call-site AST
node. Output: the same edges with `guard` populated from the enclosing condition.

- **Walk the enclosing condition, copy it verbatim.** From the call site, ascend
  to the nearest controlling construct — `IfStatement` test, `ConditionalExpression`
  test, `&&`/`||` left operand, or a guard-component prop/`return` condition — and
  capture its source text via the AST (`.getText()`), not a re-serialization.
- **Symbolic, not evaluated.** The guard is opaque data; the adapter does no
  feasibility or truthiness reasoning (`40-adapter-contract.md §2`). This is the
  core trade-off: cheap and always-legible over precise and undecidable
  (the infeasible-path problem, dossier §4.4).
- **`else`/negation legibility.** A navigation in an `else` branch records the
  controlling test as-written; an optional `!`-normalization is *out of scope* —
  we keep the literal source so the text always traces back to a line.
- **Modality is unchanged.** F2.5 never promotes/demotes; an unconditional
  navigation stays `must` with `guard: null`. Nested conditions capture the
  nearest enclosing one (deeper-context join is deferred — see §7).

## 4. Data shapes

This feature defines **no new IR types**. It only *populates* the existing
`GraphEdge.guard: string | null` field defined in `30-ir-spec-v0.md §2`
(symbolic, never evaluated, §6). The matching witness/`ruleId` (e.g.
`rr.guard-if` / `rr.guard-ternary`) follows the F2.3/F2.4 witness already on the
edge. No overlay, no schema change.

## 5. Test strategy (write these first)

Run against `examples/sample-react-app` (F2.1) and its manifest guard rows.

1. **`if`-guarded navigation.** A navigation inside an `if (cond) { navigate(...) }`
   yields a `may`-edge whose `guard` equals the `cond` source text.
2. **Ternary-guarded navigation.** A `cond ? <Navigate to=.../> : ...` (or ternary
   target) yields a `may`-edge with `guard` = the ternary test text.
3. **`&&` short-circuit.** `cond && navigate(...)` captures `cond` as the guard.
4. **Guard-component condition.** A navigation gated by a guard wrapper/conditional
   render records that component's condition as symbolic text.
5. **Unconditional carries no guard.** Each `must`-edge from F2.3 has
   `guard === null` — guard capture never touches unconditional navigations.
6. **Over-approximated may-edges (F2.4) get the guard too.** A conditional,
   non-literal navigation's fanned-out `may`-edges each carry the same guard text.
7. **Verbatim text.** Captured guard text matches the manifest's recorded
   `symbolicText` for that condition (readable, source-faithful, not normalized).

## 6. Self-check / acceptance criteria

- Each **conditional navigation** in the sample app produces a `may`-edge whose
  `guard` field contains the **readable source condition** (tests 1–4, 6).
- Each **unconditional navigation** carries `guard: null` (test 5).
- Captured guard strings **match the manifest's** recorded condition text (test 7).
- No modality or edge count changes versus F2.4; only `guard` is filled.
- `scripts/check.mjs` (typecheck + lint + tests) is green; no framework import
  leaks into `@uigraph/core`.

## 7. Soundiness / open questions

- **Data-dependent guards are captured, not resolved** (`user.role === 'admin'`):
  recorded as text only — this is intended, not a gap (dossier §4.4).
- **Nesting/join policy:** v1 captures only the *nearest* enclosing condition. A
  conjunction of multiple enclosing guards (and how to render it) is deferred; the
  case is declared in F2.6's soundiness report rather than silently approximated.
- **Guard-component detection** is heuristic (recognizing a wrapper as a guard);
  unrecognized custom wrappers may leave `guard: null`, flagged in F2.6.
- **`else`/negation** is recorded as the literal test text, not a negated form;
  legible but the reader infers the branch.
