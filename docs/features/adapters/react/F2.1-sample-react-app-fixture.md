# F2.1 — Scaffold sample-react-app golden fixture

- **Status:** planned
- **Milestone:** M2 · **Level:** L0
- **Depends on:** F0.5

## 1. Purpose (abstract)

The React adapter (F2.2–F2.7) needs a controlled target whose correct output is
known *before* the extractor exists. This feature hand-authors that target: a
small React app with a deliberately chosen, fully enumerated set of routes,
guards, and navigations spanning both react-router v5 and v6 idioms. Because the
app is small and authored on purpose, its expected transition graph is known by
construction — it is the golden ground truth every later adapter feature is
scored against, not a real codebase we hope to handle.

## 2. Contract & boundary

This feature is **not core and not an adapter** — it is a *fixture*, an input the
adapter reads. It lives under `examples/sample-react-app/` as a buildable React
app plus a sibling human-authored manifest. It imports neither `@ui-graph/core`
nor any `@ui-graph/adapter-*`; it is plain React + react-router source.

**Exposes** (consumed by F2.2–F2.7):
- A compiling/building React app exercising the v5 and v6 router constructs
  catalogued in `40-adapter-contract.md §4`.
- A `MANIFEST.md` (and a machine-checkable list) enumerating the known routes,
  guards, and navigation call sites — the documented "known set".

**Depends on:** F0.5 (adapter contract) only to know *which* constructs the
adapter promises to handle, so the fixture covers exactly that surface. The
golden `UiGraph` JSON encoding of this manifest is produced later (F2.7); here we
own only the app and the prose/known-set manifest.

## 3. Abstract design

Input: nothing (hand-authored). Output: a buildable app + a manifest of its known
set.

Key decisions:
- **Two router dialects, one app.** Include a v6 subtree (`<Routes>`/`element`/
  `useNavigate`/`<Navigate>`) and a v5 subtree (`<Switch>`/`component`/
  `useHistory().push`/`<Redirect>`) so a single fixture validates both idioms.
- **Every adapter rule gets a witness in source.** Cover each row of the React
  table in `40-adapter-contract.md §4`: literal `<Link to>`, literal
  `useNavigate`/`useHistory().push` (→ expected `must`), a conditional/guarded
  navigation (→ expected `may` with symbolic guard text), and at least one
  non-literal/computed target (→ expected over-approximated `may` over the route
  set, F2.4). Including the hard cases on purpose is what makes the fixture able
  to *fail* a naive adapter.
- **Small and total.** Keep the route set tiny so the manifest can enumerate the
  full expected node/edge set exhaustively, by hand, without ambiguity.
- **Manifest is the spec, not a dump.** The manifest is authored from intent
  (what we *put* in the app), then the app is written to match it — so it is an
  independent oracle, not a transcript of the code.

Trade-off: the fixture is intentionally not representative of a real app's size;
real-world coverage is F7's job. Here, completeness of the *known set* beats
realism.

## 4. Data shapes

This feature defines **no IR types** — shared types live in `30-ir-spec-v0.md`
and are not redefined or imported here. It owns one local artifact: the manifest
schema for the known set, expressed as plain documented rows, e.g.

- **route**: `{ path, routerVersion: 'v5' | 'v6', component, expectedNodeLabel }`
- **navigation**: `{ fromRoute, idiom, targetExpr, literal: boolean,
  expectedModality: 'must' | 'may', guard?: string }`
- **guard**: `{ name, symbolicText, guardsRoute }`

These describe expectations in plain terms (which become `GraphNode`/`GraphEdge`
fields in the F2.7 golden), so the manifest is readable without the IR.

## 5. Test strategy (write these first)

1. **Build test.** `pnpm --filter sample-react-app build` (and `tsc --noEmit`)
   exits zero — the fixture is a real, compiling app.
2. **Manifest exists and parses.** The known-set manifest file is present and its
   enumerated rows parse into the route/guard/navigation lists.
3. **Routes present.** Each route declared in the manifest is found in the app
   source (v5 `<Route>` under `<Switch>` and v6 `<Route element>` under
   `<Routes>`), with no manifest route missing from source and no extra unlisted
   route in source.
4. **Navigation call sites present.** Each manifest navigation idiom
   (`<Link>`/`<NavLink>`, `useNavigate`, `useHistory().push`, `<Navigate>`/
   `<Redirect>`) has a corresponding call site in source.
5. **Idiom coverage.** Assert the fixture contains at least one of each: literal
   `must` navigation, conditional/guarded `may` navigation, and a non-literal
   computed-target navigation — so F2.3/F2.4/F2.5 each have a case.
6. **Guards present.** Each manifest guard maps to a guarded navigation / guard
   wrapper in source with the recorded symbolic condition text.

## 6. Self-check / acceptance criteria

- `examples/sample-react-app` **builds** (and typechecks) green via the workspace
  scripts; the self-healing gate (`scripts/check.mjs`) passes with the fixture in
  the tree.
- A **written manifest enumerates** the app's known routes, guards, and
  navigations, and tests 2–6 above confirm every manifest entry is actually
  present in source (and vice versa) — establishing it as usable golden ground
  truth for F2.2–F2.7.
- The fixture imports no `@ui-graph/*` package.

## 7. Soundiness / open questions

- The **golden `UiGraph` JSON** (the committed expected graph) is intentionally
  *out of scope here* — it is authored in F2.7 once the IR encoding and node/edge
  ids are settled; F2.1 ships only the app and the prose/known-set manifest.
- The included **non-literal/computed navigation** is the deliberate
  over-approximation case; F2.1 only guarantees the call site exists, not how the
  adapter fans it out (that is F2.4).
- Node `id` and `event` string conventions are not fixed by this feature; the
  manifest records *labels and intent*, leaving id assignment to the adapter so
  the fixture does not prematurely lock the IR encoding.
