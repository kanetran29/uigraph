# F2.4 — Over-approximation for non-literal React targets

- **Status:** planned
- **Milestone:** M2 · **Level:** L2
- **Depends on:** F2.3 (React literal navigation-edge extraction)

## 1. Purpose (abstract)

A navigation whose target is not a resolvable literal — a computed string, a
variable, dynamic dispatch like `actions[mode]()` — cannot be pinned to one
route node, yet it must not silently vanish. This feature handles those call
sites by **over-approximating**: it emits a fan of `may`-edges to every declared
route node, applying the **route-table-bounds-the-codomain** principle (dossier
§4.2) so the unknown target is sound-by-construction over the finite route set.
Non-literal navigations thus appear as honestly-imprecise `may`-edges flagged as
over-approximated, never as a precise `must` and never as nothing.

## 2. Contract & boundary

Lives in **`@ui-graph/adapter-react`** — React-router knowledge belongs only here;
`@ui-graph/core` stays framework-agnostic. This extends F2.3's navigation-edge
extractor: F2.3 resolves *literal* targets, this feature is the **fallback** for
the call sites F2.3 classifies as non-literal.

Exposes (adapter-internal surface, consumed by the F2.7 `extract` pipeline):

```ts
// Given a navigation call site whose target argument is not a static literal,
// emit one over-approximated may-edge to each declared route node.
function overApproximate(
  site: NavCallSite,        // the unresolved navigation (from-node + witness)
  routeNodes: GraphNode[],  // the bounded codomain from F2.2 route extraction
): GraphEdge[];
```

Depends on: the route-node inventory from **F2.2** (bounds the codomain), the
call-site/literal classification from **F2.3**, and the shared IR types
(`GraphEdge`, `GraphNode`, `Modality`, `Witness`) from `@ui-graph/core`. Emits
only IR — it adds no new on-disk shape.

## 3. Abstract design

Input: an unresolved `NavCallSite` (a from-node plus the source witness of the
navigation) and the declared `routeNodes`. Output: a `may`-edge from the site's
node to **every** route node, each `source: 'static'` (it is still a static
fact — *that* a navigation happens, just not *where*), each carrying the same
static `witness` (the call-site location) and a marker that it is
over-approximated.

Key decisions / trade-offs:

- **Modality is `may`, never `must`.** Per IR invariant §4.5, an over-approximated
  target can never be promoted to `must` — that is the whole soundiness contract.
- **Low confidence.** `confidence` is `1/|routeNodes|`-ish (a small constant), not
  `~1.0`, marking these as deliberately imprecise versus F2.3's literal edges.
- **Marked, not silent.** Each edge is tagged so F2.6's soundiness report can
  enumerate it; the imprecision is surfaced, not hidden (dossier §4.3:
  uncertain regions are the most valuable for testing, not an apology).
- **Codomain = declared routes only.** No edge to a node outside the route table;
  the route table is the bound that makes over-approximation sound.

Trade-off: a fan of `N` `may`-edges per unresolved site is noisy, but soundness
("never miss a real edge") wins over precision here; the marker + confidence let
consumers down-weight or collapse them.

## 4. Data shapes

This feature owns **no new IR type**. Over-approximated edges are ordinary
`GraphEdge`s (see `docs/30-ir-spec-v0.md §2`) distinguished by
`modality: 'may'` + low `confidence` + an adapter-set over-approximation marker
(an `effect`/`ruleId` tag such as `ruleId: 'rr.over-approx'` on the `witness`).
The marker is an adapter-layer convention over existing fields, not a schema
change. Route/edge/witness types are the shared IR — do not redefine them.

## 5. Test strategy (write these first)

1. A computed-target `navigate(path)` in the sample app (where `path` is a
   variable/expression) produces **one `may`-edge per declared route node** —
   the fan spans exactly the F2.2 route set.
2. **No spurious `must`.** None of the emitted edges has `modality: 'must'`;
   all are `may`.
3. Every over-approximated edge carries the **over-approximation marker** and a
   **static witness** pointing at the call site.
4. Confidence on over-approximated edges is **strictly below** the confidence
   F2.3 assigns a literal `must`-edge (down-weighted, not `~1.0`).
5. A *literal* navigation in the same file is **not** over-approximated (F2.3
   still resolves it precisely) — the fallback only fires for non-literals.
6. Dynamic-dispatch (`actions[mode]()`) and template-string targets are both
   classified non-literal and over-approximated (representative idioms).
7. The codomain is **closed**: no over-approximated edge points to a non-route
   node.

- [ ] A computed-target navigation in `examples/sample-react-app` yields

## 7. Soundiness / open questions

- **Targets outside the route table** (cross-window, external URLs, federated
  modules, lazy route configs from an API) are *not* covered by the declared
  codomain — these are unresolved, deferred to F2.6's soundiness report rather
  than fabricated here.
- **Fan-out noise** on large apps (`N` `may`-edges per unresolved site) is a known
  cost; collapsing/down-weighting them is a consumer (dashboard/MCP) concern, not
  this feature's.
- **No feasibility reasoning.** This feature never tries to narrow the target by
  evaluating the expression — legibility over decidability (dossier §4.4); guard
  capture for the conditional context is F2.5's job.
