# F2.6 — React adapter soundiness report

- **Status:** planned
- **Milestone:** M2 · **Level:** L2
- **Depends on:** F2.5

## 1. Purpose (abstract)

A static extractor cannot precisely resolve every navigation: computed targets,
dynamic dispatch, and idioms outside the adapter's rule table get
over-approximated or skipped. This feature makes the adapter emit a **soundiness
report** alongside the graph that openly declares exactly those cases — the
honest claim level the dossier calls *sound modulo a declared list* (dossier §1).
Consumers get a truthful coverage account (what resolved, what was fanned out,
what was dropped) instead of a graph that silently pretends to be complete.

## 2. Contract & boundary

This lives in **`@ui-graph/adapter-react`**, not the core — it summarizes
React-specific extraction outcomes. It is the realization of the adapter
contract's promise that `extract` emits a soundiness report
(`40-adapter-contract.md §2`).

**Exposes:** the React `extract` result now carries a report next to the
`UiGraph` — conceptually `extract → { graph, soundiness }`. The report's shape
(`§4`) is owned here. The CLI (`F4.2`) and the real-world run (`F7.1`/`F7.2`)
consume it.

**Depends on:** F2.5 (the full literal + over-approximation + guard pipeline) for
the per-edge signals it tallies. It reads the edges/witnesses F2.3–F2.5 produced
plus the declared route set from F2.2; it adds **no** new edges and changes
**no** IR types.

## 3. Abstract design

Input: the extracted `UiGraph` plus the adapter's per-site extraction trace
(which call sites resolved to literal `must`-edges, which were
over-approximated into `may`-edges over the route set, which idioms were
recognized-but-unresolved or skipped entirely). Output: a structured report
object summarizing that trace.

Key decisions:

- **Derive, don't re-analyze.** The report is computed from signals the
  F2.3–F2.5 pipeline already emits (each call site is tagged resolved /
  over-approximated / unresolved as it is processed). The report folds those
  tags into counts and a per-case list — it does not re-walk the AST.
- **Three honest buckets.** `resolved` (literal targets → witnessed `must`/`may`
  edges), `overApproximated` (non-literal targets fanned out over the route set,
  F2.4), and `unresolved` (recognized navigation whose target could not be
  bounded, or an idiom outside the rule table that was skipped). Every navigation
  call site lands in exactly one bucket.
- **Counts must reconcile.** `resolved + overApproximated + unresolved` equals
  the total navigation sites seen, so the denominator is explicit and the
  coverage ratio is auditable.
- **Cite source, not guesses.** Each over-approximated / unresolved entry records
  its source location (file + loc) and the reason, so a human can find and judge
  it.

Trade-off: the report counts *call sites and declared cases*, the honest
coverage unit — not hypothetical runtime paths, which static extraction cannot
enumerate.

## 4. Data shapes

No IR types change (shared types stay in `30-ir-spec-v0.md`). This feature owns
one adapter-local type:

```ts
type SoundinessCategory = 'over-approximated' | 'unresolved' | 'skipped-idiom'

interface SoundinessCase {
  category: SoundinessCategory
  file: string
  loc: { line: number; col: number }
  idiom: string        // e.g. 'useNavigate' | 'history.push' | '<Link to>'
  reason: string       // why imprecise, e.g. 'non-literal target (computed string)'
  edgeIds?: string[]   // the may-edges this case fanned out into, when applicable
}

interface SoundinessReport {
  adapter: string                  // '@ui-graph/adapter-react'
  rulesetVersion: string
  counts: {
    navigationSites: number        // total sites seen (the denominator)
    resolved: number               // literal targets → must/may edges
    overApproximated: number
    unresolved: number             // includes skipped idioms
  }
  cases: SoundinessCase[]          // one entry per imprecise/skipped case
}
```

## 5. Test strategy (write these first)

1. **Report is emitted.** Running the React `extract` on `sample-react-app`
   returns a `SoundinessReport` alongside the `UiGraph`.
2. **Over-approximated cases enumerated.** Each known non-literal/computed
   navigation in the fixture (the F2.4 case) appears as an
   `over-approximated` case with its correct file + loc and `edgeIds` pointing at
   the may-edges it produced.
3. **Unresolved / skipped cases enumerated.** Any fixture idiom outside the rule
   table (or a recognized navigation with an unbounded target) appears as
   `unresolved` / `skipped-idiom` with a readable `reason` — and is absent from
   `resolved`.
4. **Resolved count matches literal edges.** `counts.resolved` equals the number
   of literal-target navigation sites (the F2.3 `must`/literal `may` edges).
5. **Counts reconcile.** `resolved + overApproximated + unresolved ===
   navigationSites`, exactly, with no double-counting.
6. **No spurious cases.** A purely literal navigation does **not** appear in
   `cases`; the report lists only genuinely imprecise/skipped sites.

## 6. Self-check / acceptance criteria

- Extracting `examples/sample-react-app` produces a `SoundinessReport` whose
  `cases` list contains **exactly** the fixture's known unresolved and
  over-approximated navigations (tests 2–3, 6), each with an accurate source
  location.
- The `counts` are accurate and reconcile: `resolved` matches the literal-edge
  count and the three buckets sum to `navigationSites` (tests 4–5).
- The report changes no IR types and adds no edges; the self-healing gate
  (`scripts/check.mjs`) is green with this feature in the tree.

## 7. Soundiness / open questions

- **The report is the declared list itself** — it is the artifact that makes the
  adapter "sound modulo a declared list", so its completeness *is* the honesty
  claim. A missing case is a soundiness bug, not a tolerated gap.
- **Granularity of `unresolved` vs `skipped-idiom`** is a labeling choice; both
  count toward `counts.unresolved` so the reconciliation holds regardless.
- **Data-dependent guards** are out of scope here — guard *text* is captured in
  F2.5; this feature does not reason about guard feasibility, only about target
  resolvability.
- **Lazy/dynamic-import route boundaries** (code-split routes not statically
  reachable) are a known real-world unresolved class; the fixture need not
  exercise it, but the `unresolved` bucket is where F7 will record it.
