# F2.2 — React route-node extraction (v5 + v6)

- **Status:** planned
- **Milestone:** M2 · **Level:** L1
- **Depends on:** F2.1, F1.6

## 1. Purpose (abstract)

Give `@ui-graph/adapter-react` its node side: walk a React project's source and discover every declared route across react-router v5 (`<Switch>` + `<Route component|render>`) and v6 (`<Routes>` + `<Route element>`), emitting one IR `GraphNode` per route. This is the L0/L1 node-inventory floor — it establishes *which screens exist* before any edge is drawn. Crucially, it materializes the **declared route set that bounds the codomain** (dossier §77): later edge features (F2.3–F2.5) over-approximate only over these nodes, so getting the inventory exactly right is what makes over-approximation honest rather than unbounded.

## 2. Contract & boundary

Lives **only in the adapter** (`@ui-graph/adapter-react`), never in `@ui-graph/core`. It imports the IR types (`GraphNode`, `NodeKind`, `UiGraph`) and the `Adapter`/`AdapterContext` contract from core; it imports ts-morph / the TS compiler API for parsing. No core file changes.

**Exposes (internal to the adapter):** a route-discovery pass, conceptually `extractRouteNodes(ctx): GraphNode[]`, that the full `extract` pipeline (F2.7) consumes. It produces `kind: 'route'` nodes with a populated `route` pattern, `componentPath` (the backing component when resolvable), a derived `label`, and a stable `id`.

**Depends on:** F2.1 (the sample-react-app golden fixture + known-route manifest to test against) and F1.6 (the core algorithms/IR layer this populates feeds). Uses `AdapterContext.tsProject()` / `readFile` for sandboxed, cached source access rather than opening files itself.

## 3. Abstract design

**Input:** a `projectDir` (via `AdapterContext`). **Output:** the set of route `GraphNode`s.

Approach: locate router container JSX (`<Switch>`, `<Routes>`) and the `<Route>` elements within, then read each route's `path` prop and its target component reference (`component`/`render` in v5, `element` in v6). The version idioms are unified into one IR node — the IR is adapter- and version-independent (§7 of the IR spec), so a v5 `<Route component>` and a v6 `<Route element>` at the same `path` produce the same node shape.

Key decisions / trade-offs:
- **Node identity is the route pattern**, not source position — so the same logical route is one stable node even if declared once. Ids are derived deterministically from the path (e.g. `/users/:id` → `n_users_id`).
- **Literal `path` props only in v1.** Static string paths resolve precisely; computed/spread paths are recorded as a soundiness gap, not guessed.
- **Node-only scope.** This feature emits *no edges* and makes no must/may decision — modality and witnesses are an edge concern (F2.3+). Keeping the inventory pass pure of edge logic keeps the codomain definition single-sourced.

## 4. Data shapes

Owns **no new IR types**. It produces `GraphNode` (`{ id, route, componentPath, label, kind }`) with `kind: 'route'`, defined in `30-ir-spec-v0.md` — not redefined here. No overlay or edge types are touched.

## 5. Test strategy (write these first)

1. **v5 discovery:** the sample app's `<Switch>`/`<Route component|render>` block yields exactly its known v5 route nodes, each with the correct `route` pattern.
2. **v6 discovery:** the sample app's `<Routes>`/`<Route element>` block yields exactly its known v6 route nodes with correct `route` patterns.
3. **Path-identifier correctness:** static paths (incl. params like `/users/:id` and an index/`*` catch-all if present in the fixture) map to the expected pattern strings and deterministic node ids.
4. **componentPath linkage:** when a route's component is a resolvable local import, the node's `componentPath` points at the backing source file.
5. **Exact-set assertion:** the union of v5+v6 nodes equals the route set in F2.1's manifest — no missing, no spurious, no duplicate-id nodes.
6. **Determinism:** running extraction twice on the fixture yields identical node sets (stable ids, canonical ordering).

## 6. Self-check / acceptance criteria

- Route extraction on `examples/sample-react-app` yields **exactly** the known set of route nodes for **both** v5 and v6 declarations (no extras, no omissions).
- Every emitted node has `kind: 'route'`, a correct `route` pattern matching the manifest, and a unique id.
- Tests, `tsc --noEmit`, and lint are green via the self-healing gate (`scripts/check.mjs`).

## 7. Soundiness / open questions

- **Non-literal `path` props** (computed strings, spread route config arrays, paths from variables) are out of v1 scope; record them as a declared soundiness gap (F2.6) rather than inventing a node.
- **Lazily/dynamically registered routes** (routes built at runtime, code-split `lazy`) may be under-counted — flagged, not silently dropped.
- **Nested routes:** v6 nested `<Route>` path composition (parent + child segment) — confirm against the fixture whether the manifest expects composed full paths; if nesting is out of the fixture's known set, defer composed-path handling.
