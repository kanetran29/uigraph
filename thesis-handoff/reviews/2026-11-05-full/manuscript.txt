Abstract

A user-interface (UI) transition graph describes the screens of an application and the
transitions a user can cause between them. For single-page web applications they
are usually built by running the application, though routing frameworks now declare
routes in the source. How well static extraction works on real applications, and why
it fails, has not been measured construct by construct.
   This thesis builds a static extractor for Angular and makes that measurement
with it on six open-source applications. The extractor reads nested and parameterised
route trees, which the stated restrictions of an earlier Angular extraction exclude in
every one of them. Five methods check the graphs. Each construct the extractor
does not recover is assigned to a loss category; under the order of the loss rules,
the largest is navigation that belongs to no single screen, such as a link in a shared
header. For this loss the thesis proposes scope attribution, a dataflow analysis that
computes the set of screens from which each navigation site can fire.
    Three results stand out. First, almost no navigation can be extracted as a
deterministic transition, mostly because the applications’ own guards and branches
decide it. The corpus yields 159 such edges from 25 constructs. Most of them come
from one toolbar whose screen set is untested, and most rest on an assumption
about route order that the extractor does not read. Second, almost every cause of
loss traced in the source is a construct a static reader can read, so the loss was the
tool’s; the final version reads most of them, and two lie beyond any static reader
of a route table. Third, scope attribution recovers 66.7 % of the constructs the loss
rules assign to it, most of them on one application and almost all as possible rather
than certain transitions. Unlike the mechanisms of earlier work, it places navigation
inside services: 20 of 48 such constructs. Against screen sets read from the sources
of two applications, it finds every pair and none outside them on one; on the other,
recall off the shell rises from 43.2 % to 90.9 % and precision falls to 82.0 %. Both
references apply the analysis’s own relations, and the first was partly completed from
the graph’s output and guided two repairs. Mutation testing on three applications
shows that the graph responds to injected changes in constructs it already represents;
its harness was corrected after its misses were read, so the test is not independent.
   A declared route table is a usable but insufficient basis for static navigation
extraction. The figures are in-sample; beside Rima et al.’s tool, on five corpus
applications it finds 94.1 % of the real transitions either finds, against 10.2 %, at
similar precision; on the largest its precision is 6.5 % against 80.0 %.
Keywords: static analysis; UI transition graph; single-page application; Angular;
dataflow analysis; program analysis; software testing

Chapter 1

Introduction

A user interface (UI) transition graph is a model of an application. The nodes
are the screens a user can see, and the edges are the transitions a user action can
cause between them. For each edge, the graph records the event that triggers it,
the condition under which the transition is available, and the screen it leads to. A
graph of this kind makes it possible to answer questions that are difficult to answer
from the code alone. One example is which screens are reachable from a given screen.
Another is which parts of the user interface are affected when a particular component
changes.
    Transition graphs have been used in automated testing for a long time. In
the Android domain they are used for test generation and for guiding exploration
[79, 39, 14], and in web testing they form the basis of crawling-based test derivation
[50, 51]. They are also useful for change impact analysis [4, 12], because each
transition can be traced back to the code that implements it, and from there to the
tests that cover it.
    This chapter explains why a static transition graph for single-page applications
is worth measuring and what is not yet known about it. It then states the research
questions and the limits of scope, and ends with the structure of the thesis.


1.1     Motivation
There are two general ways to obtain a transition graph. A dynamic approach
executes the application and records the states and transitions it observes. A static
approach reads the source code and derives the graph without running anything.
Their limitations differ. A dynamically built graph contains only the states the
crawler managed to reach. Which states those are depends on the available test data,
authentication, and the exploration budget. The graph also has to be rebuilt for
every new version. A statically built graph covers everything the source declares. It
can be recomputed on each commit without a running system. It is limited, however,
to what can be decided from the source, and it must over-approximate wherever a
target cannot be resolved.
   The two limitations complement each other. Applications of the kind studied
here are mostly used signed in. Much of their navigation therefore runs behind an


                                          8
authentication guard whose outcome only a running system decides. A crawler, for
its part, reaches only the states its data and credentials open. A static graph can
name the screens and candidate transitions a crawler should look for, and the guards
each waits on. A run can confirm which of them occur. This thesis measures the
static side; the combination is discussed in Section 6.5 and is not measured.
    For Android, static extraction is a well-established technique. The window
transition graph work derives windows and the transitions between them from
bytecode. It also resolves the control flow of callbacks to the widget that registered
each handler [79, 78, 77]. For the web, navigation models have been extracted from
server-rendered frameworks, in which pages and links are declared in templates and
configuration files, with the help of a crawler or of runs against the server [62, 9]; a
patent describes a fully static method [69]. Modern single-page applications, however,
have almost always been modelled by executing them. Crawljax builds its state flow
graph by firing events against the Document Object Model (DOM) of a running
application [50]. Later tools in the same line improve the exploration strategy without
changing where the model comes from [51, 74]. A survey of web testing covering 2014
to 2025 collects the model-based tools of the past decade [36]. Of the tools it lists,
every one whose model construction was examined for this thesis builds that model
by executing the application. Static analyses of a modern client-side framework are
few. One builds a component dependency graph for React and does not address
routing [38]. Three extract navigation, each for a different consumer:

  • one from Angular in order to model-check it, under stated restrictions, among
    them that the application declare no nested routes and no route parameters,
    and without treating data-binding changes as page transitions [56];
  • one from Angular sources in order to enumerate the workflows a generated
    end-to-end suite should cover [64];
  • one from the compiled JavaScript bundle of a single-page application in order
    to check an access-control policy against the screens it can reach [81].

Section 2.4 compares them with the work reported here.
   When the dynamic approach was developed, a single-page application had no
declarative route table. Its navigation therefore had no explicit representation in
the source and was hard to recover from it. The DOM was the observable the
tools used (Section 2.4). Client-side routing frameworks changed this. Angular,
React Router and Vue Router all declare routes as data in the source code. They
connect navigation to those routes through template attributes and service calls.
They also attach guards to routes as named functions [27]. The artefact needed for
static analysis now exists. How well static extraction works on real applications
built with these frameworks, and where it fails, has been measured only against
hand-built references on the applications each work evaluated. It has not been
measured construct by construct.
   A statically extracted graph also has consumers outside model-based testing.
Tools that drive a graphical user interface (GUI) with a large language model either
explore an application without a model of its navigation structure or build one by

                                           9
exploring it. GPTDroid treats mobile GUI testing as a question-and-answer loop,
passing the current screen to the model and replaying the action it returns. It reports
higher activity coverage and more bugs than the best baseline on 93 applications
[46]. AutoDroid gives the model application-specific knowledge in addition to its
commonsense knowledge, held as a UI transition graph that it builds by automated
dynamic exploration offline [73]. LLMDroid uses the model to guide exploration
towards coverage the test run has not reached [70]. The approach has been applied
to web interfaces with a vision-language model and curiosity-driven exploration [72],
and a survey of large language models in software testing covers the wider area [71].
Coding agents working on a repository may also benefit from structure of this kind.
The SWE-bench issues typically require coordinated edits across functions, classes
and files [31]. Agent performance also depends on the interface through which the
repository is navigated [76]. Whether a navigation graph helps such tools is not
tested here. These uses motivate the extraction but do not depend on the results of
this thesis.
    This thesis builds a static extractor for Angular and carries out that measurement
with it. It also proposes an analysis for the largest loss it finds under the order of its
loss rules. The analysis, scope attribution, is stated as a dataflow analysis over a
lattice of screen sets. Nothing in its formulation depends on this extractor.
    A method of this kind cannot be assessed without being instantiated, because
the questions asked here are empirical. They ask how much of the navigation in real
applications it recovers, where it fails, and whether the resulting graph responds to
a change in the source. The extractor is an open-source static analyser for Angular
built in this thesis. It is part of the contribution, not an existing tool. It reads nested,
parameterised and lazily loaded route trees; the stated restrictions of an earlier
Angular extraction exclude the first two (Section 5.3.6). It also implements scope
attribution. Its development versions and the corrections between them are listed
in Section 4.3.2. Because the same person built the tool and measured it, on the
same corpus, the figures describe what this extractor recovers on these applications.
Section 6.2 discusses what that means for them. Chapter 6 separates the limits of
the method from those of this implementation.


1.2      Research questions and scope
The thesis addresses five research questions (RQs). This section states what each
asks and how it is answered. The exact measures are defined in Section 4.2. The
answers are given in Chapter 5.

RQ1. How much of the navigation in Angular applications can static analysis recover
as deterministic transitions?
This is measured at two levels, because a transition cannot be recovered without the
screens it runs between. The first level is node coverage: the share of the screens
an application declares that the graph holds a node for. The second is the share
of navigation constructs in the source that yield at least one deterministic (must)
transition.

                                            10
RQ2. Where does static extraction fail, and why?
The observed failures are grouped into defect classes. A class is accepted only if
at least two lines of evidence confirm it. At least one of them must come from an
evaluation method of Section 4.3. Each construct that is not recovered is assigned to
one loss category, so the categories can be compared by size.
RQ3. How does scope attribution affect the recovered share and precision of static
navigation analysis?
Scope attribution is the analysis this thesis proposes. For a navigation site that
belongs to no single screen, it computes the set of screens from which the site can fire.
The same extractor is run with the analysis disabled and enabled, so that nothing
else differs between the two runs.
RQ4. Does the extracted graph respond to source changes in the constructs it
represents, as change impact analysis requires?
This is measured with mutation testing: known changes are inserted into the source,
and the graph is checked for the expected difference.
RQ5. Are the losses a property of the applications or of the tool?
A defect class names where extraction failed, but not whether the navigation was
unreadable or merely unread. Each class is therefore traced to its cause in the source,
and for each cause the thesis records whether the final version reads it. If it does, the
information was in the source and the loss was the tool’s. The causes that are still
not read, and those beyond a static reader, are named. Every site that still yields no
transition must carry a recorded label.
    The questions are answered on a corpus of six open-source Angular applications
pinned to fixed commits (Chapter 4). Five evaluation methods are used, and RQ3
adds four further measurements; the methods are chosen so that their blind spots
differ. The figures in Chapter 5 are those of the final version of the extractor. Its
development versions and the corrections between them are listed in Section 4.3.2.
   The thesis has the following limits of scope.
   • It does not claim completeness. Where a navigation target is computed at
     run time, the transitions cannot in general be determined statically. The
     thesis instead states a soundness property over a declared scope and lists what
     it approximates. This follows the soundiness position (Section 2.6.2). The
     property is tested, not proved.
   • It does not measure the effect of the graph on coding agents or any other
     consumer.
   • The screen sets that scope attribution computes are compared in both directions
     on two applications only, against references that apply the analysis’s own
     relations.
   • The extractor was developed on this corpus, so every figure on it is in-sample
     and is not an estimate for other applications. One comparison, on seven
     applications of earlier work, is out-of-sample (Section 5.3.7).

2.1      User-interface transition graphs
A UI transition graph is a directed graph in which the nodes represent user-visible
states of an application and the edges represent transitions that a user action can
cause between those states. Figure 2.1 shows a small example in the model used in
this thesis.
    Several research communities have studied this kind of graph under different names.
In Android static analysis it is a window transition graph [79], activity transition
graph [14] or screen transition graph [39]. For Ajax (asynchronous JavaScript and
XML) crawlers it is a state flow graph over DOM states [50]. In web engineering
it is a navigation model or navigation state machine [62, 18]. This thesis uses the
term UI transition graph and treats the other terms as equivalent for its purposes,
although they differ in what counts as a state and in how the graph is constructed.
    More important than the naming is how the graph is obtained: statically, from
source code or binaries without executing the application, or dynamically, by running
and observing it. It also matters whether the graph represents guards. That is,
it matters whether each edge records the condition under which the transition is
available, or only that the transition exists. Table 2.1 classifies the work reviewed in
the following sections according to both distinctions.

2.2       Static extraction for Android
The largest body of static work on transition graphs concerns Android. Yang et al.
introduced the window transition graph. Its nodes are windows (activities, dialogs
and menus), and its edges are transitions caused by callbacks that run on the UI
thread. The analysis models the stack of active windows, so that the effect of the
back button is captured [79]. A journal version extends the work [77]. A related
analysis by the same group constructs a callback control-flow graph whose nodes are
pairs of a handler and the widget it belongs to [78]. StoryDroid builds an activity
transition graph from startActivity calls [14]. GoalExplorer combines a statically
derived screen transition graph with dynamic exploration [39]. UI-CTX finds the
code context of a widget’s behaviour with a backward data-flow analysis from the
handler to the call that retrieves the widget [44].
   These approaches have in common the way a navigation is attributed to a screen.
In Android, an event handler is registered on a widget object, and at run time that
object belongs to exactly one window. Attribution can therefore be treated as an
object resolution problem: the widget identifier is resolved, usually by constant
propagation of the getId() call, and the window is then known [78].
    The limits of this approach become visible in ProMal. Its authors report that
a purely static window transition graph contains infeasible transitions. The cause
is that imprecision in the reference analysis makes several widgets aliases of one
another, and the over-approximated data flow then attaches a handler to the wrong
window. They address this by combining the static analysis with runtime traces and
a learned model [45]. Where the owning object cannot be resolved precisely, ProMal
therefore turns to dynamic evidence rather than refining the static attribution.

2.3      Navigation models for web applications
Navigation models for the web were first extracted from server-rendered sites, well
before single-page applications became common. Ricca and Tonella modelled a
web application as a set of pages, frames and forms connected by links and form
submissions. Their model includes conditional edges that carry a boolean condition
on input values, and was derived semi-automatically with a crawler and annotations
by an analyst [62]. WebUml recovers a state diagram from Hypertext Markup
Language (HTML), script and server-side pages by static analysis combined with
runs against the server, deriving guards by control-flow analysis of the server code
[9]. A patent assigned to Fujitsu describes a fully static method for extracting a
navigation model from Struts and JSP sources [69]. For verification, SiteHopper
builds abstracted navigation state machines on the fly for model checking [18].
     This work shows that navigation models, including guards, have been extracted
from web applications with the help of a crawler or of runs against the server, and
that a fully static method has been described in a patent. The models reviewed in
this section all concern server-rendered frameworks, where a page corresponds to a
file and a link to an anchor element. None of them deals with a client-side router, a
component tree, or dependency injection. Section 2.4 turns to the work that does.


2.4      Dynamic state models for single-page applica-
         tions
When web applications moved to Ajax and later to client-side frameworks, work
on model construction moved to run time. Crawljax executes user events against a
running application, compares the DOM before and after each event, and builds a
state flow graph whose nodes are equivalence classes of DOM states [50]. Later work
in this line changed the exploration strategy but not the source of the model [51, 74].
The survey by Kertusha et al. reviews web testing research from 2014 to 2025 [36].
Of the model-based tools it lists, every one whose model construction was examined
for this thesis builds that model by executing the application.
   The reason is largely historical. In an Ajax application there was no declarative
route table, and one uniform resource locator (URL) could represent many states,
because navigation was implemented by handlers that modified the DOM. Static
analysis of JavaScript existed [29], but recovering navigation from it was hard, and
nothing in the source represented the routes explicitly. The dynamic approach
observed directly what the source represented only implicitly.
    Client-side routing frameworks changed this situation. The route table is now
a declared data structure in the source. A navigation is an attribute or a method
call that names a route. A guard is a named function attached to a route. Four
static analyses of such a framework were found during the literature search for this
thesis, three of them reading the framework’s own sources and one a compiled bundle.
Kurant’s component dependency graph for React stops at the component rendering


                                          16
graph without addressing routing [38].
    The other three do address routing. Oshima and Kishi extract page transi-
tions from an Angular application in order to model-check them with SPIN [56].
Their extraction reads the transition information from the route declarations in
RouterModule, reads the navigable paths from every component, and resolves the
parent–child relationships among the root component, the routed component and the
custom child components. That attribution step is scope attribution. A navigable
path is attributed to the routed component that contains it, and the root component’s
own paths are attributed to every page. Section 5.3.3 measures that combination, as
the rooted level of the analysis presented here (the levels are defined in Section 4.2).
    What distinguishes the present work is the input the method accepts and what it
claims about its output. The authors list restrictions on the applications they handle,
among them that the routing declarations must not use the children attribute
or route parameters. They also state that changes arising from data binding are
not treated as page transitions. Those exclusions remove nested route trees and
parameterised addresses. How the method treats a navigation whose destination is
an expression rather than a literal is not stated in the paper, and it is not assumed
here. A screen is identified by the name of its routed component rather than by an
address, so path composition does not arise. Guards, lazy loading and named outlets
are not part of the model. A navigation site that reaches a screen through a method
call or through a dispatch lies outside the attribution mechanism. The model carries
no modality, so a navigation that is always available and one that is available only
if a guard admits it are represented identically. The evaluation applies the tool to
four constructed applications and to two published ones of 1824 and 6893 lines, with
six and twenty-three pages. It reports whether the intended model was produced
and whether transition faults, injected by hand into constructed variants of the first
sample application, were detected. What the extraction loses on an application it
cannot fully read is not measured. This is the question this thesis takes as its subject.
    Two recent works read a client-side router configuration statically for other ends.
Rima et al. parse Angular sources and templates to build a graph of navigation struc-
ture, interaction sites and the conditions (guards among them) that decide whether an
interaction is executable. They enumerate workflows over that graph and compile each
workflow into a browser test. The graph is a coverage denominator for generated end-
to-end tests [64]. This account is taken from the publisher’s abstract, the operational
specification in the project’s replication package (softscanner-sw/softscanner_fa,
docs/paper/approach.md), and the anonymised manuscript in the same repository
(docs/paper/main.pdf). The published chapter was not available to this review
and may differ from both documents. Both documents describe attribution beyond
containment: the components active at a route are those activated by the route
and its ancestor routes, closed under composition, plus the bootstrap components.
This covers what the rooted and outlet levels of Section 5.3.3 place. A handler
is followed into helper methods of the same class to depth one and into the first
callback of a subscribe. The specification excludes router-outlet modelling and
provider resolution beyond module and root providers. It does not follow a call
into a service, so a navigation inside a service member is not placed on the screens


                                           17
of its callers. Zhang et al. parse the compiled JavaScript bundle rather than the
sources, taking declared routes as vertices and navigation calls as edges, and check
an access-control policy against the screens reachable from an authorised one. Two
of their four subjects are multi-page applications, which are crawled instead. The
graph is declared an over-approximation and is not narrowed. The paper does not
describe how the source screen of a navigation call is determined, and guards appear
only as runtime conditions the graph does not model [81]. Rima et al. compare their
output with a ground truth generated from their pipeline’s output and annotated by
hand for the applications they study. Neither work classifies the losses by construct
or measures them across a corpus. The problem addressed in this thesis is therefore
neither new nor settled. Section 2.10 states what none of these works does.
   The work reported here is located between these analyses and the dynamic tools
described above.


2.5      Static analysis of JavaScript and TypeScript
         source
The analysis in Chapter 3 reads Angular source with the TypeScript compiler
application programming interface (API), so it works on a source-level abstract
syntax tree rather than on a compiled artefact. This section reviews that tooling
style, the abstract interpretation work behind lattice-based analysis of JavaScript,
what the type annotations of a TypeScript program contribute, and the evidence
that frameworks rather than the language limit such analyses in practice.


2.5.1     Analyses over a source-level syntax tree
Analysing the syntax tree of the source is a long-established style, used for example
by Baxter et al. to detect code clones in a C system of about 400 000 lines [8]. It
keeps the analysis close to what the developer wrote, which matters when the result
has to be reported back at a source location. SPOON makes this style into a reusable
library for Java [58]. The TypeScript compiler API occupies the same position for
TypeScript: it gives a typed syntax tree, a symbol table and a type checker. This is
what allows the Angular adapter to resolve a constant reference in a route table or
the declared type of an injected field. The cost of the style is that the analysis sees
the program as written, including the parts that a compiler would later rewrite or
erase.


2.5.2     Abstract interpretation of JavaScript
Lattice-based analysis of JavaScript itself has a formal treatment. Jensen et al.
present a static analysis based on abstract interpretation that infers sound type
information for the full JavaScript language [29]. It shows that the framework of
Section 2.6 applies to JavaScript at the level of individual values, a considerably


                                          18
harder problem than the one addressed here. Scope attribution (Section 3.2.2) uses
the same machinery over a much coarser domain than heap objects.


2.5.3     What TypeScript’s types contribute
Angular applications are written in TypeScript, so an analysis can read declared
types instead of inferring them. The type system is deliberately unsound. Bierman
et al. give a precise definition of it [10], and Richards et al. describe the annotations
as unsound by design [63]. That deliberate unsoundness means a declared type is
evidence about the program rather than a guarantee about its execution.
   The empirical picture is consistent with that. Both Flow and TypeScript detected
only about 15% of fixed bugs in JavaScript project histories when annotations
were added to the buggy versions [25]. Across 604 GitHub projects, TypeScript
was associated with better code quality and understandability but no lower bug
proneness [11]. The declarations that describe untyped libraries can themselves be
wrong: TSCheck found 142 errors in the declarations of 10 libraries [22].
    What follows for an analysis of Angular code is a division of labour. A declared
type narrows the set of candidate implementations of a call, which is useful and
is what the call graph construction in Section 2.7 relies on. It does not establish
that the call reaches exactly one of them, so an unresolved or ambiguous type has
to widen the result rather than be trusted. In the graph model this appears as the
difference between the must tier and the may tier.


2.5.4     Frameworks, not the language, are the obstacle
The practical obstacle to analysing a client-side application is the framework around
the code, not the language. Madsen et al. observe that JavaScript applications
depend on large frameworks and libraries whose behaviour a static analysis has to
know. Hand-written models of them are tedious, incomplete and sometimes wrong,
so they infer library behaviour from the way the application uses it [48]. A later
analysis by Madsen et al. addresses implicit control flow directly with an event-based
call graph for Node.js that represents listeners that run when an event fires [49]. An
Angular application has the same shape of problem, with the router, template event
bindings and observable subscriptions in place of the Node.js event emitter.
   Two further static analyses of a framework in the Angular family bear on this work.
The one that addresses navigation is Oshima and Kishi’s, discussed in Section 2.4.
The other, which does not, is Aurebesh, by Ocariza et al. [55]. It detects identifier and
type inconsistencies between models, views and controllers of a model–view–controller
(MVC) framework. The work concerns AngularJS 1.x, a different framework from the
Angular versions this thesis analyses, with a different template language, component
model and injector. What the two have in common is the problem of relating an
identifier in a template to the code that defines it.




                                           19
2.6      Formal foundations
The analysis builds on three ideas from the literature: a transition system in which
edges carry a modality, a stated position on what soundness can mean for a practical
analysis, and dataflow analysis as the computational framework.


2.6.1     Modal transition systems
The modal transition system of Larsen and Thomsen labels each transition as either
required (must) or merely permitted (may) [42]. The graph model in Chapter 3
adopts this distinction and adds a third label, unknown, for edges whose modality
could not be determined. The distinction has practical consequences. The thesis
makes a soundness claim about the must tier only. The evaluation treats the tiers
differently, since the evidence behind a may edge establishes less than the evidence
behind a must edge.
   With a single edge kind, an analysis that cannot decide whether a transition
occurs must either emit the edge and lose precision, or drop it and lose recall. With
a modality the edge records how much was established, and a consumer can select
the tier it needs. The tiers are reported separately in Chapter 5 for this reason.


2.6.2     Soundiness
Livshits et al. argue that practical static analyses are sound only with respect to a
subset of the language. They argue that this is unavoidable in practice. They also
argue that the appropriate response is to state explicitly which language features are
approximated rather than to claim soundness in general [47]. The thesis states its
own position in Section 3.1. The literature reviewed in Sections 2.5 to 2.7 gives the
specific reasons why a general claim is not available for this setting. Type annotations
in TypeScript are deliberately not guarantees. Framework configuration decides
which implementation a call reaches. The firing condition of a reactive computation
is not written in the program text.


2.6.3     Dataflow analysis and abstract interpretation
Kildall showed that many program analyses can be stated as the computation
of a fixpoint over a lattice of abstract values. Information is combined with a
join operation and propagated along the edges of a graph until nothing changes
[37]. If the lattice has finite height and the transfer functions are monotone, the
computation terminates and its result does not depend on the order in which nodes
are visited. Cousot and Cousot gave the general theory behind this approach as
abstract interpretation [16], and Nielson et al. give a textbook account [54]. Scope
attribution in Chapter 3 is an instance of this framework; its abstract values and
join are defined in Section 3.2.2.
   A particular instance needs a lattice of bounded height and a propagation graph.


                                          20
Where the propagation graph is incomplete, because a call could not be resolved,
the result is incomplete in a way the framework does not detect.

2.7.1    Routes
An Angular application declares its screens as a tree of route objects. Each route
has a path pattern and, in addition, either a component to render, a redirectTo
target, or a list of children. A route that has children but no component acts
as a path prefix and does not itself correspond to a screen. Routes can be loaded
lazily using loadChildren or loadComponent, in which case the child routes or the
component are defined in another module or file. Routes may also have guards,
namely canMatch, canActivate, canActivateChild and canDeactivate. Guards
are functions or injectable classes that return a boolean, a redirect, or a Promise
or Observable of one. A canMatch that returns false makes the router try the next
matching route rather than cancel the navigation. Routes may also have resolvers,
which fetch data the router awaits before it activates the route. Route paths are
strings, but they are not necessarily string literals. Applications that keep their
route table in one place often write path: routes.about.path, and resolving such
a path requires following the constant to its definition.


2.7.2    Components and templates
Each screen is rendered by a component, which is a class together with a template. A
template can instantiate other components by their selectors, so the components of an
application form a nesting graph. A template can also contain a <router-outlet>
element, which marks the position where the router inserts the component of the
currently active child route. Components that are above the outlet in the nesting
graph make up the application shell and are present on every screen, whereas
components below a routed component are present only on that screen. Structural
directives such as @if and *ngIf make the nesting conditional. Templates can
additionally be passed around as TemplateRef values, and components can be
created programmatically at run time.


2.7.3    Navigation sites
In a template, navigation is expressed with the routerLink directive, whose value
is either a literal path or an array of path segments. In class code, navigation is
performed by calling Router.navigate or Router.navigateByUrl; the target may
be given relative to the current route through the relativeTo option. Both kinds
of navigation site can appear in any component, in any injectable service, and in
guards, interceptors and resolvers. The source code does not state anywhere which
screens a given site can be triggered from; this information has to be derived.


2.7.4    Dependency injection
Angular creates services and passes them to the components and services that declare
them as dependencies. This is dependency injection, a form of inversion of control:
a class does not construct or look up its collaborators, but receives them from a


                                         22
container [32, 24]. A dependency is requested by type or by an injection token, and
the same token can be bound to different implementations in different injector scopes,
using useClass, useExisting or a factory function.
    The pattern is widely used outside Angular: Yang, Tempero and Melton detected
its use from source code in 34 open-source Java applications [75], and Laigner et
al. catalogue 12 dependency injection anti-patterns and detect them with a static
analyser [40]. Dependency injection configuration is therefore readable statically; it
does not state which binding a given call site will see.
    For a static analysis this turns a simple method call into a dispatch problem. A
call such as this.nav.goHome() can only be linked to the method it invokes after the
type of nav and the binding of that type in the relevant injector have been resolved.
This is the call graph construction problem known from object-oriented languages,
where a virtual call must be resolved to its possible targets. Class hierarchy analysis
resolves such a call using the declared type and its subclasses [17], rapid type analysis
narrows the result to classes that are instantiated [5], and points-to analysis narrows
it further [2]; Grove and Chambers place these in a common framework [28]. For
JavaScript, Feldthaus et al. show that an approximate call graph is precise enough
for practical tools [23].
    Dependency injection adds a further difficulty, because the binding of a type to an
implementation is not written in ordinary code but in framework configuration. The
Java literature has measured what this costs a general analysis and what recovers
it. Sridharan et al. report that the heavy use of reflection in frameworks makes
static taint analysis ineffective, and that adding support for one framework at a time
does not scale. Their tool instead generates a specification of framework behaviour
from the application code and its configuration files, which an unmodified taint
engine then consumes [67]. Antoniadis et al. capture the concepts that enterprise
frameworks share, such as components and entry points, in a declarative form and
measure about four times higher completeness [3]. Landman et al. put a bound on
what can be hoped for: reflection cannot be ignored in 78% of Java projects, and
resolving it requires unsound assumptions [41].
    The closest analogue to resolving Angular’s injectors is Jasmine, by Chen et
al. [13]. Spring’s dependency injection and aspect-oriented programming rely on
dynamic language features, so a conventional call graph of a Spring application is
missing edges. Jasmine extends Soot so that the call graph of a Spring program
becomes more complete. The structural problem is the one that occurs in Angular.
An injected field has a declared type. The binding of that type lives in framework
configuration. An analysis that does not read the configuration cannot connect the
call to a body. The difference is in where the configuration lives and how far its effect
reaches. Angular binds tokens in provider arrays that belong to a module, a route or
a component, so the same token can resolve to different implementations depending
on where the injection happens. Resolution is relative to an injector rather than
global, which makes the provider hierarchy part of the input to the analysis.
    The analysis follows the advice this literature converges on, which is to model
the framework explicitly rather than to treat its configuration as ordinary code
(Section 3.2.3).


                                           23
2.7.5     Reactive state
Recent versions of Angular include signals and effects. A signal is a value that
changes over time, and an effect is a computation that runs again whenever a signal
it read changes [26]. This is an instance of reactive programming, which goes back
to functional reactive programming [21] and has been surveyed by Bainomugisha
et al. [6]. In reactive systems the dependencies between values are recorded at run
time, and the runtime propagates updates without explicit calls in the program text.
So when a navigation call is placed inside an effect, the condition under which it
fires is a data dependence in a reactive graph and not a control-flow condition. A
static analysis can find which signals the effect reads, but in general the source does
not determine when the effect runs. The analysis of this thesis does not attempt
to bound it. Angular applications also use observables from Reactive Extensions
for JavaScript (RxJS) for the same purpose. Section 2.8 reviews what the reactive
programming literature establishes about this boundary.


2.8      Reactive programming and the limits of static
         dataflow
The reactive style gives the runtime, rather than the program text, control over when
a computation runs. This section reviews the propagation discipline that reactive
runtimes implement, and the evidence about how well reactive code can be reasoned
about with tools.


2.8.1     Propagation order and glitch freedom
A reactive program is a graph of values in which an update to one value has to
be propagated to the values that depend on it. Cooper and Krishnamurthi embed
dynamic dataflow in a call-by-value language, so that an expression evaluates to a
node in a dataflow graph [15]. Their account names the central hazard: a glitch
occurs when a signal is recomputed before all of the signals it depends on have been
brought up to date, which makes an intermediate value observable that no consistent
state of the program ever had. Their runtime prevents glitches by updating signals
in topological order, which requires the dependency graph to be acyclic. Drechsler et
al. carry glitch freedom into a distributed setting [20]. An Angular signal graph, as
described in Section 2.7.5, records its dependencies as they are read, so it is the kind
of structure that these propagation algorithms are defined over.
    The consequence for a static analysis is that the order in which reactive compu-
tations run is a property of the graph that the runtime builds, and the graph is built
from the reads that actually happen. The set of signals a given effect may read can
be over-approximated from the source. The number of times the effect runs, and
the state of the application when it runs, depend on which writes occur and in what
order, so they cannot in general be determined exactly from the source. A static
analysis could still over-approximate them, and the one presented here does not try.


                                          24
2.8.2     Reactive code and the tools developers have
The empirical literature on reactive programming reports a split between reading
code and reasoning about its behaviour. Salvaneschi et al. ran an experiment
with 127 subjects comparing reactive programming against object-oriented code
using the Observer pattern, and found comprehension significantly better in the
reactive version [66]. The same group reports that the tool support is the weak side.
Reactive programs, they argue, need debugging concepts of their own, because a
conventional debugger shows a call stack while the question is about a dataflow graph.
Their Reactive Inspector implements such concepts and outperformed conventional
debugging in a controlled experiment [65].
    The same picture holds for the Rx family of libraries, which Angular applications
use for asynchronous data. Banken et al. report that conventional debuggers have
no support for Rx and that developers fall back on inserting console logging. Their
RxFiddle visualises the structure and the values of an Rx dataflow, and in an
experiment with 111 developers it let them finish debugging tasks faster [7]. Alabor
and Stolze interviewed 10 professional engineers and observed 4 of them debugging
RxJS code. They found that the engineers rely on manually added trace logging
rather than on specialised tools. The study is a workshop paper with a small sample,
so it indicates rather than establishes the practice [1]. The surface that a tool would
have to cover is large: Zimmerle et al. mined RxJava, RxJS and RxSwift usage on
GitHub and Stack Overflow. They found that 95.2% of the Rx operators are used in
practice. The stream abstraction itself is the largest of the 23 Stack Overflow topics
they identified, at 36.4% of the posts [82].
    An analysis that aims to recover navigation from an Angular application inherits
this boundary. A navigation placed in an effect or in a subscription has a firing
condition that is a data dependence in a reactive graph. The read set is visible in
the source. The firing is not determined by it exactly, and this analysis does not
approximate it. Chapter 3 therefore specifies the modality unknown for such edges
and keeps the read set as the symbolic guard. This is the treatment the soundiness
position of Section 2.6 prescribes for a construct that cannot be decided. No pass in
this version emits that modality for an effect or a subscription. The unknown edges
it does emit are those whose destination it cannot resolve to a screen.


2.9     Mutation testing
RQ4 asks whether the extracted graph responds to source changes in the constructs
it represents, as change impact analysis requires. The method used to answer it is
mutation testing, applied in an unusual direction. The mutants are inserted into
the application source. The artefact whose reaction is measured is the extracted
graph rather than a test suite. This section reviews the technique, its use on web
applications, and the reporting practice that Chapter 4 follows.




                                          25
2.9.1     The coupling effect
Mutation testing inserts small syntactic changes into a program and measures how
many of them a test suite detects. The original argument for it is the coupling effect
stated by DeMillo et al., namely that tests which uncover simple errors are often also
effective at uncovering much more complex errors [19]. Without that assumption a
mutant would say nothing about the faults a developer actually writes.
    Jia and Harman give the standard survey of the field [30], and Papadakis et al.
survey the following decade of work and list the problems that remain open [57]. The
evidence that mutants are a usable proxy comes from Just et al., who found with 357
real faults that mutant detection correlates significantly with real-fault detection,
independently of code coverage [33].


2.9.2     Mutation for JavaScript and web applications
Mutation analysis has been adapted to JavaScript and to web applications, where
the cost of generating and running mutants is a central concern. Mirshokraie et
al. guide mutant generation with static and dynamic analysis towards code that is
error-prone or likely to affect the output, and propose mutation operators specific to
JavaScript and the web [52, 53]. Praphamontripong and Offutt define operators for
faults in the way web components interact, in a workshop paper [59].
   On the tooling side, Stryker is a mutation testing framework for JavaScript and
TypeScript. No peer-reviewed publication describing it was found, and the project
does not cite one. Its documentation describes more than 30 supported mutations
and a runner-agnostic design [68]. The absence of a paper is the reason the mutation
procedure in Chapter 4 is specified in the thesis rather than delegated to a tool’s
defaults.


2.9.3     Reporting a mutation experiment
Papadakis et al. also give best-practice advice on the use of mutation in empirical
studies of testing [57]. Chapter 4 follows it by stating the operator set, how the
mutants were produced and sampled, which mutants were excluded and why, and
the detection rate for each operator separately instead of one aggregate figure.
    This use of mutation puts the thesis in the change impact analysis tradition
rather than in test adequacy measurement. Arnold and Bohner define a framework
for comparing impact analysis approaches [4], and the collection they edited is
the standard reference for the area [12]. Chianti is the classic tool of this kind: it
decomposes the difference between two versions of a program into atomic changes and
reports, for each affected test, the changes that affect it [61]. Lehnert’s taxonomy, a
workshop paper, classifies impact analysis approaches in more detail [43]. A transition
graph whose edges carry source witnesses supports the same kind of query at the
level of screens, and the mutation experiment measures whether the graph changes
when the source it was derived from changes.

2.10       Summary and the gap
Static extraction of navigation models from web applications has been directed
largely at server-rendered frameworks, in which a page is a file and a link an anchor;
client-side routing frameworks have mostly been modelled dynamically instead.
The literature search for this thesis found three static extractions of a client-side
navigation graph, two from a framework’s own sources and one from a compiled
bundle, each building its graph for a different consumer. Oshima and Kishi’s is the
one that fixes the terms of the problem addressed here (Section 2.4). It does so,
however, under stated restrictions, among them that the routing declarations use
no children attribute and no route parameters, and it does not treat data-binding
changes as page transitions. Its attribution is computed over component containment
and the root component’s own paths. It puts no modality on the transitions. It
makes no measurement of what the extraction fails to read. The other two put the
graph to work without narrowing it. One uses it as the coverage denominator of
a generated end-to-end suite [64]. The other uses it as the reachability relation of
an access-control check, declared an over-approximation [81]. Rima et al. already
read nested and lazily loaded route trees and attach guards to edges as constraints.
What this review found no earlier work combining is attribution that follows calls
across classes and into services under their provider bindings, a modality on each
transition that separates what is unconditionally available from what a guard or an
unresolved scope makes uncertain, and a measurement of the resulting loss, classified
by construct, on applications large enough for the difficult constructs to occur. The
Android literature is the nearest static relative. It attributes navigation by resolving
the owning object, and when that resolution is imprecise it falls back on runtime
traces. A navigation site in a web application frequently has no owning object that
could be resolved. In Android the owning object of a handler usually identifies the
window, so attribution reduces to object resolution in the common case. Fragments,
background tasks and aliased widgets are the exceptions, and the Android work
handles them with dynamic evidence. That is why an Android technique cannot
simply be reused.
    The literature reviewed in Sections 2.5 to 2.9 fills in why the problem is open
and what is available for addressing it. The analysis machinery is not missing.
Abstract interpretation of JavaScript is established [29]. Source-level analysis over a
typed syntax tree is a standard tooling style [8, 58]. The Java literature has shown
repeatedly that framework behaviour can be modelled explicitly to recover call edges
that a general analysis loses [67, 3, 13]. The other peer-reviewed static analysis
in the Angular family targets AngularJS 1.x and checks template and controller
consistency rather than navigation [55]. The type information that TypeScript adds
narrows a dispatch without settling it, because the type system is unsound by design
[10, 63]. The reactive literature marks where the boundary of the approach lies. This
is because the firing of a reactive computation is decided by a graph the runtime
builds and not by the program text [15, 7]. Mutation testing supplies a method for
asking whether an extracted model reacts to source changes [30, 57]. For a statically
extracted navigation graph of a client-side framework, it has been applied only to
faults injected by hand into constructed applications [56]. An operator-level mutation

3.1      Graph model and soundness
Definition 3.1 (UI transition graph). A UI transition graph is a labelled transition
system (S, Σ, G, M, E) with

                             E ⊆ S × Σ × G × M × S.

S is the finite set of screens, the states of the system and the nodes of the graph. Σ
is the finite set of event kinds that can be raised at a screen, such as the activation
of a routerLink or a call to Router.navigate. G is the set of guards, each held
as the symbolic source text of the condition under which an edge may be taken. M is
the set of modalities, which has exactly three elements,

                            M = {must, may, unknown},

and whose elements are confidence labels: a modality states how firmly the extractor
asserts an edge, and never denotes a screen, a route or a navigation target. An
edge (s, σ, g, m, s′ ) ∈ E reads: at screen s, event σ under guard g leads to screen s′ ,
asserted with confidence m. Both the source s and the target s′ are elements of S,
namely the first and the last component of the tuple. Constructs in the source that
agree on source, event kind, guard and target yield the same edge. That edge carries
the strongest modality among them, with M ordered unknown < may < must. So E
holds at most one modality for each (s, σ, g, s′ ). The paragraph on witnesses below
says how the constructs are traced.

    Nodes outside the model. The extractor emits two node kinds that are not
screens, and the edge relation does not range over them. An unplaced origin stands
for a component, with the navigation sites in it, that the analysis could not place
under any screen. A dynamic target stands for a destination the extractor records as

and line of a construct that produced it, or an observation identifier. Where several
constructs produce the same edge, one is kept as the witness and the others are

without a witness; manual edges stay in a separate overlay. The first evaluation
method checks this mechanically.
   The soundness claim. The soundiness position that frames such claims is
argued in Section 2.6.2. The thesis claims only the following.
Claim 3.1 (Soundness of the must tier). Every must edge corresponds to a navigation
that occurs, for every input on which the enclosing code executes, over the declared
route set, under the route-order assumption of Section 6.3, and for a site whose
component is not placed by a join over an ambiguous selector, within the following
execution model: the event is a plain primary activation that navigates the current
browsing context, no other listener the event reaches starts a navigation, and no
call the reader cannot resolve to a body in the application, nor any work the handler
schedules for later, starts one.

The execution model is part of the claim and not a detail of the implementation.
Section 6.3 lists the cases it excludes: a call into a library that cancels the navigation
by starting another, a second listener on the element or an ancestor, and an activation
with a modifier key or into another browsing context. On such an execution a must
edge can name a navigation that does not complete, and the claim says nothing
about it.

target is a literal. It is not a meaningful question for edges the extractor produced
by over-approximation. Treating it as one leads to spurious failures (Section 4.3.2,

the may tier is read as an over-approximation. The must and may edges together
are meant to contain every transition the application can take between its declared
screens. An excess may edge, one the application never takes, is admitted by this
reading and costs only precision. A transition the application takes and the graph
lacks is the defect. No completeness theorem is claimed. The end-to-end check
(Section 5.3.5) measures how far the graph falls short of the transitions the suites
take; the structural references (Section 5.3.4) measure only how far it falls short of
the analysis’s own relations. Section 6.3.1 sorts what is still missing by whether it
lies inside the static boundary.


3.2      Scope attribution
What is specified and what is implemented. Scope attribution is specified here
as a fixpoint over four input relations:

   • component nesting (N ): which component’s template instantiates which;

   • router outlets: which components lie on the path from the root to an outlet,
     and below a route’s component;

   • the call graph with dependency injection (CG);

   • dispatch (D): the relations that carry NgRx effects (NgRx is the Angular
     state-management library) and router event subscriptions.

The fixpoint also uses two derived relations. Mem links each component to its
members. T links each callable that holds a navigation site to the entry guards
that navigation runs. The prototype implements three of the four input relations:
nesting, outlets and the call graph. The dispatch relation D is specified but not
implemented. The guard relation T is not implemented either, and a stand-in replaces

                                           35
it (Section 3.3). The evaluation of Chapter 4 therefore measures this three-relation
prototype and not the full model.
    Three further parts belong to the model only: guards that return a UrlTree, the
injector hierarchy, and navigation inside signal effects and observable subscriptions,
which the model labels unknown (Section 3.2.5). The extractor approximates or omits
them as Section 6.3 lists. A site that no implemented relation reaches contributes no
edge and is counted in the loss category “Attribution, service” of Table 4.3.


3.2.1     The defect being addressed
Without scope attribution, a navigation site is attributed to a screen only if it occurs
directly in the component that the route for that screen renders. Navigation sites
anywhere else are attributed to no screen. This one cause explains three symptoms:

   • shared components contribute no edges, because the application shell places
     the header next to the router outlet and not inside the subtree of any screen;

   • a component mounted at several routes contributes one edge instead of one
     per route;

   • navigations from injected services yield no edges.

These are the symptoms of the baseline, the extractor with the attribution pass
disabled (Section 3.3). On it no application is without edges.


3.2.2     Scope
This subsection is the definition of scope attribution that the rest of the thesis points
to.
   The lattice. Every navigation site is anchored at a scope: the set of screens
from which it can fire. A scope is an element of the powerset P(S). The abstract
domain of the analysis is P(S) ordered by inclusion, with set union as join,

                     X ⊑ Y ⇐⇒ X ⊆ Y,             X ⊔ Y = X ∪ Y,

the powerset lattice over the screens. Its least element is the empty scope ⊥ = ∅, a
site that fires from no screen at all. Its greatest element is ⊤ = S, every screen.
   True, computed and reference scope. Two different things are called a scope,
and the rest of this thesis keeps them apart.

   • scope ∗ (x) is the true scope of a site x, the set of screens from which x really
     can fire. It is a property of the application and not of any analysis.

   • scope(x) is the computed scope, the set of screens the extractor emits edges
     from for x. In the model it is the fixpoint of Section 3.2.3. The prototype
     widens it with fallbacks that are not constraints of the model (Section 3.3).


                                           36
A screen in scope ∗ (x) \ scope(x) is a scope too small, and a screen in scope(x) \
scope ∗ (x) is a scope too large. No true scope is established anywhere in this thesis.
For two applications a third set is read off the sources by hand: the structural
reference scope R (x). It applies the analysis’s own relations without its implementation
(Section 5.3.4). Agreement between scope and scope R shows that the relations are
implemented as stated. It does not show that either equals scope ∗ . Everywhere else
the thesis reports the computed scope and says so.
   The empty scope. The empty computed scope is likewise two situations, and
conflating them would hide a defect inside a property of the application.

   • A site is unreachable when scope ∗ (x) = ∅: the code exists and no screen can
     reach it, so contributing no edge is the correct answer.

   • A site is unresolved when scope(x) = ∅ because no rule of the analysis reaches
     it (a navigation in a service nothing is known to inject, or behind a construct
     the reader could not follow). The true scope is simply unknown.

Both yield ⊥, so ⊥ alone does not say which holds. The extractor therefore does
not let an unresolved site vanish silently. A site in a component that no rule
places is anchored at an unplaced origin, a node that carries the component’s file.
The site’s edges are held at may. A site in any other component whose scope is
empty contributes no edge. The extractor records a note naming its file and the
reason. Either trace makes the unresolved sites countable in Chapter 5 rather than
indistinguishable from unreachable code.
    Named elements. Three elements of the domain are named, because attribution
anchors edges at them. Write r′ ⪰ r for the reflexive ancestor relation on routes: r′
is r itself or an ancestor of r in the route tree. The three elements are

      {screen(r)},      subtree(r) = { screen(r′′ ) ∈ S | r ⪰ r′′ },     ⊤ = S,

and they form the chain

                       ⊥ ⊑ {screen(r)} ⊑ subtree(r) ⊑ ⊤.

The chain is stated for a route with a component; for a prefix route only subtree(r)
is defined.
    These names are a representation device for anchoring edges, not a restriction
of the domain: the join of two scopes is their union, so a component mounted at
two unrelated leaf routes has the scope {screen(r1 ), screen(r2 )}, none of the three
named elements. The names matter for storage, where an edge anchored at ⊤ or
at subtree(r) is kept once rather than once per screen. Table 3.3 assigns a scope to
each Angular construct.

     The transfer functions are monotone because the only operation they apply to
     a scope is a join, and union is monotone in both arguments.

and the worklist handles them. The restrictions, fallbacks and stand-ins of Section 3.3
are computed outside the worklist.


3.2.3       Input relations
Four relations, in order of increasing difficulty, provide the input to the fixpoint.

   • Component nesting. A → B when A’s template instantiates B’s selector,


                                              38
      resolved within the correct import scope. Matching selector text globally is
      unsound, since two components may share a selector string in different scopes.

   • Router outlets. Components on the path from the root to the outlet form the
     shell and take ⊤. Components below the component of route r take its scope
     subtree(r). A named outlet carries a second mount, which makes auxiliary
     routes representable without separate treatment.

   • Call graph with dependency injection. A call links to a method only after
     resolving the receiver’s type and its binding in the relevant injector. Reso-
     lution follows class hierarchy analysis [17]. Angular’s provider declarations
     are modelled explicitly as the source of bindings, as the framework-modelling
     literature recommends [67, 3]. Where a token admits several implementations
     the analysis joins over all of them, which is one source of may modality.

   • Dispatch relations. A dispatch is treated as a call-graph edge from every
     dispatcher to every handler, which admits NgRx effects and router event
     subscriptions under the same fixpoint.

    Algorithm 1 gives the computation, and its propagation steps are the transfer-
function applications bounded above. A step adds a screen to a scope only when
an edge of N , Mem, CG, D or T carries it there, and scopes only grow. What
the algorithm computes is therefore the least solution of the constraint system that
Table 3.3 states. In the model a component that is both mounted by a route and
rendered in the template of another component holds the join of the two scopes.
Section 3.3 reports where the prototype departs from this. It does not propagate
into a component that a route mounts. It also adds fallbacks that are not constraints
of the table, so its result is not the least solution of this system or of any restriction
of it.


3.2.4     Guards as program points
A guard that returns a UrlTree is itself a navigation, typically to a login screen. Its
source is not the guarded route. A canActivate or canMatch guard on r runs while
the router leaves the screen the navigation started from. The redirect edge therefore
leaves that screen, the origin of an edge into subtree(r). Only a canDeactivate
guard redirects from a screen of subtree(r) itself. Treating guards only as labels on
inbound edges misses this edge class entirely.
   Further, the guard of an edge in the model is the conjunction of the structural
conditions on the path from screen to call site and the guards the router runs on that
navigation (Section 3.1). The prototype does not materialise that conjunction in
the measured graph: a structural condition or an enclosing if demotes the edge to
may but is not written into its guard, so the guard of a screen-to-screen edge holds
only the router’s guards. The evaluated graph therefore records that a navigation is
conditional without recording the condition. Only an optional mode that no table of
Chapter 5 uses keeps the enclosing condition.

3.2.5     Boundary
A navigation inside a signal effect has a firing condition that is a data dependence
on a reactive graph. As Section 2.7 notes, only the read set is statically visible. The
model gives such edges the modality unknown and records the set of signals read by
the effect as the symbolic guard. No pass in this version emits one. The analysis
does not try to determine when these edges fire. It marks this limit explicitly instead
of giving a result that looks more precise than it is.

so a directive has a scope as a component does.

primary <router-outlet>. Everything it renders gets the scope ⊤. A component

likely mounted by a route the extractor cannot see, for example through a helper

function that wraps a route table. It is also treated as shell. Its edges are capped at
may, so that Claim 3.1 is not put at risk by a scope that may be too large.
   Departures from Algorithm 1. The pass departs from the algorithm in two
respects.
    The first is that it does not propagate a scope into a component that a route
mounts. A routed component keeps subtree(r) and does not also receive the scope
of a component whose template renders it. Traversal does pass through a routed
component, so a component nested beneath it still receives the scopes of the com-
ponents above. Taken alone, this restriction can only shrink a routed component’s
scope, never enlarge it. Two other rules can enlarge a scope beyond the model’s:

   • components that nothing references and no route renders, but whose subtree
     holds the primary outlet, are treated as shell and given ⊤, with their edges
     capped at may;
   • an ambiguous selector that no candidate’s import resolves joins over all candi-
     dates, which Claim 3.1 excludes.

A scope that is too small loses edges and cannot invent them, which is why the
restriction cannot put Claim 3.1 at risk. It costs recall. The constructs it strands
are counted in Chapter 5.
   The second departure is in how the call graph of Section 3.2.3 is read. The pass
ranges over the members of classes, and a member of a component runs on that
component’s screens. A call this.f.g() is resolved through the declared type of f (a
constructor parameter, typed field, inject(T) field or @Inject(TOKEN) parameter).
The call resolves to:

   • the class that type names;
   • the classes a provider binds it to with useClass or useExisting; or
   • for an abstract class no provider binds, its subclasses in the application.

This is class hierarchy analysis [17] restricted to the declared type. Bindings are read
across the whole application rather than relative to the injector that resolves them,
so where two injectors bind a token differently the join covers both. This can only
widen a scope. A factory or value provider is not read. A call on a type declared
outside the application contributes no edge.
   The seeded call-graph iteration on its own reaches the least solution of its
constraints. The scopes emitted for service sites add two fallbacks to it:

   • a member no caller reaches falls back to the join over every component that
     injects its class, the per-class approximation that the class level of the ablation
     applies to every service (Section 5.3.3);
   • a member the iteration does reach receives more screens where a caller the
     graph does not see reaches it: the join of that caller’s class is added, or this
     class’s own join if nothing places the caller.

Neither fallback is a constraint of Table 3.3. The first is not monotone in the call

therefore the least call-graph solution widened by these fallbacks, and not the least

because the calls on the way carry conditions the analysis does not follow.
    Anchored edges. Edges with scope ⊤ are stored once at a node of kind scope.
Edges whose screen set is exactly subtree(r) for a screen r with at least one descendant

that is not itself a screen is not anchored. Other screen sets are stored per screen. The
core provides the query edgesFrom(r) and a function that materialises all anchored
edges.
   Stand-ins for D and T . A navigation in an NgRx effect has no scope from the
model itself, because D is not implemented. Two approximations stand in where
the model has a relation the pass does not implement. Section 5.3.3 withholds them
below the full level of Figure 3.1, so no lower level counts their sites.

   • Guards (for T ). A guard is given the screens of the routes that name it, as a bare
     identifier, in canActivate, canActivateChild, canMatch or canDeactivate:
     the screen of each such route, not subtree(r), and nothing for a componentless
     prefix. For a canDeactivate guard that is narrower than the model’s scope.
     For an entry guard it is not the model’s rule, since the redirect leaves the
     screen a navigation starts from. The stand-in can therefore be too small where
     navigations into the route start elsewhere, and too large where they do not
     start at the route itself.

   • Effects (for D). An effect, being registered for the lifetime of the application,
     is given ⊤.

Edges from both are capped at may. A class the call graph does not reach and
nothing injects still has no scope. The evaluation counts those in the loss category
“Attribution, service” of Table 4.3. One change was made to the baseline itself: for
components with an inline template, the witness now points at the construct’s own
line rather than the template’s first line; on the corpus the baseline graphs with and
without this change are identical. Unit tests cover each case above, including that
the baseline is unchanged when the option is off.


3.4      Summary
The chapter defined a graph of screens and edges with three confidence labels and one
soundness claim for the must tier, relative to the declared route set, the route-order
assumption and an execution model; the evaluation tests only a necessary condition
of it. Scope attribution assigns each navigation site a set of screens as a least fixpoint
over four input relations. The prototype implements three of them, replaces the
guard relation by a stand-in, and widens the scopes with fallbacks that are not part
of the model. Chapter 4 describes how the analysis is measured.

4.1      Corpus selection and validity

4.1.1     Selection
Ten candidate applications were screened against six criteria: a real application
rather than a library or template; a nested, lazily loaded route tree; guards present;
end-to-end test configuration for a browser driver; retrievable history in which tests
and source change together; and an active repository. Six candidates were retained
(Table 4.1), each fixed to a specific commit so that the measurements can be repeated
on the same code.
   Criterion (4) was checked as configuration, not as a usable suite. At the pinned
commits only alfresco has specifications the test-source cross-check can read, so
that method covers alfresco alone. Ghostfolio and bitwarden carry no browser-test
configuration at all, so for them the criterion was not met. It was therefore not
applied uniformly: gravitee was rejected for a thin UI suite while two applications
with none were kept.
    Four candidates were rejected; the counts were read from the repositories and are
not generated. angular/components is a component library with no product router.
vendure has 169 end-to-end specifications, all of which exercise the GraphQL server
and none the user interface. gravitee declares 618 routes but has 14 UI specifications.
SAP/spartacus has a large Cypress suite, but its routing is configuration-driven in
a way the extractor does not support; that reason is tool support, which is not one
of the six criteria, so this rejection rests on a ground added after screening began.
   Route-tree size and end-to-end test density were inversely related: no application
provides both a large route tree and execution-based ground truth. The methods
that need test suites are applied only to the applications that have them, and the
other methods to all six.

4.1.2      Validity of an open-source corpus
Kalliamvakou et al. show that many GitHub repositories are inactive, personal or
not software projects, and recommend filtering candidates by explicit criteria and
reporting them [34, 35], which the selection above does. The remaining threats
are external validity (open-source applications may differ from proprietary ones)
and a possible selection bias, since I selected the corpus and wrote the extractor.
The selection protocol is therefore reported in full: the criteria were fixed before
any results were obtained, but one candidate was rejected on tool support and two
retained applications do not meet the test-suite criterion. The corpus spans nearly
two orders of magnitude in routes, and the commits and harness are released so the
measurement can be repeated.
    None of this addresses a further threat. The extractor was developed on this
corpus and is measured on it (Section 6.2), so the figures are fitted to it. The one
measurement outside it runs the frozen extractor on the seven subjects of Rima
et al. against their ground truth, preregistered before any subject was mapped
(Section 5.3.7). A case study on a proprietary Angular application, reporting only
aggregate figures, is planned as the most direct response (Chapter 6). The literature
reviewed in Chapter 2 offers no standard benchmark corpus of single-page applications
either, so the corpus and its manifest are an output of the thesis.

4.2      Metrics
Each research question is answered with one main measure. Table 4.2 lists every
ratio the thesis reports, and the paragraphs after it define the terms the table uses.
    Navigation construct. A navigation construct is a routerLink binding in a
template, or a call to Router.navigate or Router.navigateByUrl in class code,
in the application source excluding tests. Constructs are found by a separately
written parser that shares no code with the extractor. Table 4.5 qualifies what that
independence covers: for the route-path forms added during development, the two
resolve the same constructs by the same rules, and three of the independent parser’s
corrections were made because it disagreed with the extractor.
   Must conversion (RQ1). Must conversion is the fraction of in-scope constructs
that are witnessed by at least one must edge. Three rules make it precise.

   • A construct is matched to a witness on its own line or on a line either side, to
     absorb offsets in the extractor’s locations. Two constructs on adjacent lines
     can therefore both be credited by one witness, so the ratio is an upper bound
     at line granularity.

   • Query-only navigations and the two exclusions of Table 4.3 are left out of the
     denominator as well as the numerator.

   • When several constructs produce the same edge, the extractor keeps the most
     certain as the witness and records the others as merged witnesses, each with
     the modality it earns on its own. A construct counts as converted only where
     it earns must itself.

    The other ratios. More than one of these measures has been called coverage in
the literature this thesis builds on, but they are not interchangeable: on this corpus
they differ by more than an order of magnitude (99.2 % of sites accounted for against
1.4 % converted to must). Node coverage rises if less of an application is read, so the
blind-spot count is printed beside it. The recovered share widens the must-conversion
numerator to an edge of any tier. The accounted share alone measures whether the
losses are declared, not how much is recovered. Coverage without a qualifier means
node coverage; the gap in recovered constructs is called the recovery gap, and the
loss tables measure it.
    Agreement between a scope and the rendered interface (RQ3). The
measures above cannot be asked the question the contribution turns on: is the set of
screens that attribution computes for a site the set that site can really fire from? The
rendered-interface check, run on the harness of the runtime route oracle (Section 4.3),
answers one direction. The harness navigates to each screen the graph holds, reads
the in-app links the DOM carries and compares them with the edges the graph’s
per-screen query yields there.
    A link rendered at a screen where the graph has no such edge is unambiguous: the
site was attributed to too few screens or never read. An edge the graph has and the
DOM does not show is weaker, since a template may render links conditionally and

                                          47
this harness signs in to nothing; where a target could not be resolved to one address,
every address the static prefix admits is recorded at reduced confidence, which is
not a claim that the screen links there. This direction is therefore judged only over
predictions that name a destination exactly, and their number is published. Three
bounds apply. Only template-sourced sites are judged, since a Router.navigate
call in an event handler leaves nothing in the DOM. A screen whose guard redirects
to a sign-in page without a backend renders another screen’s links and cannot be
judged; such screens are counted apart, and on this corpus they are most screens
(Section 5.3.1). Ghostfolio’s per-locale build does not fit the harness, so it is measured
by every other method and by none of this one.
    The ablation and the structural reference (RQ3). Two measurements ask
whether the attribution computes a set of screens that agrees more closely with a
structural reference than a simpler analysis does, or only a larger one.
   The ablation withholds the mechanisms of Section 3.2 one at a time and extracts
the whole corpus at each level:

   • Owned: a site belongs to the screen whose routed component’s own file holds
     it, the direct ownership of the Android literature.

   • Nesting: adds component containment through template element selectors.

   • Rooted: adds the shell rule, so a component the root renders is attributed to
     every screen. Oshima and Kishi assemble their page information from the root
     component as well (Section 2.4), so this level measures how far the prior work
     reaches here.

   • Outlet: adds router-outlet descent.

   • Full: adds the member-level call graph, with its fallback join and the stand-ins
     for guards and effects.

Each level adds to the one before it, so the full step is not one mechanism alone. A
sixth level, class, runs beside the nested ones and replaces the call graph with the
per-class rule, which joins a navigating service over every component that injects its
class. The harness checks on the real graphs that the levels nest: a (site, screen) pair
present at one level and absent at the next is a defect in the switch, and no table is
written.
    The structural reference is scored in both directions, which no other method
allows. For one application, the screens each navigation site fires from were read off
the sources by hand, with a derivation per site, in route-oracle/ground-truth/
realworld.json. It is the structural reference of Section 3.2.2, called the ground
truth below. A pair the reference has and a level does not is a scope too small by
the reference; the converse is a scope too large. Four limits apply.

   • On realworld it is one application, small enough to read exhaustively. A second,
     alfresco, is read under the same rules (Section 5.3.4).



                                           48
   • It is the author’s reading, so it is not independent of the tool’s author. It is
     published with its reasoning so a reader can check it.

   • Its rules are the analysis’s own relations, and a template condition or guard
     that admits a screen only in one sign-in state does not narrow a scope under
     them. The ground truth therefore tests whether the implementation applies
     the relations correctly, not whether they match what the running application
     renders.

   • It is checked in one direction only: the scorer reports every site the graph
     places that the ground truth omits.

   The end-to-end navigation check (RQ3). The structural reference applies
the analysis’s own relations, so it cannot show that they miss a navigation the
application performs. This check takes its reference from execution. Two applications
ship an end-to-end suite that can be run here. The first, realworld, runs against
the public demonstration backend, which is not pinned. The second, mifos, runs
against a local Fineract server with the image pinned by digest. A small module
added to each application logs every navigation the router completes while the suite
runs, with the route patterns of the screen left and the screen reached.
    An observed pair is such a source and target pattern for a navigation the applica-
tion itself triggered; back-button navigations and the first screen after a full page
load are excluded. A pair is contained if any edge, must or may, joins the two screens
once scope nodes are expanded to their members, with parameter names ignored.
An edge to an unknown target never counts. A hit is any such edge, not the edge
of the site the test used, so the check does not test the scope of an individual site.
Redirected navigations are compared on the address they asked for, as preregistered.
The scorer’s first departure from this rule is listed in Table 4.5, and its figure is not
used.

match wins:

   • redirect: the navigation was redirected and the graph holds the pair on the
     address it landed on (the preregistered redirect class);

   • base: the target is reached from a screen above the source but not from the
     source, as a relative link resolved against the wrong route appears;

   • dynamic: the source screen’s routed component, or one above it, holds a site
     whose target the extractor records as unresolved;

   • other: none of these.

of the order, the dynamic count is what is left after base. On mifos every miss met

    The counting rules, three validity checks and predictions for each application

    Loss breakdown (RQ2). Each construct is matched to the edges whose witness

extractor reproduces the baseline edge set exactly on every application (Section 3.3).
   Must-tier precision is the fraction of must edges that meet two conditions. The
witness line contains a construct of the claimed kind with the claimed target, and
the destination node sits at an address the independent route set declares; otherwise
a node minted at an address the application never mounts would pass.
    An edge whose destination the check cannot read is neither a pass nor a failure,

that do not fail. RQ3 is answered positively only if the recovered share and must

either run, not as a precision that did not fall where the check reads only part of the
tier. The bounds of the two runs cover different sets of must edges, so they are not
compared as rates.

4.3.1     Preconditions
Two properties of the extractor were checked before any measurement. Determinism:
two extractions from the same unchanged source give identical nodes and edges.
No accumulated state: extracting into an existing database gives the same graph as
extracting after deleting it. Without them, differences seen in mutation testing could
not be told from noise.

5.1     The two levels of loss (RQ1)
RQ1 is answered at two levels. The first is whether the graph holds the screens the
application declares. The second is how much of the application’s navigation becomes
a deterministic transition between them (the ratios are defined in Section 4.2). The
first is a precondition of the second, because a transition cannot start or end at a
screen the graph does not have. It is not a numerical bound on the second: one ratio
counts screens and the other counts constructs, so a missing screen costs only the
constructs that name it.

can produce many over-approximated may edges.

5.3.2        What the attribution discriminates
The rendered-interface check cannot say whether the scopes are too large, so this
subsection asks how much narrower the computed attribution is than the widest one
there is. Assigning every navigation site to every screen recovers every construct and
needs no analysis. It is useless, because the per-screen query would return the whole
site list on every screen. The ratio between the two measures what the analysis
contributes (Table 5.12).
   The analysis is between 1.7 and 18.7 times narrower than that baseline, and the
low end of the range is the figure that qualifies RQ3. On k8sdash the average site is
attributed to 39.5 of 67 screens, which is 59 % of the application. The per-screen
query there excludes about two screens in five and admits the rest.
    Two things follow, and the second is the less favourable to the analysis.

   1. The trivial baseline is not a competitor for the must tier. An unguarded site in
      a shared component attributed to every screen would yield a must edge from
      screens that never render it, so Claim 3.1 would fail by construction. That
      none of the readable must edges attribution added fails the witness check is
      meaningful only where the attribution is narrow. Of the 142 must edges it
      added, 62 are unread, all on k8sdash, where the scopes are widest.

   2. On part of this corpus the attribution is not very narrow. A scope that names
      three fifths of an application is a weak statement about where a site fires,
      and the attribution recovery RQ3 reports is bought with scopes of that width.
      Nothing in the evaluation shows those wide scopes to be wrong, because the
      rendered-interface check could not test the direction in which they would
      be wrong. Nothing shows them to be right either. The recovered share of
      Table 5.22 should be read together with the widths in this table.

5.5.1    What the losses were
This section keeps two words apart: a class is a row of Table 5.4, and a cause is

Read by the final version. The information was in the source, so the loss was

    commands array, relativeTo passed through a variable, and the base of a
    relative link in a template shared with child screens (Section 5.3.5, Table 4.5).

  • Attribution: 66.7 % of its constructs are recovered. The remainder is in Ta-

   The causes the final version reads fall into three groups, traced here in the source.

The route table was not reached. This is the lazy-boundary cause. An Ng-
Module loaded by loadChildren keeps its routes in a separate *-routing.module
that it imports, and a reader that stops at the module file finds nothing. A lazy
route may also name a module through a barrel that re-exports a feature mod-
ule. A reader that follows one hop finds no table and places the screens at the
application root (/breach-report), where the running router mounts them deeper
(/reports/breach-report). Both static readers shared this cause, so their agree-
ment could not expose it and the runtime route oracle did. The final extractor
follows the chain to the table, bounded at three hops.

The path was named, not written. This is the constant-path cause. In one
application every route path is a reference into a constant table, which collapses its
graph to a single node when it is not followed.

The destination was named, not written. A target may be a field, a dotted
chain into the route table, an element of a commands array, the return of a builder,
or a value in a lookup the component fills. A field seeded with a literal is mutable
state, not a constant, and the reader does not follow it, because following it would
turn a run-time value into a must edge.
   Node extraction is therefore not the bottleneck on the final version: every
application is complete against the readers’ denominator. An analysis that decides
where a navigation can fire needs a node for the screen it fires from, and a construct
whose source screen has no node is a loss attribution cannot repair.

5.5.3     The final tier and the node set
The final tier. The attributed must tier has 0 witness-check failures among 159
edges, with 62 destinations unread, which are neither passes nor failures. The unread
destinations are the toolbar edges of one application, whose source side rests on the
scope of its chrome component and on the route-order assumption. The witness check
compares the destination a construct names with the destination its edge names; it
does not ask whether the construct runs every time or whether the router lets the
navigation through, which the demotion rules cover. Neither the source reading of
the must tier, made once by the AI assistant with the extractor’s decisions in view,
nor the mechanical check is an independent proof of Claim 3.1.

The whole graph. Over the whole graph the check says much less. The 13830 edges
cite 15638 locations, and only 7.0 % are clean, because 87.2 % are over-approximations
for which the check claims no target agreement. 39.4 % of all edges (5454) come from
one call site in mifos, view-transaction.component.ts:135, a navigateByUrl to
a template literal with an empty static prefix. Of the 1437 locations the check judges,
76.2 % are clean, and none of the rest is cited by a must edge. A precision figure for
the must tier is not one for the graph.

The node set. Across the corpus the compared graph declares 0 screens at
addresses the framework mounts nothing at. Every address the extractor claims is
an address the framework’s own configuration mounts, which is external evidence
about these six applications that the two static readers could not produce, since
an address both place at the wrong prefix is one they agree on. The evidence is a
precondition of the must-tier property and not part of it, and it is bounded by what
a census keyed on addresses can represent: entries on a named outlet or decided by
a UrlMatcher (65 route entries) are counted in neither column.

The runtime route oracle. The oracle loads each application, built in its develop-
ment configuration, in a headless browser, reads the live router’s route configuration
after expanding every lazily loaded subtree, and counts an address as mounted when
the configuration places a component there on the primary outlet. No route file is
parsed. Against the 1146 addresses it mounts, the node set is 892 of 1146. The oracle
ran on an earlier graph (29–30 October) with the same node total, one corrected
using earlier findings of this check. The oracle’s classification was itself checked by
navigation and agrees on 41 of 41 addresses; the 251 unminted addresses are not
individually checked.

5.6      Dead links, found from the source
A site whose target the application mounts nothing at is a dead link. The method
finds candidates for such links at no extra cost. The candidates are found statically,
and each is then checked against the route configuration the runtime route oracle
recorded before it is reported. The result is a candidate list and not a verdict: no
candidate was navigated to in a running application, so that a link is reached at run
time is not established.
    The clearest case is mifos. A transactions tab links to a journal entry at the address
/journal-entry/view/:id. The application declares that screen at /accounting/
journal-entry/view/:id, inside the accounting module. The link omits the parent
prefix, so the URL it builds is one no route matches. mifos declares a catch-all
route to a not-found component, so the link does not fail invisibly. It renders the
not-found screen, which a user can mistake for missing data rather than a broken link.
The same shape repeats across the application: links to /loans-accounts/... and
/savings-accounts/... name subtrees declared only under an owner, and further
calls name segments the application mounts under other names. A test that never
opens the tabs holding these links would not find them, and a crawler would find
them only if it reached those screens. Reading the route configuration finds them
without running anything.
   The list is not one defect class, and the split matters for what each part is worth.

   • 18 of the candidates are an absolute link written against a path the application
     does not mount, usually the name the server uses rather than the one the
     router does. Those are the application’s.

   • 5 come from a relative routerLink, such as [routerLink]="’edit’" or
     [routerLink]="[’../../transactions’]". Their target depends on the
     route the link resolves against, that of the component holding it (Section 3.2.6),
     so a wrong base is the analysis’s question before it is the application’s defect.

   • 6 are neither, because the result files do not record enough of the construct to
     say which it is. They are counted and not classified, rather than assigned to
     the half that would flatter the finding.

    The last two groups are reported as candidates and weighted lower. Counted as
places in the source rather than as targets, the three groups are 18, 3 and 6; the
difference is one relative link in a shared template that resolves against three owning
screens.
    A further 69 sites are not published at all, because they sit outside the directory the
measurement is scoped to, in ../../libs, ../aca-shared, ../browser, in the repositories
of 2 applications. Most are the source of a sibling front end, a browser extension
whose own router declares the same addresses a census would have called dead, so
publishing them would report one application’s valid links as another’s defects. They
are counted here and left out of the census.

Chapter 6

Discussion

This chapter interprets the results of Chapter 5; it does not repeat them. The thread
running through the chapter is that the extractor loses transitions in two places, at
the nodes and at the edges, and that each level limits what the other can achieve.


6.1      Key findings
Two places where extraction fails. Static extraction of a transition graph from
Angular source fails in two places, and the first turned out to be the tool’s rather
than the method’s. Node extraction is complete on all six applications against the
readers of the route configuration (Table 5.3). The runtime route oracle observes no
node placed at an address where the framework mounts nothing. That shows that
no such error was observed, not that none can occur. The runtime route oracle also
bounds the first claim, and node completeness has two readings.
  • Against the readers of the route configuration, node extraction is complete on
    all six applications. The loss classification is computed against this weaker
    reading.
  • Against the mounted addresses, the route configuration the oracle reads holds
    251 addresses with no node, 242 of them in ghostfolio (Section 5.5.3). Only
    2 of the six are complete in this stronger sense of a node for every mounted
    address, which is what a user of the graph would want.
The node defects (constant paths, lazy boundaries) are traced in Section 5.2. The
final version reads their causes (Section 5.5), and those losses are empty.

What remains is lost at the edge. The navigation sites exist in the source and
the screens they would connect exist in the graph, but the extractor cannot decide
which screens a site belongs to. The exceptions are sites that the diagnosis labels as
having a target screen with no node. The label also covers targets held in a field.
Most of these sites are in ghostfolio (Table 5.10). Scope attribution addresses this
loss at the edge. Under the order in which the loss rules are applied it is the largest
loss category in every application (Table 5.5). That order, however, is part of the
measure (Section 6.2). The ranking is a fact about an extractor, not a limit of the
approach. The two levels are not independent. Attribution cannot draw an edge


                                          93
into a screen that has no node. A complete set of nodes yields few transitions while
the sites outside the component a route renders stay unattributed. Reporting only
one level would have described a tool that works better than it does, which is why
Chapter 5 reports node coverage beside must conversion.

RQ3 and what the loss rules can delimit. A lost construct is assigned to the
first loss category that applies (Table 4.3). A construct inside a shared component
that appears only in screens without nodes is therefore counted as an attribution
loss, although attribution alone cannot recover it. The categories are a diagnostic
partition of the losses, not a bound on what attribution recovers.
   The demotion rules decide whether the edges attribution added at k8sdash (its
toolbar edges, Section 5.5.3) occur on every input. 125 of them are kept at must. The
demotion rules were written during development, in part in response to objections
from red-team panels run with the AI assistant. The witness check finds 0 failures
among the 159 must edges. It cannot read the destination of 62, all of them k8sdash’s
toolbar edges. So only about half of that application’s must edges are read.

RQ4 is conditional, and the condition is RQ1. Leave aside the rename
operator, whose detection is close to guaranteed by construction. The other three
operators are each generated or scored only at constructs the graph already represents
in the simplest form the extractor reads. They are detected in 45 of 45 scored mutants
on the attributed graph (Table 5.21), split as follows.
  • Deleted routerLink: every one is detected.
  • Retargeted calls: 20/20.
  • Removed guards: 11/11.
The mutation harness was corrected during development after its misses had been
read (Section 4.3.2), so the clean result is not an independent test. It does not show
that the remaining operators would survive a larger or differently drawn sample.
    For guards, what separates a detected mutant from an unobservable one is
whether any edge enters a screen the guarded route yields, which is the exclusion
rule (Section 5.4). The class “guards unreliable in both directions” of Chapter 5
rests instead on what Section 5.5 measured. These are a guard carried by a route
a wrapper function returns, and a canActivate element written as a call. Source
review in red-team panels found those defects, not the witness check. The mutation
run neither confirms nor refutes the class.
    Detection is also conditional on recovery. The conclusion is therefore as follows.
Given that a construct is represented in the graph, every scored change to it was
visible. The probability that it is represented at all is what RQ1 measures. For
change impact analysis this form of claim is appropriate, because an impact query is
only asked about the part of the application that the model represents. The graph
states which part through its witnesses.

Two uses of the graph. The first, with measured support, is change impact
analysis. Every edge carries the file and line of the construct that produced it.

                                         94
Changed lines therefore map to the edges whose witnesses fall inside them. From
there they map to the screens those edges leave and enter. This is the screen-level
counterpart of Chianti [61], in the impact analysis tradition of Arnold and Bohner
[4, 12, 43]. RQ4 shows that the mapping reacts to the injected edits for the constructs
the graph represents. That is a property such an analysis needs, not a measure of its
accuracy, which would ask whether every affected screen is named and how many
are named in excess.
    The second, not itself measured, is checking in continuous integration at no exe-
cution cost. The graph is recomputed from source on each commit, deterministically
and without installing, serving or crawling anything (Section 4.3). Properties such
as “a screen still has an inbound deterministic transition” can then be asserted like a
type check. A guard assertion is the member of that list the graph cannot yet carry,
and for a screen no edge enters there is nothing to read. A dynamically built model
cannot be used this way at the same cost, because it needs a running application,
test data and an exploration budget [50, 51, 36].

Where both uses stop. Both stop at runtime dynamic routing: a target computed
from a value, a route table assembled at startup from configuration, and an overlay
no route describes. There the static graph is silent or over-approximates into the
may tier, which carries no soundness claim. Under the assumptions of Claim 3.1 the
must tier is a lower bound on the navigation an application can perform; the may
tier is not. A query that must not miss a transition therefore cannot be answered
from the graph alone. The graph’s witnesses and declared approximations tell a
consumer which queries those are. Authentication bounds the deterministic tier in
the same way. A guard decides on state the source does not fix, so a reader that
keeps Claim 3.1 demotes it. The small must tier is in part this fact and not a defect
of the extractor. Taking every guard to let the navigation through raises the tier
from 159 to 203 edges (Section 5.5).

graph holds 162567 of the 367236 possible pairs (Section 5.3.5). The classes are the
author’s reading of each miss, recorded with its site in the repository; the script that
joins them to the scores refuses a miss without a class and a class without a miss.


6.4       Transfer to other frameworks
All measurements in this thesis concern Angular. This section argues how much of
the approach would carry over to React with React Router and to Vue with Vue
Router [60, 80]. It is a qualitative analysis of the routers’ documented behaviour,
not a measurement; showing that the approach performs as well on React or Vue
would require a corpus for each framework.
   The analysis has a framework-independent part and a framework-specific part.
The graph model, the lattice of scopes, the fixpoint, anchored edges and the expansion

                                               108
query do not mention Angular. What is specific to Angular are the four input relations
of Section 3.2: component nesting, router outlets, the call graph with dependency
injection, and dispatch relations. Moving to another framework means deriving the
same four relations from that framework’s constructs.
   Outlets transfer directly: in all three routers a parent route renders a placeholder
where the matched child is inserted. The components above the placeholder form a
shell that is present on every child screen, so the scopes ⊤ and subtree(r) have the
same meaning.
   The call graph is easier in React and Vue, because a hook or composable gives
every navigation site an owning component and no injector needs to be resolved.
Code that imports the router instance directly is the analogue of Angular’s service
case and can be resolved by ordinary import resolution.
    Redirects do not transfer, and the asymmetry was found by porting the model’s
reading. Angular’s validator refuses a route that declares redirectTo beside
children or a component. A redirecting Angular route therefore has neither a
layout nor a component to lose, and the model’s step from “redirects” to “renders
nothing” costs nothing. Vue Router applies a record’s redirect only when that
record is the last one matched, so a redirecting parent with children does render
its component for a matching child. Carrying the Angular reading into the Vue
extractor dropped those components. The extractor now keeps the component of a
redirecting record that has children. It declares one residue as a note at the parent
rather than modelling it as an edge: navigating to the parent’s own address lands
on the redirect target with that component unmounted. The same porting exposed
a second Vue-only hazard. A table that mixes the Vue 2 catch-all ’*’ with the
Vue 3 form ’/:pathMatch(.*)*’ folds both to one address. The extractor keeps the
record declared first. Where that is the Vue 2 form, which Vue Router 4 rejects, the
surviving component is the wrong one. The collision is declared, but which record to
keep is not something the table alone determines.
   Guards move to different scopes. A React Router loader redirect plays the role of
canActivate, so its scope is the join of the origins of the navigations that may run
the loader, as the relation T gives for entry guards, and not subtree(r). Vue’s global
beforeEach guard corresponds most closely to a canActivateChild on a root route
with no component, anchored at ⊤.
    Component nesting is harder in React. Angular and Vue keep templates in a
separate language, so the nesting relation can be read from element names. In React,
components are created in JSX, which is ordinary JavaScript. A component can be
stored in a variable, passed as a property or as children, and rendered under any
condition the language can express. Recovering the nesting relation then becomes a
data flow problem closer to points-to analysis than to reading a template. This is
the main place where a React version would need new work.
    The lattice, the fixpoint and the anchored representation transfer unchanged.
Of the relations, outlets and guards transfer with small changes, the call graph
becomes simpler, and component nesting becomes harder in React. These are
expectations derived from the routers’ documented behaviour, and testing them on
real applications is left for future work (Section 6.5).

                                         109
6.5      Future work
This section looks forward; the development versions and the corrections between
them are listed in Section 4.3.2. The topics are listed in the order of how much each
would change what the thesis can claim.

An oracle for the screen set on a large application. This is the cheapest
addition that would strengthen the thesis most. The hand-built ground truth of
Section 5.3.4 covers only the smallest application. Reading every site by hand is
not practical on an application of hundreds of screens, where most of the corpus’s
(site, screen) attributions are made (Table 5.12). Two routes lead there: driving such
an application into a signed-in state and reading its rendered links, or annotating a
stratified sample of its sites instead of all of them.

The unimplemented part of the model. Chapter 3 specifies two things the
prototype leaves out.
   • The dispatch relations that carry NgRx effects and router event subscriptions.
   • The injector hierarchy that the implemented call graph reads past, since it takes
     every provider binding as applying application-wide (Section 6.3). Reading
     bindings relative to the injector that resolves them would narrow the scopes,
     and the fixpoint already covers it. The call graph follows class hierarchy analysis
     [17]. It models the provider declarations explicitly, as the framework-modelling
     literature recommends [67, 3].
Guards that return a UrlTree belong to the same group, since a redirecting guard
is itself a navigation site and not only a label. The wider treatment of guards in
Chapter 3, where the guard of an edge is the conjunction of the conditions on the
containment path with the guards the router runs, is the more substantial piece
of work. Its test is the guard-removal operator, which on this corpus reaches only
guards the graph already records on an edge (Section 5.4).

A runtime tier. The runtime tier is the complement to the whole static approach
and not an extension of it. The model already admits observation identifiers as
witnesses beside source locations. Setting that tier against the dynamic lineage, where
the state flow graph comes from firing events on a running application [50, 51, 74],
would answer the question this thesis cannot. The question is how much of what a
crawler finds the static graph already contains, and how much of what the static
graph contains a crawler never reaches. The Android work combines static analysis
with runtime traces in the same way [45, 39].
   For applications used signed in, such a combination is also the way to complete
the graph: a signed-in run against a seeded backend would show which may edges
occur, and an observed transition would gain an observation witness beside its source
witness. That is evidence that the may edge exists, not a promotion to must, since a
must edge asserts the transition on every execution the claim ranges over and one
run shows it on one. A candidate never observed stays may. The combination can

                                         110
therefore add evidence without weakening Claim 3.1. This thesis neither builds nor
measures it.

A larger and broader corpus. An automated search over a larger pool of
repositories, keeping applications the extractor handles badly [34, 35], would weaken
the tool-driven selection bias of Section 6.2. A case study on a proprietary industrial
application, reporting only aggregate figures, is the most direct answer to the external
validity threat.

The use that motivated the thesis. That use is still unmeasured. Consider
a graph of screens and guarded transitions, recomputed from source and carrying
a witness on every edge. Whether such a graph improves mobile testing agents or
coding agents (Chapter 1), or improves automated test generation, is a controlled
experiment that this thesis does not attempt. The graph and the harness are the
artefacts such an experiment would need, and the defects quantified in Chapter 5
are what it would have to control for.


6.6      Summary
The transfer argument is a hypothesis, not a measurement. The most valuable next
steps are an oracle for the screen set on a large application and a runtime tier that
completes the graph for signed-in use.

Contributions. The thesis contributes four things. The first is the extractor, built
in this work. It accepts nested and parameterised route trees, which the stated
restrictions of an earlier Angular extraction exclude. Those restrictions admit 0
of the 6 corpus applications (Section 5.3.6). The extractor extracts all of them.
The second is the measurement itself: a corpus of six pinned applications, five
evaluation methods with different blind spots, four further checks of the scopes,
and a classification of every lost construct. The third is the apparatus that makes
it checkable. The result tables are generated from the harness’s result files. The
methods that read the sources re-run from pinned commits. The runtime route oracle
re-runs only in part. The realworld end-to-end check depends on an unpinned public
backend. Superseded figures cannot be regenerated. The fourth is scope attribution,
specified as a dataflow analysis over screen sets and implemented over three of its
four input relations (Section 3.2). It contains the mechanisms of earlier work as levels
and adds one they lack, the placement of navigation inside services (Section 5.3.6),
which also accounts for the transitions it adds over their rules on their own subjects
(Section 5.3.7).



                                               114
What remains open. The dispatch relation is specified but not implemented,
the guard relation is replaced by a stand-in, and the call graph ignores the injector
hierarchy. The screen sets were checked in both directions on two applications only,
against references that apply the analysis’s own relations. Further, the extractor
was developed on the same corpus it is measured on; on the seven applications of
Rima et al., which it was not developed on, it holds 69 of the 73 reference pairs,
after four defects found there were repaired (68 before them), so those figures too
are now partly fitted (Section 5.3.7). Beside their tool on the same applications
the comparison rests on readings by the AI assistant of small samples, of which I
confirmed 41 of the 41 I re-read (Section 5.3.8). The end-to-end check on mifos
found transitions lost to target forms the extractor did not read and to a relative link
resolved against the child tab’s address rather than the route that holds it. They
were repaired after the check, so its final mifos figure is in-sample (Section 5.3.5).
The readings of the must tier were made by the AI assistant, and two readings
by one model measure consistency rather than correctness. The rendered-interface
check judged only the screens that are reachable without signing in. Driving the
applications into a signed-in state is the work that would test the rest (Section 6.5).
Finally, whether such a graph helps the consumers that motivated the work, such as
agents that drive a user interface or automated test generation, is not measured here.
   What the measurements establish is that a declared route table is a usable starting
point for static navigation extraction, but not a sufficient one.
