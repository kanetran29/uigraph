Abstract

A user-interface (UI) transition graph describes the screens of an application and the
transitions a user can cause between them. For single-page web applications such
graphs are usually built by running the application, although routing frameworks
declare routes in the source. How far static extraction gets on real applications, and
why it fails, has not been measured construct by construct.
   This thesis builds a static extractor for Angular and measures it on six open-
source applications, checking the graphs in five ways and assigning every construct it
does not recover to a loss category. The largest category is navigation that belongs
to no single screen, such as a link in a shared header. For it the thesis proposes
scope attribution, a dataflow analysis that computes the screens from which each
navigation site can fire.
    Few transitions are certain. The corpus yields 159 edges that always fire, 33
without an assumed route order and 203 if every guard admits the user; this is largely
a matter of definition, since 1631 of the 1657 constructs that stay merely possible
sit behind a guard or branch of the application. Most causes of loss traced in the
source are constructs a static reader can read. Scope attribution recovers 66.7 % of
the constructs assigned to it (38.6 % without the largest application), almost all as
possible transitions; its one new step, placing navigation inside services, adds 2.0 %
of the sites. Its screen sets are 1.7 to 18.7 times narrower than all screens, but its
precision against a reference read from one application’s source is 82.0 %. Beside
Rima et al.’s tool, on five applications grouped after reading, its relative recall (share
of real transitions either finds, as an AI model read them) is 94.1 % against 10.2 %,
at precision 72.6 % against 75.2 %; on the largest application, most of whose pairs
only the shell reaches, precision is 6.5 %, and the pooled comparison does not rank
the tools. Mutation testing only sanity-checks the witness mapping.
    A declared route table is a starting point but an insufficient basis for static
navigation extraction. The tool was developed on this corpus, so the figures are
in-sample; consumer use is not measured.
Keywords: static analysis; UI transition graph; single-page application; Angular;
dataflow analysis; program analysis; software testing

Chapter 1

Introduction

A user interface (UI) transition graph is a model of an application. The nodes
are the screens a user can see, and the edges are the transitions a user action can
cause between them. For each edge, the graph records the event that triggers it,
the condition under which the transition is available, and the screen it leads to. A
graph of this kind makes it possible to answer questions that are difficult to answer
from the code alone. One example is which screens are reachable from a given screen.
Another is which parts of the user interface are affected when a particular component
changes.
    Transition graphs have been used in automated testing for a long time. In
the Android domain they are used for test generation and for guiding exploration
[79, 39, 14], and in web testing they form the basis of crawling-based test derivation
[50, 51]. They are also useful for change impact analysis [4, 12], because each
transition can be traced back to the code that implements it, and from there to the
tests that cover it.
    This chapter explains why a static transition graph for single-page applications
is worth measuring and what is not yet known about it. It then states the research
questions and the limits of scope, and ends with the structure of the thesis.


1.1     Motivation
There are two general ways to obtain a transition graph. A dynamic approach
executes the application and records the states and transitions it observes. A static
approach reads the source code and derives the graph without running anything.
Their limitations differ. A dynamically built graph contains only the states the
crawler managed to reach. Which states those are depends on the available test data,
authentication, and the exploration budget. The graph also has to be rebuilt for
every new version. A statically built graph covers everything the source declares. It
can be recomputed on each commit without a running system. It is limited, however,
to what can be decided from the source, and it must over-approximate wherever a
target cannot be resolved.
   The two limitations complement each other. Applications of the kind studied
here are mostly used signed in. Much of their navigation therefore runs behind an


                                          8
authentication guard whose outcome only a running system decides. A crawler, for
its part, reaches only the states its data and credentials open. A static graph can
name the screens and candidate transitions a crawler should look for, and the guards
each waits on. A run can confirm which of them occur. This thesis measures the
static side; the combination is discussed in Section 6.5 and is not measured.
    For Android, static extraction is a well-established technique. The window
transition graph work derives windows and the transitions between them from
bytecode. It also resolves the control flow of callbacks to the widget that registered
each handler [79, 78, 77]. For the web, navigation models have been extracted from
server-rendered frameworks, in which pages and links are declared in templates and
configuration files, with the help of a crawler or of runs against the server [62, 9]; a
patent describes a fully static method [69]. Modern single-page applications, however,
have almost always been modelled by executing them. Crawljax builds its state flow
graph by firing events against the Document Object Model (DOM) of a running
application [50]. Later tools in the same line improve the exploration strategy without
changing where the model comes from [51, 74]. A survey of web testing covering 2014
to 2025 collects the model-based tools of the past decade [36]. Of the tools it lists,
every one whose model construction was examined for this thesis builds that model
by executing the application. Static analyses of a modern client-side framework are
few. One builds a component dependency graph for React and does not address
routing [38]. Three extract navigation, each for a different consumer:

  • one from Angular in order to model-check it, under stated restrictions, among
    them that the application declare no nested routes and no route parameters,
    and without treating data-binding changes as page transitions [56];
  • one from Angular sources in order to enumerate the workflows a generated
    end-to-end suite should cover [64];
  • one from the compiled JavaScript bundle of a single-page application in order
    to check an access-control policy against the screens it can reach [81].

Section 2.4 compares them with the work reported here.
   When the dynamic approach was developed, a single-page application had no
declarative route table. Its navigation therefore had no explicit representation in
the source and was hard to recover from it. The DOM was the observable the
tools used (Section 2.4). Client-side routing frameworks changed this. Angular,
React Router and Vue Router all declare routes as data in the source code. They
connect navigation to those routes through template attributes and service calls.
They also attach guards to routes as named functions [27]. The artefact needed for
static analysis now exists. How well static extraction works on real applications
built with these frameworks, and where it fails, has been measured only against
hand-built references on the applications each work evaluated. It has not been
measured construct by construct.
   A statically extracted graph also has consumers outside model-based testing.
Tools that drive a graphical user interface (GUI) with a large language model either
explore an application without a model of its navigation structure or build one by

                                           9
exploring it. GPTDroid treats mobile GUI testing as a question-and-answer loop,
passing the current screen to the model and replaying the action it returns. It reports
higher activity coverage and more bugs than the best baseline on 93 applications
[46]. AutoDroid gives the model application-specific knowledge in addition to its
commonsense knowledge, held as a UI transition graph that it builds by automated
dynamic exploration offline [73]. LLMDroid uses the model to guide exploration
towards coverage the test run has not reached [70]. The approach has been applied
to web interfaces with a vision-language model and curiosity-driven exploration [72],
and a survey of large language models in software testing covers the wider area [71].
Coding agents working on a repository may also benefit from structure of this kind.
The SWE-bench issues typically require coordinated edits across functions, classes
and files [31]. Agent performance also depends on the interface through which the
repository is navigated [76]. Whether a navigation graph helps such tools is not
tested here. These uses motivate the extraction but do not depend on the results of
this thesis.
    This thesis builds a static extractor for Angular and carries out that measurement
with it. It also proposes an analysis for the largest loss it finds under the order of
its loss rules. The analysis, scope attribution, is stated as a dataflow analysis over
a lattice of screen sets. Nothing in its formulation depends on this extractor. The
measurement is the main contribution and scope attribution a modest extension:
most of what attribution recovers comes from mechanisms of earlier work, which it
contains as levels, and its one new step, the service join, adds 36 sites (2.0 %) over
the outlet level (Section 5.3.3).
    A method of this kind cannot be assessed without being instantiated, because
the questions asked here are empirical. They ask how much of the navigation in real
applications it recovers, where it fails, and whether the resulting graph responds
to a change in the source. The extractor is a static analyser for Angular built in
this thesis. It is part of the contribution, not an existing tool. It reads nested,
parameterised and lazily loaded route trees; the stated restrictions of an earlier
Angular extraction exclude the first two (Section 5.3.6). It also implements scope
attribution. Its development versions and the corrections between them are listed
in Section 4.3.2. Because the same person built the tool and measured it, on the
same corpus, the figures describe what this extractor recovers on these applications.
Section 6.2 discusses what that means for them. Chapter 6 separates the limits of
the method from those of this implementation.

Background

This chapter gives the background needed for the rest of the thesis and ends by
stating the gap the thesis addresses. Section 2.1 fixes the terminology. Sections 2.2
to 2.4 review the three lines of prior work closest to this thesis: static extraction
for Android, navigation models for web applications, and dynamic state models
for single-page applications (SPAs). Section 2.5 reviews source-level static analysis,
Section 2.6 the three formal ideas the analysis builds on, and Section 2.7 the Angular
mechanisms it has to deal with. Section 2.8 reviews reactive programming and the
boundary it puts on a static analysis. Section 2.9 reviews mutation testing, the
method Chapter 4 uses to answer RQ4. Section 2.10 states the gap.


2.1      User-interface transition graphs
A UI transition graph is a directed graph in which the nodes represent user-visible
states of an application and the edges represent transitions that a user action can
cause between those states. Figure 2.1 shows a small example in the model used in
this thesis.
    Several research communities have studied this kind of graph under different names.
In Android static analysis it is a window transition graph [79], activity transition
graph [14] or screen transition graph [39]. For Ajax (asynchronous JavaScript and
XML) crawlers it is a state flow graph over DOM states [50]. In web engineering
it is a navigation model or navigation state machine [62, 18]. This thesis uses the
term UI transition graph and treats the other terms as equivalent for its purposes,
although they differ in what counts as a state and in how the graph is constructed.
    More important than the naming is how the graph is obtained: statically, from
source code or binaries without executing the application, or dynamically, by running
and observing it. It also matters whether the graph represents guards. That is,
it matters whether each edge records the condition under which the transition is
available, or only that the transition exists. Table 2.1 classifies the work reviewed in
the following sections according to both distinctions.

2.2       Static extraction for Android
The largest body of static work on transition graphs concerns Android. Yang et al.
introduced the window transition graph, whose nodes are windows (activities, dialogs
and menus) and whose edges are transitions caused by UI-thread callbacks; the
analysis models the stack of active windows, so the back button is captured [79, 77].
A related analysis by the same group builds a callback control-flow graph over pairs
of a handler and its widget [78]. StoryDroid builds an activity transition graph
from startActivity calls [14]. GoalExplorer combines a statically derived screen
transition graph with dynamic exploration [39]. UI-CTX finds the code context of a
widget’s behaviour with a backward data-flow analysis from the handler to the call
that retrieves the widget [44].
    These approaches attribute a navigation to a screen by object resolution: a
handler is registered on a widget, and at run time that widget belongs to exactly
one window, so resolving the widget identifier, usually by constant propagation of
getId(), gives the window [78]. The limit shows in ProMal: its authors report that
imprecision in the reference analysis makes several widgets aliases of one another, so
the over-approximated data flow attaches a handler to the wrong window and the
static graph contains infeasible transitions. They combine the static analysis with
runtime traces and a learned model [45], turning to dynamic evidence rather than
refining the static attribution.


2.3       Navigation models for web applications
Navigation models for the web were first extracted from server-rendered sites. Ricca
and Tonella modelled a web application as pages, frames and forms connected by
links and form submissions, with conditional edges carrying a boolean condition

                                                14
on input values, derived semi-automatically with a crawler and annotations by an
analyst [62]. WebUml recovers a state diagram from Hypertext Markup Language
(HTML), script and server-side pages by static analysis combined with runs against
the server, deriving guards by control-flow analysis of the server code [9]. A patent
assigned to Fujitsu describes a fully static method for Struts and JSP sources [69].
SiteHopper builds abstracted navigation state machines on the fly for model checking
[18].
     All of these concern server-rendered frameworks, where a page corresponds to a
file and a link to an anchor element. None of them deals with a client-side router, a
component tree, or dependency injection. Section 2.4 turns to the work that does.


2.4      Dynamic state models for single-page applica-
         tions
With Ajax and client-side frameworks, model construction moved to run time.
Crawljax executes user events against a running application, compares the DOM
before and after each event, and builds a state flow graph whose nodes are equivalence
classes of DOM states [50]. Later work in this line changed the exploration strategy
but not the source of the model [51, 74]. The survey by Kertusha et al. reviews
web testing research from 2014 to 2025 [36]; of the model-based tools it lists, every
one whose model construction was examined for this thesis builds that model by
executing the application. The reason is largely historical: an Ajax application
had no declarative route table, one uniform resource locator (URL) could represent
many states, and nothing in the source represented routes explicitly, although static
analysis of JavaScript existed [29].
    Client-side routing frameworks changed this. The route table is now a declared
data structure, a navigation is an attribute or a method call that names a route,
and a guard is a named function attached to a route. Four static analyses of such a
framework were found during the literature search for this thesis, three reading the
framework’s own sources and one a compiled bundle. Kurant’s component dependency
graph for React stops at the component rendering graph without addressing routing
[38].
    The other three address routing. Oshima and Kishi extract page transitions from
an Angular application in order to model-check them with SPIN [56], reading the
route declarations in RouterModule and the navigable paths of every component,
and resolving the parent–child relationships among the root, routed and custom child
components. A navigable path is attributed to the routed component that contains
it, and the root component’s own paths are attributed to every page. Section 5.3.3
measures that combination, as the rooted level of the analysis presented here (the
levels are defined in Section 4.2). The authors list restrictions on the applications
they handle, among them that the routing declarations must not use children or
route parameters, and changes arising from data binding are not treated as page
transitions. How a navigation whose destination is an expression rather than a literal
is treated is not stated in the paper, and it is not assumed here. A screen is identified

                                           15
by the name of its routed component, not an address. Guards, lazy loading and
named outlets are not modelled, and a navigation site that reaches a screen through
a method call or a dispatch lies outside the attribution mechanism. The model
carries no modality, so an always-available navigation and one available only if a
guard admits it are represented identically. The evaluation applies the tool to four
constructed applications and to two published ones of 1824 and 6893 lines, with six
and twenty-three pages, and reports whether the intended model was produced and
whether hand-injected transition faults in constructed variants of the first sample
application were detected. What the extraction loses on an application it cannot
fully read is not measured; this is the question this thesis takes as its subject.
    Two recent works read a client-side router configuration statically for other ends.
Rima et al. parse Angular sources and templates to build a graph of navigation struc-
ture, interaction sites and the conditions (guards among them) that decide whether
an interaction is executable, and compile workflows enumerated over that graph into
browser tests; the graph is a coverage denominator [64]. This account is taken from
the publisher’s abstract, the operational specification in the project’s replication
package (softscanner-sw/softscanner_fa, docs/paper/approach.md), and the
anonymised manuscript in the same repository (docs/paper/main.pdf); the pub-
lished chapter was not available to this review and may differ from both documents.
Both describe attribution beyond containment: the components active at a route
are those activated by the route and its ancestor routes, closed under composition,
plus the bootstrap components, which covers what the rooted and outlet levels of
Section 5.3.3 place. A handler is followed into helper methods of the same class to
depth one and into the first callback of a subscribe. The specification excludes
router-outlet modelling and provider resolution beyond module and root providers,
and does not follow a call into a service, so a navigation inside a service member is
not placed on the screens of its callers. Zhang et al. parse the compiled JavaScript
bundle rather than the sources, taking declared routes as vertices and navigation
calls as edges, and check an access-control policy against the screens reachable from
an authorised one. Two of their four subjects are multi-page applications, which are
crawled instead. The graph is declared an over-approximation and is not narrowed.
The paper does not describe how the source screen of a navigation call is determined,
and guards appear only as runtime conditions the graph does not model [81]. Rima et
al. compare their output with a ground truth generated from their pipeline’s output
and annotated by hand for the applications they study. Neither work classifies the
losses by construct or measures them across a corpus, so the problem addressed in
this thesis is neither new nor settled. Section 2.10 states what none of these works
does.


2.5      Static analysis of JavaScript and TypeScript
         source
The analysis in Chapter 3 reads Angular source with the TypeScript compiler
application programming interface (API), so it works on a source-level abstract


                                          16
syntax tree rather than on a compiled artefact, a style used for example by Baxter
et al. for clone detection in C [8] and made a reusable library for Java by SPOON
[58]. It keeps the analysis close to what the developer wrote, which matters when
the result has to be reported at a source location; the cost is that the analysis sees
the program as written. Jensen et al. show that abstract interpretation can infer
sound type information for the full JavaScript language [29], so the framework of
Section 2.6 applies at the level of individual values, a harder problem than the one
addressed here. Scope attribution (Section 3.2.2) uses the same machinery over a
much coarser domain.
    Angular applications are written in TypeScript, so an analysis can read declared
types instead of inferring them. The type system is deliberately unsound [10, 63], so
a declared type is evidence about the program rather than a guarantee. Both Flow
and TypeScript detected only about 15% of fixed bugs in JavaScript project histories
[25], TypeScript was associated with better code quality and understandability but
no lower bug proneness across 604 GitHub projects [11], and the declarations of
untyped libraries can themselves be wrong: TSCheck found 142 errors in those of 10
libraries [22]. A declared type therefore narrows the set of candidate implementations
of a call, which the call graph construction in Section 2.7 relies on, but does not
establish that the call reaches exactly one of them, so an unresolved or ambiguous
type has to widen the result rather than be trusted. In the graph model this is the
difference between the must tier and the may tier.
    The practical obstacle is the framework around the code, not the language.
Madsen et al. observe that JavaScript applications depend on large frameworks
whose behaviour a static analysis has to know, and that hand-written models of them
are tedious, incomplete and sometimes wrong [48]; they also address implicit control
flow with an event-based call graph for Node.js [49]. An Angular application has the
same shape of problem, with the router, template event bindings and observable
subscriptions in place of the event emitter. The only other peer-reviewed static
analysis of a framework in the Angular family that this review found, apart from
Oshima and Kishi’s (Section 2.4), is Aurebesh [55]. It checks identifier and type
consistency between models, views and controllers of AngularJS 1.x, a different
framework with a different template language, component model and injector, and it
does not address navigation.


2.6     Formal foundations
The analysis builds on three ideas from the literature: a transition system in which
edges carry a modality, a stated position on what soundness can mean for a practical
analysis, and dataflow analysis as the computational framework.


2.6.1    Modal transition systems
The modal transition system of Larsen and Thomsen labels each transition as either
required (must) or merely permitted (may) [42]. The graph model in Chapter 3


                                         17
adopts this distinction and adds a third label, unknown, for edges whose modality
could not be determined. The distinction has practical consequences. The thesis
makes a soundness claim about the must tier only. The evaluation treats the tiers
differently, since the evidence behind a may edge establishes less than the evidence
behind a must edge.
   With a single edge kind, an analysis that cannot decide whether a transition
occurs must either emit the edge and lose precision, or drop it and lose recall. With
a modality the edge records how much was established, and a consumer can select
the tier it needs. The tiers are reported separately in Chapter 5 for this reason.


2.6.2     Soundiness
Livshits et al. argue that practical static analyses are sound only with respect to a
subset of the language. They argue that this is unavoidable in practice. They also
argue that the appropriate response is to state explicitly which language features are
approximated rather than to claim soundness in general [47]. The thesis states its
own position in Section 3.1. The literature reviewed in Sections 2.5 to 2.7 gives the
specific reasons why a general claim is not available for this setting. Type annotations
in TypeScript are deliberately not guarantees. Framework configuration decides
which implementation a call reaches. The firing condition of a reactive computation
is not written in the program text.


2.6.3     Dataflow analysis and abstract interpretation
Kildall showed that many program analyses can be stated as the computation
of a fixpoint over a lattice of abstract values. Information is combined with a
join operation and propagated along the edges of a graph until nothing changes
[37]. If the lattice has finite height and the transfer functions are monotone, the
computation terminates and its result does not depend on the order in which nodes
are visited. Cousot and Cousot gave the general theory behind this approach as
abstract interpretation [16], and Nielson et al. give a textbook account [54]. Scope
attribution in Chapter 3 is an instance of this framework; its abstract values and
join are defined in Section 3.2.2.
   A particular instance needs a lattice of bounded height and a propagation graph.
Where the propagation graph is incomplete, because a call could not be resolved,
the result is incomplete in a way the framework does not detect.

2.7.1      Routes, components and navigation sites
An Angular application declares its screens as a tree of route objects. Each route
has a path pattern and, in addition, either a component to render, a redirectTo
target, or a list of children. A route that has children but no component acts as a
path prefix and does not itself correspond to a screen. Routes can be loaded lazily
using loadChildren or loadComponent, and may have guards, namely canMatch,
canActivate, canActivateChild and canDeactivate, which return a boolean, a
redirect, or a Promise or Observable of one. A canMatch that returns false makes
the router try the next matching route rather than cancel the navigation. Routes
may also have resolvers, which fetch data the router awaits before it activates the
route. Route paths are not necessarily string literals: applications often write path:

                                                19
routes.about.path, and resolving such a path requires following the constant to
its definition.
   Each screen is rendered by a component, a class together with a template. A
template can instantiate other components by their selectors and can contain a
<router-outlet> element, which marks where the router inserts the component of
the active child route. Components above the outlet make up the application shell
and are present on every screen, whereas components below a routed component are
present only on that screen. Structural directives such as @if and *ngIf make the
nesting conditional, and components can be created programmatically at run time.
    In a template, navigation is expressed with the routerLink directive; in class
code, by calling Router.navigate or Router.navigateByUrl; the target may be
given relative to the current route through the relativeTo option. Both kinds of
navigation site can appear in any component, in any injectable service, and in guards,
interceptors and resolvers. The source code does not state anywhere which screens a
given site can be triggered from; this information has to be derived.


2.7.2     Dependency injection
Angular creates services and passes them to the components and services that declare
them as dependencies. This is dependency injection, a form of inversion of control
[32, 24]. A dependency is requested by type or by an injection token, and the
same token can be bound to different implementations in different injector scopes,
using useClass, useExisting or a factory function. The pattern is common outside
Angular, and its use and anti-patterns have been detected statically in Java [75, 40].
The configuration is therefore readable statically; it does not state which binding a
given call site will see.
    For a static analysis this turns a simple method call into a dispatch problem. A
call such as this.nav.goHome() can only be linked to the method it invokes after
the type of nav and the binding of that type in the relevant injector have been
resolved. This is the call graph construction problem known from object-oriented
languages, addressed by class hierarchy analysis [17], rapid type analysis [5] and
points-to analysis [2], placed in a common framework by Grove and Chambers [28].
For JavaScript, Feldthaus et al. show that an approximate call graph is precise
enough for practical tools [23].
    Because the binding lives in framework configuration, the Java literature models
the framework explicitly. Sridharan et al. generate a specification of framework
behaviour from the application code and its configuration files [67]; Antoniadis et al.
capture shared enterprise-framework concepts declaratively and measure about four
times higher completeness [3]; Chen et al.’s Jasmine extends Soot so that the call
graph of a Spring program becomes more complete [13]. Landman et al. put a bound
on what can be hoped for: reflection cannot be ignored in 78% of Java projects, and
resolving it requires unsound assumptions [41]. The difference in Angular is that
tokens are bound in provider arrays that belong to a module, a route or a component,
so the same token can resolve to different implementations depending on where the
injection happens. Resolution is relative to an injector rather than global, which

                                          20
makes the provider hierarchy part of the input to the analysis, and the analysis
models the framework explicitly (Section 3.2.3).


2.7.3     Reactive state
Recent versions of Angular include signals and effects: a signal is a value that changes
over time, and an effect is a computation that runs again whenever a signal it read
changes [26]. This is an instance of reactive programming [21, 6], in which the
dependencies between values are recorded at run time. So when a navigation call is
placed inside an effect, the condition under which it fires is a data dependence in
a reactive graph and not a control-flow condition. A static analysis can find which
signals the effect reads, but in general the source does not determine when the effect
runs. The analysis of this thesis does not attempt to bound it. Angular applications
also use observables from Reactive Extensions for JavaScript (RxJS) for the same
purpose.


2.8      Reactive programming and the limits of static
         dataflow
In reactive programming the runtime, rather than the program text, controls when
a computation runs. Cooper and Krishnamurthi embed dynamic dataflow in a
call-by-value language and name the central hazard, the glitch, in which a signal is
recomputed before all of the signals it depends on are up to date [15]; Drechsler et
al. carry glitch freedom into a distributed setting [20]. The consequence for a static
analysis is that the set of signals a given effect may read can be over-approximated
from the source, whereas the number of times the effect runs, and the state of the
application when it runs, depend on which writes occur and in what order, so they
cannot in general be determined exactly from the source. A static analysis could
still over-approximate them, and the one presented here does not try.
    Tool support for reactive code is also weak. Salvaneschi et al. found comprehension
better in reactive code in an experiment with 127 subjects [66] but argue that reactive
programs need debugging concepts of their own [65]; Banken et al. report that
conventional debuggers have no support for Rx [7]; Alabor and Stolze’s workshop
study of 10 engineers is small, so it indicates rather than establishes that engineers
rely on manual trace logging [1]. The surface a tool would have to cover is large:
95.2% of the Rx operators are used in practice [82].
    An analysis that aims to recover navigation from an Angular application inherits
this boundary. A navigation placed in an effect or in a subscription has a read set
that is visible in the source, but the firing is not determined by it exactly. Chapter 3
therefore specifies the modality unknown for such edges and keeps the read set as
the symbolic guard, which is the treatment the soundiness position of Section 2.6
prescribes for a construct that cannot be decided. No pass in this version emits that
modality for an effect or a subscription; the unknown edges it does emit are those
whose destination it cannot resolve to a screen.

2.9     Mutation testing
RQ4 asks whether the extracted graph responds to source changes in the constructs it
represents. The method is mutation testing applied in an unusual direction: mutants
are inserted into the application source, and the artefact whose reaction is measured
is the extracted graph rather than a test suite.
    Mutation testing inserts small syntactic changes into a program and measures how
many of them a test suite detects. It rests on the coupling effect stated by DeMillo
et al.: tests that uncover simple errors are often also effective at uncovering much
more complex errors [19]. Without that assumption a mutant would say nothing
about the faults a developer actually writes. Jia and Harman give the standard
survey [30], and mutant detection correlates with real-fault detection across 357 real
faults [33]. Operators exist for JavaScript and web applications [52, 53, 59]. Stryker
is a mutation testing framework for JavaScript and TypeScript; no peer-reviewed
publication describing it was found, and its documentation describes more than
30 supported mutations [68]. That is why the mutation procedure in Chapter 4 is
specified in the thesis rather than delegated to a tool’s defaults.
    Papadakis et al. advise that empirical studies state the operator set, how the
mutants were produced and sampled, which mutants were excluded, and the detection
rate for each operator separately instead of one aggregate figure [57]; Chapter 4
follows this advice. The use of mutation here belongs to the change impact analysis
tradition rather than to test adequacy measurement [4, 12, 61, 43].


2.10      Summary and the gap
Static extraction of navigation models from web applications has been directed
largely at server-rendered frameworks, in which a page is a file and a link an anchor;
client-side routing frameworks have mostly been modelled dynamically instead.
The literature search for this thesis found three static extractions of a client-side
navigation graph, two from a framework’s own sources and one from a compiled
bundle, each building its graph for a different consumer. Oshima and Kishi’s is the
one that fixes the terms of the problem addressed here (Section 2.4). It does so,
however, under stated restrictions, among them that the routing declarations use
no children attribute and no route parameters, and it does not treat data-binding
changes as page transitions. Its attribution is computed over component containment
and the root component’s own paths. It puts no modality on the transitions. It
makes no measurement of what the extraction fails to read. The other two put the
graph to work without narrowing it. One uses it as the coverage denominator of
a generated end-to-end suite [64]. The other uses it as the reachability relation of
an access-control check, declared an over-approximation [81]. Rima et al. already
read nested and lazily loaded route trees and attach guards to edges as constraints.
What this review found no earlier work combining is attribution that follows calls
across classes and into services under their provider bindings, a modality on each
transition that separates what is unconditionally available from what a guard or an


                                         22
unresolved scope makes uncertain, and a measurement of the resulting loss, classified
by construct, on applications large enough for the difficult constructs to occur. The
Android literature is the nearest static relative. It attributes navigation by resolving
the owning object, and when that resolution is imprecise it falls back on runtime
traces. A navigation site in a web application frequently has no owning object that
could be resolved. In Android the owning object of a handler usually identifies the
window, so attribution reduces to object resolution in the common case. Fragments,
background tasks and aliased widgets are the exceptions, and the Android work
handles them with dynamic evidence. That is why an Android technique cannot
simply be reused.
    The literature reviewed in Sections 2.5 to 2.9 fills in why the problem is open
and what is available for addressing it. The analysis machinery is not missing.
Abstract interpretation of JavaScript is established [29]. Source-level analysis over a
typed syntax tree is a standard tooling style [8, 58]. The Java literature has shown
repeatedly that framework behaviour can be modelled explicitly to recover call edges
that a general analysis loses [67, 3, 13]. The other peer-reviewed static analysis
in the Angular family targets AngularJS 1.x and checks template and controller
consistency rather than navigation [55]. The type information that TypeScript adds
narrows a dispatch without settling it, because the type system is unsound by design
[10, 63]. The reactive literature marks where the boundary of the approach lies. This
is because the firing of a reactive computation is decided by a graph the runtime
builds and not by the program text [15, 7]. Mutation testing supplies a method for
asking whether an extracted model reacts to source changes [30, 57]. For a statically
extracted navigation graph of a client-side framework, it has been applied only to
faults injected by hand into constructed applications [56]. An operator-level mutation
study of such a graph was not found in this review.

3.1      Graph model and soundness
Definition 3.1 (UI transition graph). A UI transition graph is a labelled transition
system (S, Σ, G, M, E) with

                             E ⊆ S × Σ × G × M × S.

S is the finite set of screens, the states of the system and the nodes of the graph. Σ
is the finite set of event kinds that can be raised at a screen, such as the activation
of a routerLink or a call to Router.navigate. G is the set of guards, each held
as the symbolic source text of the condition under which an edge may be taken. M is
the set of modalities, which has exactly three elements,

                            M = {must, may, unknown},

and whose elements are confidence labels: a modality states how firmly the extractor
asserts an edge, and never denotes a screen, a route or a navigation target. An
edge (s, σ, g, m, s′ ) ∈ E reads: at screen s, event σ under guard g leads to screen s′ ,
asserted with confidence m. Both the source s and the target s′ are elements of S,
namely the first and the last component of the tuple. Constructs in the source that
agree on source, event kind, guard and target yield the same edge. That edge carries
the strongest modality among them, with M ordered unknown < may < must. So E
holds at most one modality for each (s, σ, g, s′ ). The paragraph on witnesses below
says how the constructs are traced.

    Nodes outside the model. The extractor emits two node kinds that are not
screens, and the edge relation does not range over them. An unplaced origin stands
for a component, with the navigation sites in it, that the analysis could not place
under any screen. A dynamic target stands for a destination the extractor records as

      Screens and routes. The set S is derived from the route configuration, and not


                                               26
every route contributes a screen. Write Routes for the set of routes the application
declares and component(r) for the component that route r renders. Then

           S = { screen(r) | r ∈ Routes and component(r) is defined },

where screen(r) is the node for route r, identified by the full path that concatenates
the paths of r and of its ancestors. Two kinds of route contribute no element of S:

   • A route that declares children but no component is only a path prefix (Sec-

   • A route whose only effect is a redirectTo renders nothing.

In Angular a redirecting route is only a redirect: the router refuses redirectTo
together with children or a component. This was read off the router’s configuration
validator in Angular 18.2.14, the vendored version, and is not true of every router:
Vue Router applies a redirect only when its record is the last one matched, so a
redirecting parent does render its component for a matching child (Section 6.4).
    Angular also permits two component-bearing routes with the same full path,
told apart at run time by pathMatch or a canMatch guard. The model assumes this
does not occur: the extractor keeps the route declared first and drops the later ones,
silently for Angular and with a note for Vue and React (Section 6.4). Two routes
with different paths that render the same component give two screens, which is the
case that makes the attribution of Section 3.2 necessary.
   Witnesses. Every edge of static or runtime origin carries a witness: the file
and line of a construct that produced it, or an observation identifier. Where several
constructs produce the same edge, one is kept as the witness and the others are
recorded as merged witnesses (Section 4.2). No edge is added to the base graph
without a witness; manual edges stay in a separate overlay. The first evaluation
method checks this mechanically.
   The soundness claim. The soundiness position that frames such claims is
argued in Section 2.6.2. The thesis claims only the following.
Claim 3.1 (Soundness of the must tier). Every must edge corresponds to a navigation
that occurs, for every input on which the enclosing code executes, over the declared
route set, under the route-order assumption of Section 6.3, and for a site whose
component is not placed by a join over an ambiguous selector, within the following
execution model: the event is a plain primary activation that navigates the current
browsing context, no other listener the event reaches starts a navigation, and no
call the reader cannot resolve to a body in the application, nor any work the handler
schedules for later, starts one.

The execution model is part of the claim and not a detail of the implementation.
Section 6.3 lists the cases it excludes: a call into a library that cancels the navigation
by starting another, a second listener on the element or an ancestor, and an activation
with a modifier key or into another browsing context. On such an execution a must
edge can name a navigation that does not complete, and the claim says nothing
about it.

    The must tier is therefore a lower bound only relative to four assumptions, each
with a class of counterexample. A1, route order: a catch-all in a separately registered

execution model: the plain primary activation above; a modifier key, a second listener
or another browsing context breaks it. The edges resting on A3 and A4 are not
counted, and neither is checked against a run.
    What the evaluation tests. The evaluation tests a necessary condition of

   An exception from an earlier synchronous call is not counted, since every call can

decisions in view; this checks that each decision can be defended and is not an
independent second reading (Section 5.5). Some defects in the condition rules were
found by an earlier review of a development version’s tier and not by the witness
check (Section 4.3.2). What the witness check establishes is therefore narrower than
the claim. It establishes that every cited site exists in the source and agrees on
its target. The stronger half of the claim rests on the demotion rules and is not
independently verified.
    Scope of the claim. This is the only soundness property claimed in the thesis,
and it holds only relative to the declared route set. No such property is claimed for the
may and unknown tiers. The witness of a may edge shows that the corresponding call
site exists in the source, not that the transition is ever taken. This difference matters
for the evaluation. Whether the target found at a witness location agrees with the
target of the edge is a meaningful question for must edges, and for may edges whose
target is a literal. It is not a meaningful question for edges the extractor produced
by over-approximation. Treating it as one leads to spurious failures (Section 4.3.2,
Table A.1).
    The may tier as a design intent. As in a modal transition system [42], the
may tier is meant as an over-approximation: the must and may edges together are
meant to contain every transition the application can take between its declared
screens. This is a design intent and not a property that holds. Some rules under-
approximate: the rules that take the first matching route, read an interpolation
as one path segment, order a catch-all route last, and place dispatch and dialogs,
and the rule that a call with no body in the application navigates nowhere. The
graph can lack a transition it was meant to contain. An excess may edge, one the
application never takes, is admitted by this reading and costs only precision. A
transition the application takes and the graph lacks is the defect. No completeness
theorem is claimed. The end-to-end check (Section 5.3.5) measures how far the graph
falls short of the transitions the suites take; the structural references (Section 5.3.4)
measure only how far it falls short of the analysis’s own relations. Section 6.3.1 sorts
what is still missing by whether it lies inside the static boundary.


3.2      Scope attribution
Scope attribution is specified here over three input relations. The analysis that is
evaluated implements all three, and adds fallbacks after the fixpoint, one of which is


                                           30
not monotone; termination and the least-solution property hold for the fixpoint core
only:

   • component nesting (N ): which component’s template instantiates which;

   • router outlets: which components lie on the path from the root to an outlet,
     and below a route’s component;

   • the call graph with dependency injection (CG).

The fixpoint also uses the derived relation Mem, which links each component to
its members. Two further relations, dispatch (D) and guards (T ), are defined
in Section 3.2.7; the prototype does not implement them, and the evaluation of
Chapter 4 measures the three-relation analysis with two stand-ins and a post-pass of
fallbacks.
    Guards that return a UrlTree, the injector hierarchy, and navigation inside signal
effects and observable subscriptions (labelled unknown, Section 3.2.5) belong to the
model only. The extractor approximates or omits them as Section 6.3 lists. A site
that no implemented relation reaches contributes no edge and is counted in the loss
category “Attribution, service” of Table 4.3.


3.2.1     The defect being addressed
Without scope attribution, a navigation site is attributed to a screen only if it
occurs directly in the component that the route for that screen renders. This one
cause explains three symptoms of the baseline, the extractor with the attribution
pass disabled (Section 3.3): shared components contribute no edges, because the
application shell places the header next to the router outlet and not inside the subtree
of any screen; a component mounted at several routes contributes one edge instead
of one per route; and navigations from injected services yield no edges. On it no
application is without edges.


3.2.2     Scope
The lattice. Every navigation site is anchored at a scope: the set of screens from
which it can fire. A scope is an element of the powerset P(S). The abstract domain
of the analysis is P(S) ordered by inclusion, with set union as join,

                    X ⊑ Y ⇐⇒ X ⊆ Y,             X ⊔ Y = X ∪ Y,

the powerset lattice over the screens. Its least element is the empty scope ⊥ = ∅, a
site that fires from no screen at all. Its greatest element is ⊤ = S, every screen.
   True, computed and reference scope. Two different things are called a scope,
and the rest of this thesis keeps them apart.

   • scope ∗ (x) is the true scope of a site x, the set of screens from which x really
     can fire. It is a property of the application and not of any analysis.

                                          31
   • scope(x) is the computed scope, the set of screens the extractor emits edges
     from for x. In the model it is the fixpoint of Section 3.2.3. The prototype
     widens it with fallbacks that are not constraints of the model (Section 3.3).

A screen in scope ∗ (x) \ scope(x) is a scope too small, and a screen in scope(x) \
scope ∗ (x) is a scope too large. No true scope is established anywhere in this thesis.
For two applications a third set is read off the sources by hand: the structural
reference scope R (x). It applies the analysis’s own relations without its implementation
(Section 5.3.4). Agreement between scope and scope R shows that the relations are
implemented as stated. It does not show that either equals scope ∗ . Everywhere else
the thesis reports the computed scope and says so.
   The empty scope. The empty computed scope is likewise two situations, and
conflating them would hide a defect inside a property of the application.

   • A site is unreachable when scope ∗ (x) = ∅: the code exists and no screen can
     reach it, so contributing no edge is the correct answer.

   • A site is unresolved when scope(x) = ∅ because no rule of the analysis reaches
     it (a navigation in a service nothing is known to inject, or behind a construct
     the reader could not follow). The true scope is simply unknown.

Both yield ⊥, so ⊥ alone does not say which holds. The extractor therefore does
not let an unresolved site vanish silently. A site in a component that no rule
places is anchored at an unplaced origin, a node that carries the component’s file.
The site’s edges are held at may. A site in any other component whose scope is
empty contributes no edge. The extractor records a note naming its file and the
reason. Either trace makes the unresolved sites countable in Chapter 5 rather than
indistinguishable from unreachable code.
    Named elements. Three elements of the domain are named, because attribution
anchors edges at them. Write r′ ⪰ r for the reflexive ancestor relation on routes: r′
is r itself or an ancestor of r in the route tree. The three elements are

      {screen(r)},      subtree(r) = { screen(r′′ ) ∈ S | r ⪰ r′′ },     ⊤ = S,

and they form the chain

                       ⊥ ⊑ {screen(r)} ⊑ subtree(r) ⊑ ⊤.

The chain is stated for a route with a component; for a prefix route only subtree(r)

restriction of the domain: a component mounted at two unrelated leaf routes has

3.2.3       Input relations
Three relations, in order of increasing difficulty, provide the input to the fixpoint.

   • Component nesting. A → B when A’s template instantiates B’s selector,
     resolved within the correct import scope. Matching selector text globally is
     unsound, since two components may share a selector string in different scopes.
   • Router outlets. Components on the path from the root to the outlet form the
     shell and take ⊤. Components below the component of route r take its scope
     subtree(r). A named outlet carries a second mount, which makes auxiliary
     routes representable without separate treatment.

                                              33
   • Call graph with dependency injection. A call links to a method only after
     resolving the receiver’s type and its binding in the relevant injector. Reso-
     lution follows class hierarchy analysis [17]. Angular’s provider declarations
     are modelled explicitly as the source of bindings, as the framework-modelling
     literature recommends [67, 3]. Where a token admits several implementations
     the analysis joins over all of them, which is one source of may modality.

   Algorithm 1 gives the computation. A step adds a screen to a scope only when
an edge of N , Mem or CG carries it there, and scopes only grow, so the algorithm
computes the least solution of the constraint system that Table 3.3 states. In the
model a component that is both mounted by a route and rendered in the template of
another component holds the join of the two scopes. Section 3.3 reports where the
prototype departs from this: it does not propagate into a component that a route
mounts, and it adds fallbacks that are not constraints of the table, so its result is
not the least solution of this system or of any restriction of it.


3.2.4     Guards as program points
A guard that returns a UrlTree is itself a navigation, typically to a login screen. A
canActivate or canMatch guard on r runs while the router leaves the screen the
navigation started from, so the redirect edge leaves that screen and not the guarded
route. Only a canDeactivate guard redirects from a screen of subtree(r) itself. The
prototype does not implement this edge class.
   Further, the guard of an edge in the model is the conjunction of the structural
conditions on the path from screen to call site and the guards the router runs on that
navigation (Section 3.1). The prototype does not materialise that conjunction in
the measured graph: a structural condition or an enclosing if demotes the edge to
may but is not written into its guard, so the guard of a screen-to-screen edge holds
only the router’s guards. The evaluated graph therefore records that a navigation is
conditional without recording the condition. Only an optional mode that no table of
Chapter 5 uses keeps the enclosing condition.


3.2.5     Boundary
A navigation inside a signal effect has a firing condition that is a data dependence
on a reactive graph, of which only the read set is statically visible (Section 2.7). The
model gives such edges the modality unknown and records the signals read by the
effect as the symbolic guard. No pass in this version emits one, and the analysis
does not try to determine when these edges fire.

3.3       Implementation
The extractor was built for this thesis and is in the accompanying repository, evaluated
at commit a9d29df (Chapter 4). It consists of a framework-independent core, which
defines the graph model and the operations over graphs, and one adapter per
framework that maps source constructs onto the shared model. The Angular adapter
reads route configuration, templates and class code with the TypeScript compiler
API and emits screens and edges for routerLink attributes and Router.navigate
calls, each with the rule identifier and source location that produced it as witness.
    Scope attribution is a separate pass in the Angular adapter, enabled with the
option --attribution. With the option off, the extractor produces exactly the
baseline edge set, as checked on every application in the corpus. The pass implements
component nesting, router outlets and the call graph; stand-ins replace D and T
(below).
    The pass is switched on cumulatively in the evaluation (Section 5.3.3), at the
levels of Figure 3.1. Each level adds to the one before it, and the figure marks which
levels stand for earlier work and which only this thesis adds.
    Component nesting. Every component in the application, excluding test hosts
and stories, is read with its element selectors and template. An edge A → B is added
when A’s template contains an element with B’s selector. When a selector belongs
to more than one component, the candidates are narrowed to those that A’s file
imports. If none is imported, the analysis joins over all of them and records a note.
Edges from such a join are not capped at may, so a site in one candidate can be
placed on a screen that renders another. Claim 3.1 excludes such edges (Section 6.3).
The corpus has such joins in k8s dashboard and bitwarden. No must edge of the
final graphs cites a construct placed through one. An attribute selector is matched
the same way, so a directive has a scope as a component does.
    Router outlets. The route tree is recorded during route extraction. A route


                                                  36
component’s template is rendered on its own screen and on every descendant screen,
so its navigation sites get the scope subtree(r). A component is the application shell
when it is not routed, is not placed on a screen by the nesting relation and holds the
primary <router-outlet>. Everything it renders gets the scope ⊤. A component
that is not routed and not referenced, but whose subtree contains the outlet, is most
likely mounted by a route the extractor cannot see, for example through a helper
function that wraps a route table. It is also treated as shell. Its edges are capped at
may, so that Claim 3.1 is not put at risk by a scope that may be too large.
   Departures from Algorithm 1. The pass departs from the algorithm in two
respects.
    The first is that it does not propagate a scope into a component that a route
mounts. A routed component keeps subtree(r) and does not also receive the scope
of a component whose template renders it. Traversal does pass through a routed
component, so a component nested beneath it still receives the scopes of the com-
ponents above. Taken alone, this restriction can only shrink a routed component’s
scope. Two other rules can enlarge a scope beyond the model’s:

   • components that nothing references and no route renders, but whose subtree
     holds the primary outlet, are treated as shell and given ⊤, with their edges
     capped at may;

   • an ambiguous selector that no candidate’s import resolves joins over all candi-
     dates, which Claim 3.1 excludes.

A scope that is too small loses edges and cannot invent them, so the restriction
cannot put Claim 3.1 at risk; it costs recall, and the constructs it strands are counted
in Chapter 5.
   The second departure is in how the call graph of Section 3.2.3 is read. The pass
ranges over the members of classes, and a member of a component runs on that
component’s screens. A call this.f.g() is resolved through the declared type of f (a
constructor parameter, typed field, inject(T) field or @Inject(TOKEN) parameter).
The call resolves to:

   • the class that type names;

   • the classes a provider binds it to with useClass or useExisting; or

   • for an abstract class no provider binds, its subclasses in the application.

This is class hierarchy analysis [17] restricted to the declared type. Bindings are read
across the whole application rather than relative to the injector that resolves them,
so where two injectors bind a token differently the join covers both. This can only
widen a scope. A factory or value provider is not read. A call on a type declared
outside the application contributes no edge.
   The seeded call-graph iteration on its own reaches the least solution of its
constraints. The scopes emitted for service sites add two fallbacks to it:


                                          37
   • a member no caller reaches falls back to the join over every component that
     injects its class, the per-class approximation that the class level of the ablation
     applies to every service (Section 5.3.3);

   • a member the iteration does reach receives more screens where a caller the
     graph does not see reaches it: the join of that caller’s class is added, or this
     class’s own join if nothing places the caller.

Neither fallback is a constraint of Table 3.3. The first is not monotone in the call
graph, since adding a call edge can narrow a scope. The emitted service scopes are
therefore the least call-graph solution widened by these fallbacks, and not the least
solution of the constraints in Table 3.3. Service sites are held at may either way,
because the calls on the way carry conditions the analysis does not follow.
    Anchored edges. Edges with scope ⊤ are stored once at a node of kind scope.
Edges whose screen set is exactly subtree(r) for a screen r with at least one descendant
are stored once at a scope node listing the members of that subtree. A prefix route
that is not itself a screen is not anchored. Other screen sets are stored per screen. The
core provides the query edgesFrom(r) and a function that materialises all anchored
edges.
    Stand-ins for D and T . Two approximations stand in where the model has a
relation the pass does not implement. Section 5.3.3 withholds them below the full
level of Figure 3.1, so no lower level counts their sites.

   • Guards (for T ). A guard is given the screens of the routes that name it, as a bare
     identifier, in canActivate, canActivateChild, canMatch or canDeactivate:
     the screen of each such route, not subtree(r), and nothing for a componentless
     prefix. For a canDeactivate guard that is narrower than the model’s scope;
     for an entry guard it is not the model’s rule, since the redirect leaves the
     screen a navigation starts from. The stand-in can therefore be too small where
     navigations into the route start elsewhere, and too large where they do not
     start at the route itself.

   • Effects (for D). An effect, being registered for the lifetime of the application,
     is given ⊤.

Edges from both are capped at may. A class the call graph does not reach and
nothing injects still has no scope. The evaluation counts those in the loss category
“Attribution, service” of Table 4.3. One change was made to the baseline itself: for
components with an inline template, the witness now points at the construct’s own
line rather than the template’s first line; on the corpus the baseline graphs with and
without this change are identical. Unit tests cover each case above.

Chapter 4

Evaluation setup and research material

This chapter describes how the analysis of Chapter 3 is evaluated: the corpus
(Section 4.1), every ratio and measure (Section 4.2), and the five evaluation methods
with what each can and cannot show (Section 4.3). Chapter 5 reports the results.


4.1      Corpus selection and validity

4.1.1     Selection
Ten candidate applications were screened against six criteria: a real application
rather than a library or template; a nested, lazily loaded route tree; guards present;
end-to-end test configuration for a browser driver; retrievable history in which tests
and source change together; and an active repository. Six candidates were retained
(Table 4.1), each fixed to a specific commit so that the measurements can be repeated
on the same code. The criteria were fixed before any results were obtained.
    Criterion (4) was checked as configuration, not as a usable suite. At the pinned
commits only alfresco has specifications the test-source cross-check can read, so
that method covers alfresco alone; ghostfolio and bitwarden carry no browser-test
configuration at all. The criterion was therefore not applied uniformly: gravitee was
rejected for a thin UI suite while two applications with none were kept. Route-tree
size and end-to-end test density were inversely related, so the methods that need test
suites are applied only to the applications that have them, and the other methods to
all six.
    Four candidates were rejected; the counts were read from the repositories and are
not generated. angular/components is a component library with no product router.
vendure has 169 end-to-end specifications, all of which exercise the GraphQL server
and none the user interface. gravitee declares 618 routes but has 14 UI specifications.
SAP/spartacus has a large Cypress suite, but its routing is configuration-driven in
a way the extractor does not support; that reason is tool support, not one of the six
criteria, so this rejection rests on a ground added after screening began.




                                          41
4.1.2     Validity of an open-source corpus
Kalliamvakou et al. recommend filtering candidate repositories by explicit criteria
and reporting them [34, 35], which the selection above does. The remaining threats
are external validity (open-source applications may differ from proprietary ones) and
a possible selection bias, since I selected the corpus and wrote the extractor; the
departures from the criteria are the two stated above. Selection was not blind to
the tool: one candidate was rejected on a ground added after screening began, the
extractor’s own support. Pooled percentages are dominated by the largest application,
mifos, so per-application figures are the primary summary where the chapters give
them. The corpus spans nearly two orders of magnitude in routes, and the commits
and harness are released so the measurement can be repeated.
    A further threat is not addressed by this. The extractor was developed on this
corpus and is measured on it (Section 6.2), so the figures are fitted to it. The one
measurement outside it runs the frozen extractor on the seven subjects of Rima
et al. against their ground truth, preregistered before any subject was mapped
(Section 5.3.7). A case study on a proprietary Angular application, reporting only
aggregate figures, is planned as the most direct response (Chapter 6). The literature
reviewed in Chapter 2 offers no standard benchmark corpus of single-page applications
either, so the corpus and its manifest are an output of the thesis.


4.2      Metrics
Each research question is answered with one main measure; Table 4.2 lists every ratio
the thesis reports, and the paragraphs after it define the terms the table uses. RQ1
is measured at two levels, since a transition cannot be recovered without the screens
it runs between: the share of declared screens that have a node, and the share of
navigation constructs that yield at least one must transition. For RQ2, observed
failures are grouped into defect classes, a class being accepted only on two lines of
evidence, at least one from an evaluation method of Section 4.3, and every construct
not recovered is assigned to one loss category. RQ3 is measured with the analysis
disabled and enabled on the same extractor, and by the references below. RQ4 is a
sanity check of witness mapping by mutation testing, not an independent test. For
RQ5 each defect class of Table 5.4 is traced to its cause in the source and recorded
as read by the final version (the loss was the tool’s and not the application’s), still
unread although a static reader could, or beyond a static reader of a route table;
the result is a list of causes, not a ratio, and every site that still yields no transition
must carry a recorded label (Section 5.5).
    Navigation construct. A navigation construct is a routerLink binding in a
template, or a call to Router.navigate or Router.navigateByUrl in class code,
in the application source excluding tests. Constructs are found by a separately
written parser that shares no code with the extractor. Table A.1 qualifies what that
independence covers: for the route-path forms added during development, the two
resolve the same constructs by the same rules, and three of the independent parser’s
corrections were made because it disagreed with the extractor.

                                            42
   Must conversion (RQ1). Must conversion is the fraction of in-scope constructs
that are witnessed by at least one must edge. Three rules make it precise.

   • A construct is matched to a witness on its own line or on a line either side, to
     absorb offsets in the extractor’s locations. Two constructs on adjacent lines
     can therefore both be credited by one witness, so the ratio is an upper bound
     at line granularity.

   • Query-only navigations and the two exclusions of Table 4.3 are left out of the
     denominator as well as the numerator.

   • When several constructs produce the same edge, the extractor keeps the most
     certain as the witness and records the others as merged witnesses, each with
     the modality it earns on its own. A construct counts as converted only where
     it earns must itself.

    The other ratios. Several of these measures have been called coverage in the
literature this thesis builds on, but they differ on this corpus by more than an order
of magnitude (99.2 % of sites accounted for against 1.4 % converted to must). Node
coverage rises if less of an application is read, so the blind-spot count is printed
beside it. The accounted share alone measures whether the losses are declared, not
how much is recovered. The gap in recovered constructs is called the recovery gap,
and the loss tables measure it.
    Agreement between a scope and the rendered interface (RQ3). The
measures above cannot be asked the question the contribution turns on: is the set of
screens that attribution computes for a site the set that site can really fire from? The
rendered-interface check, run on the harness of the runtime route oracle (Section 4.3),
answers one direction. The harness navigates to each screen the graph holds, reads
the in-app links the DOM carries and compares them with the edges the graph’s
per-screen query yields there.
    A link rendered at a screen where the graph has no such edge is unambiguous: the
site was attributed to too few screens or never read. An edge the graph has and the
DOM does not show is weaker, since a template may render links conditionally and
this harness signs in to nothing; where a target could not be resolved to one address,
every address the static prefix admits is recorded at reduced confidence, which is
not a claim that the screen links there. This direction is therefore judged only over
predictions that name a destination exactly, and their number is published. Three
bounds apply. Only template-sourced sites are judged, since a Router.navigate
call in an event handler leaves nothing in the DOM. A screen whose guard redirects
to a sign-in page without a backend renders another screen’s links and cannot be
judged; such screens are counted apart, and on this corpus they are most screens
(Section 5.3.1). Ghostfolio’s per-locale build does not fit the harness, so it is measured
by every other method and by none of this one.
    The ablation and the structural reference (RQ3). Two measurements ask
whether the attribution computes a set of screens that agrees more closely with a
structural reference than a simpler analysis does, or only a larger one.


                                           43
   The ablation withholds the mechanisms of Section 3.2 one at a time and extracts
the whole corpus at each level:

   • Owned: a site belongs to the screen whose routed component’s own file holds
     it, the direct ownership of the Android literature.

   • Nesting: adds component containment through template element selectors.

   • Rooted: adds the shell rule, so a component the root renders is attributed to
     every screen. Oshima and Kishi assemble their page information from the root
     component as well (Section 2.4), so this level measures how far the prior work
     reaches here.

   • Outlet: adds router-outlet descent.

   • Full: adds the member-level call graph, with its fallback join and the stand-ins
     for guards and effects.

Each level adds to the one before it, so the full step is not one mechanism alone. A
sixth level, class, runs beside the nested ones and replaces the call graph with the
per-class rule, which joins a navigating service over every component that injects its
class. The harness checks on the real graphs that the levels nest: a (site, screen) pair
present at one level and absent at the next is a defect in the switch, and no table is
written.
    The structural reference is scored in both directions, which no other method
allows. For one application, the screens each navigation site fires from were read off
the sources by hand, with a derivation per site, in route-oracle/ground-truth/
realworld.json. It is the structural reference of Section 3.2.2, called the ground
truth below. A pair the reference has and a level does not is a scope too small by
the reference; the converse is a scope too large. Four limits apply.

   • On realworld it is one application, small enough to read exhaustively. A second,
     alfresco, is read under the same rules (Section 5.3.4).

   • It is the author’s reading, so it is not independent of the tool’s author. It is
     published with its reasoning so a reader can check it.

   • Its rules are the analysis’s own relations, and a template condition or guard
     that admits a screen only in one sign-in state does not narrow a scope under
     them. The ground truth therefore tests whether the implementation applies
     the relations correctly, not whether they match what the running application
     renders.

   • It is checked in one direction only: the scorer reports every site the graph
     places that the ground truth omits.

   The end-to-end navigation check (RQ3). The structural reference applies
the analysis’s own relations, so it cannot show that they miss a navigation the
application performs. This check takes its reference from execution. Two applications

                                           44
ship an end-to-end suite that can be run here. The first, realworld, runs against
the public demonstration backend, which is not pinned. The second, mifos, runs
against a local Fineract server with the image pinned by digest. A small module
added to each application logs every navigation the router completes while the suite
runs, with the route patterns of the screen left and the screen reached.
    An observed pair is such a source and target pattern for a navigation the applica-
tion itself triggered; back-button navigations and the first screen after a full page
load are excluded. A pair is contained if any edge, must or may, joins the two screens
once scope nodes are expanded to their members, with parameter names ignored.
An edge to an unknown target never counts. A hit is any such edge, not the edge
of the site the test used, so the check does not test the scope of an individual site.
Redirected navigations are compared on the address they asked for, as preregistered.
The scorer’s first departure from this rule is listed in Table A.1, and its figure is not
used.
   A missed pair is classified from the graph alone, by rules over the graph so that
no assignment is made by hand. The classes are tested in this order, and the first
match wins:

   • redirect: the navigation was redirected and the graph holds the pair on the
     address it landed on (the preregistered redirect class);

   • base: the target is reached from a screen above the source but not from the
     source, as a relative link resolved against the wrong route appears;

   • dynamic: the source screen’s routed component, or one above it, holds a site
     whose target the extractor records as unresolved;

   • other: none of these.

The base and dynamic classes were defined after the misses had been read. Because
of the order, the dynamic count is what is left after base. On mifos every miss met
the dynamic test whatever the order, so that count said little alone; Section 5.3.5
names the sites, which were repaired after the check.
    The counting rules, three validity checks and predictions for each application
were written down before any log was read, except for that departure. The checks
are that the instrumented and the plain suite pass and fail the same tests, that at
least ten distinct pairs are observed, and that a second instrumented run observes
the same pair set. The check measures recall on the transitions the suite exercises
and nothing else. The graph is an over-approximation, so that recall is containment,
and its weight depends on how many (screen, screen) pairs the graph holds, which
is reported beside it: realworld’s graph holds 71 of 100 possible pairs and mifos’s
162567 of 367236, against hits of 19 of 19 and 19 of 22. A hit rate is read only against
that share, since a denser graph contains more pairs by chance; by chance alone the
graphs would hold 13.5 and 9.7 of those pairs. A graph edge no test takes is not an
error, so the check cannot measure precision, and one run cannot refute a must edge.
    Loss breakdown (RQ2). Each construct is matched to the edges whose witness
cites it. A construct that is in scope, cited by no must or may edge and not accounted

                                           45
for is lost. It is assigned to exactly one loss category by the first rule in Table 4.3 that
applies. The categories therefore partition the lost constructs. Named outlets are
removed before the assignment, and guards are measured outside it. The categories
Constant target, Node missing and Other were not put through the admission rule
that maps a category to a defect class (Chapter 5).
    Guard defects do not appear in the table, since a wrong guard mislabels an
edge rather than removing it. No method here checks a guard label directly; guard
handling is exercised only by the guard-removal mutation operator and by the source
review of Section 5.5. The guard defect was found by red-team review of the graph
and the source, not by any check above.
    The nested branch decides a category from the owning route component, so a
construct can be assigned to a node category and still be converted once attribution
gives it a scope through the shell or a subtree (Section 5.3). The size of other counts
constructs left for inspection by hand, not one cause.
   Change in recovery and must-tier precision (RQ3). Must conversion and
the loss breakdown are measured on one commit of the extractor, run twice on
identical inputs with the attribution pass disabled and enabled. With the pass off the
extractor reproduces the baseline edge set exactly on every application (Section 3.3).
   Must-tier precision is the fraction of must edges that meet two conditions. The
witness line contains a construct of the claimed kind with the claimed target, and
the destination node sits at an address the independent route set declares; otherwise
a node minted at an address the application never mounts would pass.
    An edge whose destination the check cannot read is neither a pass nor a failure,
so precision is stated as bounds: the share of must edges that pass and the share
that do not fail. RQ3 is not decided by one rule. An attribution that put every site
on every screen would raise the recovered share without lowering must conversion or
must-tier precision, so those figures alone cannot fail. RQ3 is therefore answered by
three measures read together: the recovered share and must conversion over the same
construct denominator; the width of the computed screen sets against that trivial
assignment (Section 5.3.2); and agreement with references that do not come from the
attribution’s output alone, namely the two structural references, the applications’
own suites and the comparison with Rima et al.’s tool (Section 5.3.6). The must
tier’s precision bounds are reported for both runs, but they cover different sets of
must edges and are not compared as rates.
    Detection rate (RQ4). This is a sanity check of the mapping from a source
change to its witness in the graph, not evidence of change-impact detection. It is
close to guaranteed by construction, since the sample is drawn from the graph, and
the harness was tuned on its misses (Section 4.3.2). The detection rate is the fraction
of injected source changes that produce the predicted change in the graph, reported
per mutation operator with its n. A change whose construct the graph does not
contain is excluded and not counted as a miss, since it can only repeat a recovery
gap that the loss tables measure. The rate is therefore conditional on recovery, and
the number of excluded mutants is reported alongside it.

two extractions from the same unchanged source give identical nodes and edges.

extracting after deleting it. Without them, differences seen in mutation testing could
not be told from noise.

5.3.2        What the attribution discriminates
The rendered-interface check cannot say whether the scopes are too large, so this
subsection asks how much narrower the computed attribution is than the widest one
there is. Assigning every navigation site to every screen recovers every construct and
needs no analysis. The ratio between the two measures what the analysis contributes
(Table 5.12).
   The analysis is between 1.7 and 18.7 times narrower than that baseline, and
the low end of the range is the figure that qualifies RQ3. On k8s dashboard the

5.3.8     The tool of Rima et al. on the same applications
This comparison runs their tool (commit f33003f) rather than scoring against the
reference it generated. Its static stages, extraction and workflow enumeration, were
run on their seven subjects and on the six corpus applications; its test stages need

output on the corpus was read. On each of their subjects their tool yields as many

the six whose reference is written in the same form. A workflow claims a transition

start route as the terminal, and such workflows are left out. Each claimed transition

edges with scopes expanded. Relative recall is a share of that union, not recall
against all real pairs, and a tool that proposes many pairs enlarges the union it is
measured against. The union is split per application into pairs both tools find and
pairs only one finds, and an only-ours stratum of more than 1000 pairs into those
only the shell reaches and the rest. Each stratum, or a seeded sample of 12 where it
is larger, was read from the source without the reader being told which tool proposed
a pair. Precision is a tool’s share of real pairs among those it finds; relative recall is
its share of the real pairs either tool finds.

model is not correctness; of the 41 I judged, 41 agreed with it (Wilson 95 % interval

5.5.3    The final tier and the node set
The final tier. The attributed must tier has 0 witness-check failures among 159
edges, with 62 destinations unread, which are neither passes nor failures. The unread
destinations are the toolbar edges of one application, whose source side rests on the
scope of its chrome component and on the route-order assumption. The witness
check compares the destination a construct names with the destination its edge
names; it does not ask whether the construct runs every time or whether the router
lets the navigation through, which the demotion rules cover. Neither the source
reading of the must tier (Section 6.2) nor the mechanical check is an independent
proof of Claim 3.1.

The whole graph. Over the whole graph the check says much less. The 13830 edges
cite 15638 locations, and only 7.0 % are clean, because 87.2 % are over-approximations
for which the check claims no target agreement. 39.4 % of all edges (5454) come from
one call site in mifos, view-transaction.component.ts:135, a navigateByUrl to
a template literal with an empty static prefix. mifos holds 89.9 % of all edges, so
figures pooled over the corpus are mostly mifos’s. Of the 1437 locations the check
judges, 76.2 % are clean, and none of the rest is cited by a must edge. A precision
figure for the must tier is not one for the graph.

The node set. Across the corpus the compared graph declares 0 screens at
addresses the framework mounts nothing at. Every address the extractor claims is
an address the framework’s own configuration mounts, which is external evidence
about these six applications that the two static readers could not produce, since
an address both place at the wrong prefix is one they agree on. The evidence is a
precondition of the must-tier property and not part of it, and it is bounded by what
a census keyed on addresses can represent: entries on a named outlet or decided by
a UrlMatcher (65 route entries) are counted in neither column.

The runtime route oracle. The oracle loads each application, built in its develop-
ment configuration, in a headless browser, reads the live router’s route configuration
after expanding every lazily loaded subtree, and counts an address as mounted when
the configuration places a component there on the primary outlet. No route file is
parsed. Against the 1146 addresses it mounts, the node set is 892 of 1146. The oracle

ran on an earlier graph (29–30 October) with the same node total, one corrected

5.6      Dead links, found from the source
A site whose target the application mounts nothing at is a dead link. The method
finds candidates for such links at no extra cost. The candidates are found statically,
and each is then checked against the route configuration the runtime route oracle
recorded before it is reported. The result is a candidate list and not a verdict: no
candidate was navigated to in a running application, so that a link is reached at run
time is not established.
    The clearest case is mifos, where a transactions tab links to /journal-entry/
view/:id although the application declares that screen at /accounting/
journal-entry/view/:id. The link omits the parent prefix, and mifos’s catch-
all route renders the not-found screen, which a user can mistake for missing data
rather than a broken link.
   The list is not one defect class, and the split matters for what each part is worth.

   • 18 of the candidates are an absolute link written against a path the application
     does not mount, usually the name the server uses rather than the one the
     router does. Those are the application’s.

   • 5 come from a relative routerLink, such as [routerLink]="’edit’" or
     [routerLink]="[’../../transactions’]". Their target depends on the
     route the link resolves against, that of the component holding it (Section 3.2.6),
     so a wrong base is the analysis’s question before it is the application’s defect.

   • 6 are neither, because the result files do not record enough of the construct to
     say which it is. They are counted and not classified, rather than assigned to
     the half that would flatter the finding.

    The last two groups are reported as candidates and weighted lower. Counted as
places in the source rather than as targets, the three groups are 18, 3 and 6; the
difference is one relative link in a shared template that resolves against three owning
screens.
   A further 69 sites are not published at all, because they sit outside the directory the
measurement is scoped to, in ../../libs, ../aca-shared, ../browser, in the repositories of
2 applications. Most are the source of a sibling front end whose own router declares
the same addresses a census would have called dead; they are counted here and left
out of the census.

Chapter 6

Discussion

This chapter interprets the results of Chapter 5; it does not repeat them. The
extractor loses transitions in two places, at the nodes and at the edges, and each
level limits what the other can achieve.


6.1      Key findings
Two places where extraction fails. Node completeness has two readings. Node
extraction is complete on all six applications against the readers of the route con-
figuration (Table 5.3), and the loss classification is computed against this weaker
reading. The runtime route oracle observes no node placed at an address where the
framework mounts nothing. That shows that no such error was observed, not that
none can occur. Against the mounted addresses the route configuration the oracle
reads holds 251 addresses with no node, 242 of them in ghostfolio (Section 5.5.3),
so only 2 of the six are complete in this stronger sense of a node for every mounted
address, which is what a user of the graph would want. The node defects (constant
paths, lazy boundaries) are traced in Section 5.2; the final version reads their causes
(Section 5.5), and those losses are empty.

What remains is lost at the edge. The navigation sites exist in the source
and the screens they would connect exist in the graph, but the extractor cannot
decide which screens a site belongs to. The exceptions are sites that the diagnosis
labels as having a target screen with no node. The label also covers targets held in a
field. Most of these sites are in ghostfolio (Table 5.10). Under the order in which
the loss rules are applied, scope attribution addresses the largest loss category in
every application (Table 5.5), but that order is part of the measure (Section 6.2).
The ranking is a fact about an extractor, not a limit of the approach. The two
levels are not independent: attribution cannot draw an edge into a screen that has
no node, and a complete set of nodes yields few transitions while the sites outside
the component a route renders stay unattributed. Chapter 5 therefore reports node
coverage beside must conversion.




                                          80
RQ3 and what the loss rules can delimit. A lost construct is assigned to the
first loss category that applies (Table 4.3). A construct inside a shared component
that appears only in screens without nodes is therefore counted as an attribution
loss, although attribution alone cannot recover it: the categories partition the losses
diagnostically and do not bound what attribution recovers.
    The demotion rules decide whether the edges attribution added at k8s dashboard
(its toolbar edges, Section 5.5.3) occur on every input. 125 of them are kept at
must. The demotion rules were written during development, in part in response to
objections from red-team panels run with the AI assistant. The witness check finds 0
failures among the 159 must edges. It cannot read the destination of 62, all of them
k8s dashboard’s toolbar edges. So only about half of that application’s must edges
are read.

RQ4 is a sanity check, and it is conditional on RQ1. The test checks that
the witness mapping reacts to injected edits; it is not evidence of change-impact
accuracy. Leave aside the rename operator (22/22), whose detection is close to
guaranteed by construction; the denominator of the other three operators is 45,
with rename excluded. The other three operators are generated or scored only at
constructs the graph already represents in the simplest form the extractor reads.
They are detected in 45 of 45 scored mutants on the attributed graph (Section 5.4):
every deleted routerLink, 20/20 retargeted calls and 11/11 removed guards. The
mutation harness was corrected during development after its misses had been read
(Section 4.3.2), so the clean result is not an independent test. It does not show that
the remaining operators would survive a larger or differently drawn sample.
   For guards, a detected mutant differs from an unobservable one in whether any
edge enters a screen the guarded route yields, which is the exclusion rule (Section 5.4).
The class “guards unreliable in both directions” of Chapter 5 rests instead on what
Section 5.5 measured: a guard carried by a route a wrapper function returns, and
a canActivate element written as a call. Source review in red-team panels found
those defects, not the witness check; the mutation run neither confirms nor refutes
the class.
    Given that a construct is represented in the graph, every scored change to it was
visible. The probability that it is represented at all is what RQ1 measures. This
form of claim suits change impact analysis, whose queries concern only the part of
the application that the model represents.

Two uses of the graph. The first is change impact analysis, supported only by
a sanity check of the witness mapping. Every edge carries the file and line of the
construct that produced it, so changed lines map to the edges whose witnesses fall
inside them and from there to the screens those edges leave and enter. This is the
screen-level counterpart of Chianti [61], in the impact analysis tradition of Arnold
and Bohner [4, 12, 43]. RQ4 shows only that the mapping reacts to the injected
edits for the constructs the graph represents, in a test that could hardly fail. That
is a property such an analysis needs, not a measure of its accuracy (whether every
affected screen is named, and how many in excess).

                                           81
    Neither use was tried by a consumer: consumer use is not measured. The may
tier is a candidate generator; only the must tier (25 constructs) is meant to give
transitions that hold under the assumptions of Claim 3.1.
    The second, not itself measured, is checking in continuous integration at no exe-
cution cost. The graph is recomputed from source on each commit, deterministically
and without installing, serving or crawling anything (Section 4.3). Properties such
as “a screen still has an inbound deterministic transition” can then be asserted like a
type check. A guard assertion is the member of that list the graph cannot yet carry,
and for a screen no edge enters there is nothing to read. A dynamically built model
needs a running application, test data and an exploration budget [50, 51, 36].

Where both uses stop. Both stop at runtime dynamic routing: a target computed
from a value, a route table assembled at startup from configuration, and an overlay
no route describes. There the static graph is silent or over-approximates into the may
tier, which carries no soundness claim. Only the must tier is meant as a lower bound
on the navigation an application can perform, and only relative to the assumptions
of Claim 3.1 (route order, ambiguous selector joins, the unresolved-call rule, the
execution model), each with a class of counterexample; Section 3.1 counts the edges
resting on the first two, so a query that must not miss a transition cannot be answered
from the graph alone. Authentication bounds the deterministic tier in the same way:
a guard decides on state the source does not fix, so a reader that keeps Claim 3.1
demotes it. The small must tier is largely this fact, a matter of definition rather
than a defect of the extractor. Taking every guard to let the navigation through
raises the tier from 159 to 203 edges (Section 5.5).

6.3      Declared approximations
This section lists the constructs the analysis does not decide, so that a consumer of
the graph can tell which queries it may ask; Appendix B gives the list in Table B.1.
The list separates constructs read exactly, where a failure is a defect that Chapter 5
counts, from constructs approximated, where no completeness is claimed. Constructs
of the approximated group still count in the construct denominator of Table 4.2,
as dynamic, unplaced or attribution losses. Before the repairs of Table A.1, the
end-to-end check found one such cost on mifos, the base of a relative link in a
template shared with child tabs; no remaining miss is of this kind (Section 5.3.5).
The first two rows were found by the runtime route oracle of Section 5.5.3 and not
by reading the analysis; both are places where the analysis is silent rather than
approximate.




                                               89
6.3.1     Why the may tier is incomplete
The may tier is meant as an over-approximation (design intent, Section 3.1), not a
proved upper bound: some rules do not over-approximate (first route, one segment,
catch-all order, dispatch, dialogs). A transition the application takes and the graph
lacks is therefore a defect, while an excess may edge is not. Table 6.2 sorts every
transition still missing in the two suites (Section 5.3.5) and the two structural
references (Section 5.3.4) by where its destination is fixed. Inside the static boundary,
the frontend source, a library under node_modules or configuration committed to
the repository fixes it, so a better reader recovers it: these rows are known limitations
of this tool, not of static extraction. Outside it, the backend supplies the target or
the route, configuration is fetched at run time, or user input changes the destination
screen. A third class, held, is a suite pair the graph holds on the screen a redirect
lands on, which the preregistered rule scores on the address asked for: no reader
turns it into a hit, so it counts toward neither side. On alfresco every missing (site,
screen) pair of the reference lies inside (133 of 133); on mifos 1 of the 3 missing
suite pairs lies inside and 2 are held; realworld misses nothing in either measure. A
reader that recovered every inside miss would hold 100.0 % of alfresco’s reference
pairs (now 23.6 %) and 90.9 % of mifos’s suite pairs (now 86.4 %). This is the static
ceiling on these four measures, and on the references it is weak evidence: both apply
the analysis’s own relations (Section 5.3.4), so none of their pairs can lie outside the
boundary, and realworld’s was partly completed from the graph’s output. Only the
suites can show an outside miss, and on two applications they show none. The ceiling
does not reach causes these measures do not exercise, such as the two Section 5.5.1
places beyond any static reader of a route table. It bounds the missing direction
only: the excess of the may tier is not scored, and the mifos graph holds 162567 of
the 367236 possible pairs (Section 5.3.5). The classes are the author’s reading of
each miss; the script that joins them to the scores refuses a miss without a class and
a class without a miss.


6.4      Transfer to other frameworks
All measurements in this thesis concern Angular; nothing was measured for React
with React Router or Vue with Vue Router [60, 80], and what follows is a qualitative
reading of the routers’ documented behaviour, not a result. The graph model,
the lattice of scopes, the fixpoint, anchored edges and the expansion query do not
mention Angular and would transfer unchanged, and outlets would too, since in
all three routers a parent route renders a placeholder for the matched child. What
changes are the four input relations of Section 3.2, which must be derived from the
other framework’s constructs. The call graph is easier in React and Vue, because a
hook or composable gives every navigation site an owning component. Component
nesting is harder in React, where components are created in JSX and recovering the
nesting relation becomes a data flow problem closer to points-to analysis than to
reading a template. Guards change scope: a React Router loader redirect plays the
role of canActivate, and Vue’s global beforeEach corresponds most closely to a

6.5       Future work
In order of how much each would change what the thesis can claim:

   • An oracle for the screen set on a large application. The hand-built ground
     truth of Section 5.3.4 covers only the smallest application, whereas most
     of the corpus’s attributions are made on applications of hundreds of screens


                                                91
      (Table 5.12). Either read the rendered links of such an application in a signed-in
      state, or annotate a stratified sample of its sites.

  • The unimplemented part of the model. The prototype leaves out the dispatch
    relations that carry NgRx effects and router event subscriptions, the injector
    hierarchy (it takes every provider binding as application-wide; Section 6.3), and
    guards that return a UrlTree. The wider treatment of guards in Chapter 3
    is the more substantial piece of work; its test, the guard-removal operator,
    reaches on this corpus only guards the graph already records (Section 5.4).

  • A runtime tier. Observation identifiers are already admitted as witnesses.
    Setting such a tier against the dynamic lineage [50, 51, 74] would show how
    much a crawler finds that the static graph lacks, and the reverse. An observed
    run is evidence that a may edge exists, not a promotion to must, and a candidate
    never observed stays may, so Claim 3.1 is not weakened. This thesis neither
    builds nor measures it.

  • A larger and broader corpus. An automated search over a larger pool of
    repositories, keeping applications the extractor handles badly [34, 35], would
    weaken the tool-driven selection bias of Section 6.2; a case study on a proprietary
    industrial application, reporting only aggregate figures, would answer the
    external validity threat.

  • The motivating use. Whether such a graph improves mobile testing agents,
    coding agents (Chapter 1) or automated test generation remains unmeasured
    and is a controlled experiment this thesis does not attempt.


6.6      Summary
The transfer argument is a hypothesis, not a measurement. The most valuable next
steps are an oracle for the screen set on a large application and a runtime tier that
completes the graph for signed-in use.

Contributions. The primary contribution is the measurement: a corpus of six
pinned applications, five evaluation methods with different blind spots, four further
checks of the scopes, and a classification of every lost construct. The second is the


                                              95
extractor, built in this work. It accepts nested and parameterised route trees, which
the stated restrictions of an earlier Angular extraction exclude. Those restrictions
admit 0 of the 6 corpus applications (Section 5.3.6). The extractor extracts all of
them. The third is the apparatus that makes the measurement checkable. The
result tables are generated from the harness’s result files. The methods that read
the sources re-run from pinned commits. The runtime route oracle re-runs only
in part. The realworld end-to-end check depends on an unpinned public backend.
Superseded figures cannot be regenerated. The fourth is scope attribution, specified
as a dataflow analysis over screen sets and implemented over three of its four input
relations (Section 3.2). Most of its recovery comes from the mechanisms of earlier
work, which it contains as levels; the one step it adds, the placement of navigation
inside services, adds 36 sites (2.0 %) over outlet descent (Section 5.3.3) and accounts
for the transitions it adds over their rules on their own subjects (Section 5.3.7).

What remains open. The dispatch relation is specified but not implemented,
the guard relation is replaced by a stand-in, and the call graph ignores the injector
hierarchy. The screen sets were checked in both directions on two applications only,
against references that apply the analysis’s own relations. Further, the extractor
was developed on the same corpus it is measured on; on the seven applications of
Rima et al., which it was not developed on, it holds 69 of the 73 reference pairs,
after four defects found there were repaired (68 before them), so those figures too
are now partly fitted (Section 5.3.7). Beside their tool on the same applications
the comparison rests on readings by the AI assistant of small samples, of which I
confirmed 41 of the 41 I re-read (Section 5.3.8). The end-to-end check on mifos
found transitions lost to target forms the extractor did not read and to a relative link
resolved against the child tab’s address rather than the route that holds it. They
were repaired after the check, so its final mifos figure is in-sample (Section 5.3.5).
The readings of the must tier were made by the AI assistant, and two readings
by one model measure consistency rather than correctness. The rendered-interface
check judged only the screens that are reachable without signing in. Driving the
applications into a signed-in state is the work that would test the rest (Section 6.5).
Finally, consumer use is not measured: whether such a graph helps the consumers
that motivated the work, such as agents that drive a user interface or automated
test generation, is untested here.
   What the measurements establish is that a declared route table is a starting
point for static navigation extraction, but not a sufficient one. The may tier is a
candidate generator whose edges a consumer must still check; only the must tier (25
constructs) is offered as transitions that hold under the assumptions of Claim 3.1.
