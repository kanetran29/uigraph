\chapter*{Abstract}
A UI transition graph describes the screens of an application and the transitions a
user can cause between them. Static extraction of such graphs is well established for
Android, where each event handler can be attributed to the widget that registered it
and thus to a single window. For web applications, navigation models have been built at design time, extracted statically from server-rendered applications, or obtained by crawling a running application. Earlier work extracts them
statically from the route configuration of a client-side framework for three different
purposes --- model checking, restricted to applications that declare no nested routes, no
route parameters and no data-bound navigation; end-to-end test generation; and
access-control checking --- and in none of the three did this review find a measurement of
what the extraction fails to read.

This thesis measures static extraction on six open-source Angular applications with
14 declared route entries to more than nine hundred, using a pinned corpus and five
independent evaluation methods. Measured at two levels, the extractor mints a node for
every screen the route configuration declares, as two independent static readers
enumerate it, and recovers a small fraction of the navigation constructs as
deterministic transitions; before the defects this thesis identifies were repaired, two of
the six yielded a list of routes with no transitions at all. The node result is bounded
by what a reader of the route table can enumerate: a runtime probe that visits every
address the applications answer finds \ProbeMissed{} mounted addresses with no node,
\ProbeMissedGhostfolio{} of them in a single application, and only \ProbeExactApps{} of
the six are exact against it.

Every lost construct is assigned to one defect class. Attribution is the largest
class in every application of the corpus once the
node-level defects this thesis identifies are repaired. In a web application, a navigation site
frequently has no single owning screen: it may be located in a shared component, in
an injected service, or in a route guard. The thesis formulates attribution as a
dataflow analysis over a lattice of screen sets, computed as a fixpoint over component
nesting, router outlets and a call graph that takes dependency injection into account.
It states a soundness property for the deterministic tier, which it tests mechanically
rather than proving, implements the nesting and outlet parts, and evaluates them on the
same corpus with the same methods. With attribution, \AttrRecoveredShare{} of the
constructs that loss class holds are recovered, on every application in the corpus, and
precision on the deterministic tier does not fall. Almost all of the gain is navigation the
graph reports as possible rather than certain. On the one application small enough for the
screens each navigation site fires from to be read off the sources by hand, the computed sets
are right about \GTFullRecall{} of those attributions. Most of that is not new: attributing
what the root component renders to every screen, which earlier work already does, reaches
\GTRootedRecall{} of them and attributes nothing the application does not, while every wrong
attribution any level makes comes from a rule this thesis adds. On the other five applications
the sets are checked in one direction only, which is the work's sharpest limitation.

Mutation testing on three of the applications shows that the graph detects \MutDetected{}
of \MutScored{} injected source changes, against \MutBaseDetected{} of \MutBaseScored{}
without attribution. Those two sets are not the same, because a change to a construct the
baseline graph holds no edge for cannot be scored against it; on the \MutPaired{} mutants
both graphs can score, the figures are \MutPairedDetected{} and \MutPairedBaseDetected{}.
Attribution therefore raises both the number of changes that can be scored at all and,
by the smaller paired margin, the rate at which a scored change is detected.

Finally, the thesis asks whether the losses belong to the applications or to the tool. Each
defect class is taken to its root cause and repaired where the cause is the extractor's.
Almost every defect class turned out to be a construct the extractor could read and did not,
and the exception is instructive: one application computes a route's path in a custom matcher
function, which no reader of a route table can resolve. With the readable classes repaired,
\RoundTwoFullNodes{} of the six hold a node for every screen the static readers find
declared, \ProbeExactApps{} of the six hold one for every address the running
application answers, and \RoundTwoAccounted{} of the navigation sites that remain in
scope are accounted for, as a transition, as a destination only the run time knows, or
as a source the analysis cannot place; the sites excluded from that scope, and the
ground for each exclusion, are counted in Chapter~5. Every site that remains names its reason.
Some of those reasons are dead links the graph finds without running the application, though
the count of them is a candidate list: a route the tools fail to read is indistinguishable
from one the application never declares. The deterministic tier that survives this scrutiny is small and
exact: across the corpus it holds the transitions into the screens a user reaches before
authenticating, and nothing else, because an application that guards its interior has
almost no unconditional transition to find.

\chapter*{Use of AI tools}

Aalto University asks that the use of artificial intelligence tools in a thesis be
declared. An AI coding assistant was used in three ways in this work, and I am responsible for the
whole of the result.

The extractor under study and the evaluation harness were written with the help of an AI
coding assistant. Every number reported in this thesis is produced by running that
harness, and the result tables and plots of Chapter~\ref{ch:results} are generated from
its result files, except the two tables marked as compiled by hand, so that any number can
be reproduced from the commits recorded with it. The diagrams in
Chapters~\ref{ch:introduction} to~\ref{ch:evaluation} were drawn by hand.

The assistant was also used during the literature search, to locate candidate sources and
to summarise them. No source is cited on the strength of such a summary. Every entry in
the bibliography was checked field by field against the publisher page, Crossref
metadata, arXiv metadata or DBLP before it was cited, and sources that could not be
checked in this way are kept in a separate block in the bibliography file and are not
cited anywhere in the text.

Finally, the assistant was used to draft and edit prose, which I then revised. The
research questions, the design of the analysis, the evaluation protocol and the
interpretation of the results are my own, as is the responsibility for every claim made
here.
